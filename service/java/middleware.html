服务端中间件全景与 Java 实战 ​

本质一句话：中间件就是"把某个能力从你的进程里搬到另一个进程里"。搬出去能换来共享、高可用、削峰，代价是：多一个会挂的东西、多一套一致性问题。

这篇的定位

本篇站在 Java 服务端视角讲五个最常碰的中间件：Redis、MQ、ES、对象存储、Nacos。

原理不重复讲——Redis 的数据结构、MQ 的投递语义、ES 的倒排索引，在 后端基础 等专篇里已有（Redis 见 Redis 入门），本篇只讲**「Java 侧怎么接、接完会踩什么坑」**。深度需求按需跳转：

组件原理专篇
RedisRedis 入门
MQ消息队列（Kafka）入门
ESElasticsearch 入门
分布式一致性分布式基础、数据分布场景与锁设计
微服务组件Spring Cloud 微服务

1. 用途：什么时候该上中间件 ​

难度：了解

1.1 三个引入信号 ​

中间件不是"标配"，看到这三种信号才考虑上：

信号典型场景该上什么
① 同样的计算重复了很多次同一个商品详情被查了 1 万次Redis
② 下游抖动会拖死我发个通知要调 3 个服务，其中一个经常超时MQ
③ 数据量大到不能只靠 LIKE 搜百万级商品，要按关键词模糊匹配ES
④ 二进制数据塞不进 DB图片、PDF、Excel对象存储
⑤ 服务之间要互相找到，且要独立扩缩容从 1 个服务拆成 5 个Nacos

1.2 反过来：什么时候不该上 ​

这是更值钱的部分——中间件是负债，不是资产：

场景为什么别上先做什么
数据量还小（几千条）Redis / ES 的运维成本 > 收益把索引建好，够用
单机部署、流量很小多一个组件 = 多一个故障点先单体跑通
只是"以后可能会用"提前引入 = 提前学习成本 + 提前踩坑等信号出现
团队没人运维过中间件出问题时没人会救先在小项目里跑一遍

一条判断标准：中间件带来的复杂度增量（一致性问题、故障面、排查链路）必须小于它带来的性能/解耦收益。单体项目加 Redis 缓存很容易，加了之后还要处理"缓存和 DB 不一致"——那是另一笔账。

1.3 中间件的共同代价 ​

不管你上哪个，这三笔账要提前认：

代价具体表现
多一个会挂的东西Redis 挂了，缓存穿透直接打到 DB；MQ 挂了，消息堆积
数据不再在同一个事务里本地事务管不到 Redis / MQ / ES，一致性要单独设计（这是最大的坑，见 5.1）
排查链路变长一个慢请求可能横跨 5 个组件，日志、链路 ID、监控都得跟上

自检：Nacos 控制台能打开，但服务注册不上去（服务列表为空），且日志里没有明显报错。你先查什么？

参考答案

先查 9848 端口（gRPC 端口）通不通。Nacos 2.x 的服务注册走 gRPC，只映射 8848 会导致"控制台能访问（HTTP），但注册请求发不出去（gRPC）"。docker-compose 里没映射 9848 是最常见的原因。

其次确认 spring.cloud.nacos.discovery.server-addr 写的是 localhost:8848 而不是 http://localhost:8848（协议前缀会让解析出错）。

最后看日志里有没有 Client not connected, current status: STARTING 之类的字样——Nacos 2.x 客户端会先等连接建立，超时后才报错，容易被忽略。

3. 用法：五个组件在 Java 侧怎么接 ​

难度：会用

3.1 Redis：缓存的读与写 ​

核心心智：Redis 在 Java 服务里最常见的角色是缓存——把 DB 的查询结果放在内存里，下次直接拿。

先说清一致性前提：Java 侧用 Redis 缓存，几乎一定是"旁路模式"（cache-aside）：

text
读：查缓存 → 没有 → 查 DB → 写回缓存 → 返回
写：改 DB → 删缓存（不是更新缓存！）

为什么是"删"而不是"改"：并发写时，"改缓存"可能用旧值覆盖新值；"删缓存"让下次读重新从 DB 拿，永远不会不一致。代价是下次读会打一次 DB——这就是缓存三大问题的来源（见 Redis 入门）。

代码怎么写——两种风格，按场景选：

java
// 风格一：手动（需要精细控制时用）
@Service
@RequiredArgsConstructor
public class ProductService {

    private final StringRedisTemplate redis;
    private final ProductMapper productMapper;

    private static final String KEY = "product:detail:";

    public Product getById(Long id) {
        String cached = redis.opsForValue().get(KEY + id);
        if (cached != null) {
            return JsonUtil.parse(cached, Product.class);
        }
        Product p = productMapper.selectById(id);
        if (p != null) {
            redis.opsForValue().set(KEY + id, JsonUtil.toJson(p), 30, TimeUnit.MINUTES);
        }
        return p;
    }

    public void update(Product p) {
        productMapper.updateById(p);
        redis.delete(KEY + p.getId());     // ← 改 DB 之后删缓存
    }
}
java
// 风格二：Spring Cache 注解（简单场景够用）
@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductMapper productMapper;

    @Cacheable(value = "product", key = "#id")           // 读：走缓存
    public Product getById(Long id) {
        return productMapper.selectById(id);
    }

    @CacheEvict(value = "product", key = "#p.id")        // 写：删缓存
    public void update(Product p) {
        productMapper.updateById(p);
    }
}
手动@Cacheable
控制力强（能拼 key、能设不同 TTL、能在 miss 时做兜底）弱（key 表达式受限）
代码量多少
坑忘了删缓存 / TTL 没设默认 key 是参数拼的（对象参数要小心）、默认 TTL 无限

⚠️ Spring Cache 的两个默认值要记住：① 没配 TTL，缓存永不过期；② key 默认由参数生成，参数是对象时用的是 hashCode（上一篇讲过 @Data 的 hashCode 那个坑）。

分布式锁（跨实例互斥）：

java
// 用 Redis 的 SET NX EX 语义取锁，释放时必须带 value 校验
Boolean ok = redis.opsForValue().setIfAbsent("lock:order:" + orderId, "req-uuid", 10, TimeUnit.SECONDS);
if (Boolean.TRUE.equals(ok)) {
    try {
        // 临界区
    } finally {
        // 释放前校验 value 是自己持有的那把锁，否则可能删掉别人的锁
        if ("req-uuid".equals(redis.opsForValue().get("lock:order:" + orderId))) {
            redis.delete("lock:order:" + orderId);
        }
    }
}

注意：Redis 锁是尽力而为的（Redlock 有争议），要求绝对可靠还得靠 DB 的唯一约束 / 行锁。能用数据库约束解决的，别用分布式锁（同 数据分布场景与锁设计 的思路）。

3.2 MQ：把"必须做的"和"可以晚点做的"拆开 ​

核心心智：MQ 的价值不是"快"，是解耦 + 削峰 + 异步。

text
没有 MQ：用户下单 → 扣库存 → 发短信 → 发积分 → 记录日志 → 返回
          每个下游都同步等，任何一个慢，用户就等

有 MQ：  用户下单 → 扣库存 → 发消息 → 立即返回
                     ↓
              消费者各自慢慢处理（短信、积分、日志）

Java 侧最小示例（Spring AMQP，RabbitMQ）：

三个必须答得出的问题（面试固定节目，原理见 MQ 入门）：

问题答案对应配置
消息怎么不丢生产端 confirm + 持久化交换机/队列/消息 + 消费端手动 ackpublisher-confirm-type: correlated
怎么不重复消费接受重复，靠幂等：唯一索引 / 状态机 / 去重表业务层保证
顺序怎么保证分区/队列内有序（同一 key 进同一分区）；全局有序 = 单分区 = 没有并行routingKey 设计

幂等是最容易被忽略的：MQ 只保证"至少一次"，重复消费是常态。所以消费逻辑必须幂等：

java
// 幂等的标准做法：用唯一索引兜底
public void handleCreated(Long orderId) {
    try {
        pointService.addPoints(orderId, 100);      // 里面用 INSERT IGNORE / 唯一索引
    } catch (DuplicateKeyException e) {
        log.info("订单 {} 已加过积分，忽略", orderId);   // 重复消费直接吞掉
    }
}

延迟消息（"30 分钟后取消未支付订单"）：

方案说明
RabbitMQ TTL + 死信队列每条消息设 TTL，过期后进死信队列再消费；队头阻塞（后面的消息会等前面的过期）
RabbitMQ 延迟插件x-delayed-message 插件，直接指定延迟毫秒数
RocketMQ 定时/延迟消息原生支持等级延迟（1s 5s 10s … 2h），国内项目常用它做这个
Redis + 延时队列时间轮/ZSet，自己实现，适合简单场景

3.3 ES：模糊检索 ​

核心心智：MySQL 的索引对 LIKE '%x%' 无效（前缀都定不了，走不了索引）。ES 倒排索引天生为"任意位置包含关键词"设计。

什么时候该上 ES：

需求MySQL 行不行
精确匹配、范围查询、排序✅ MySQL 完全够，别上 ES
前缀匹配（LIKE 'abc%'）✅ 能走索引
任意位置包含（LIKE '%abc%'）❌ 走不了索引 → 上 ES
分词搜索（"手机壳" 搜到 "保护壳"）❌ MySQL 不分词 → 上 ES
相关性排序、聚合分析❌ → 上 ES
海量数据 + 高并发❌ → 上 ES

Java 侧接入（Spring Data Elasticsearch）：

java
// 实体：@Document 指定索引名，@Field 指定是否可检索/是否存原始值
@Document(indexName = "product")
public class ProductDoc {
    @Id
    private Long id;

    @Field(type = FieldType.Text, analyzer = "ik_max_word")   // 中文分词
    private String title;

    @Field(type = FieldType.Keyword)                          // 精确匹配（不过分词）
    private String category;

    @Field(type = FieldType.Double)
    private BigDecimal price;
}
java
// 查询
@Service
@RequiredArgsConstructor
public class ProductSearchService {

    private final ElasticsearchOperations es;

    public List<ProductDoc> search(String keyword, String category) {
        NativeQuery query = NativeQuery.builder()
                .withQuery(q -> q.bool(b -> {
                    b.must(m -> m.multiMatch(mm -> mm
                            .query(keyword)
                            .fields("title^2", "description")));   // title 权重更高
                    if (category != null) {
                        b.filter(f -> f.term(t -> t.field("category").value(category)));
                    }
                    return b;
                }))
                .withPageable(PageRequest.of(0, 10))
                .build();
        return es.search(query, ProductDoc.class).getSearchHits()
                .stream().map(SearchHit::getContent).toList();
    }
}

两个关键设计点：

① text 还是 keyword：text 分词存倒排（能搜），keyword 不分词整体存（能精确匹配、能聚合）。同一字段两种都要，就建两个字段（title + title.raw）。

② ES 不该做"真数据源"：ES 有近实时特性（写入到能搜到有 1 秒左右延迟 refresh_interval），而且没有事务、没有强一致。真数据在 MySQL，ES 只是索引——需要"写 DB + 写 ES"的一致性方案（见 5.6）。

3.4 对象存储：文件不进数据库 ​

核心心智：数据库存结构化、可查询的数据；对象存储存大文件、按 key 取的二进制。图片、PDF、Excel、用户头像、日志文件——都该进对象存储。

为什么不能塞进 MySQL：

问题后果
单行大小限制max_allowed_packet 默认 16MB，大文件直接存不进
备份成本备份一个 100GB 的库 = 备份所有文件
带宽下载文件走 DB 连接池，把业务请求挤死
访问方式DB 要按 SQL 查；对象存储是 HTTP + key，浏览器能直连

MinIO 接入（S3 兼容协议，代码和 AWS S3 几乎一样）：

java
@Service
@RequiredArgsConstructor
public class FileService {

    private final MinioClient minioClient;      // bean 见下

    private static final String BUCKET = "mall";

    // 1. 预签名：后端只签 URL，客户端直传文件（不经过你的服务器）
    public String presignUpload(String objectName) {
        try {
            MinioPresignedPostFormData form = minioClient.getPresignedPostFormData(
                    null, BUCKET, objectName, 10, TimeUnit.MINUTES);
            return form.url();     // 客户端直接 POST 到这个地址上传
        } catch (Exception e) {
            throw new ServiceException("生成上传地址失败", e);
        }
    }

    // 2. 下载：返回一个 302 或带签名的直链
    public String presignDownload(String objectName) {
        try {
            return minioClient.getPresignedObjectUrl(GetPresignedObjectUrlArgs.builder()
                    .method(Method.GET)
                    .bucket(BUCKET)
                    .object(objectName)
                    .expiry(10, TimeUnit.MINUTES)
                    .build());
        } catch (Exception e) {
            throw new ServiceException("生成下载地址失败", e);
        }
    }
}

⭐ 预签名直传是对象存储最大的价值：

text
❌ 文件流经你的服务器：客户端 → 你的服务 → MinIO → 你的服务 → 客户端
   （你的服务带宽和内存都被占用，还多一次转存）

✅ 预签名直传：客户端 → 你的服务（只要一个签名 URL，10KB 以内）
              → 客户端 → MinIO（文件直接进对象存储）

这就是前端上传图片的标准姿势——和你在 Node 服务里做 S3 直传是一回事。

3.5 Nacos：服务发现 + 配置中心 ​

核心心智：Nacos 干两件事，和 Spring Cloud 那篇 讲的是同一套：

text
注册中心：服务启动 → 报自己的 IP:端口 → 别人按【服务名】找到我
配置中心：配置放 Nacos → 服务启动拉取 → 改了能动态刷新（不用发版）

注册中心用法（客户端代码几乎没有成本）：

yaml
spring:
  application:
    name: order-service        # ← 别人靠这个名字找到你
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
java
// 别人调用你：用【服务名】，不用 IP
@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/api/users/{id}")
    UserDTO getUser(@PathVariable Long id);
}

配置中心用法：

yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        file-extension: yaml
        # 共享配置：所有服务都要的放这里
        shared-configs:
          - data-id: common.yaml
            refresh: true
        # 专属配置：只有本服务读的
        extension-configs:
          - data-id: order-service.yaml
            group: DEFAULT_GROUP
            refresh: true
java
@RefreshScope                    // ← 关键：让这个 Bean 的 @Value 能被刷新
@RestController
public class ConfigController {

    @Value("${feature.new-checkout:false}")
    private boolean newCheckout;
}

三个必知：

事项说明
@RefreshScope 必须加不加，@Value 读到的永远是启动时的值，改配置不生效
Nacos 挂了服务还能调吗能——调用方本地缓存了实例列表（这是 AP 设计），只是感知不到变更
配置推送是"准实时"长轮询机制，不是推模型，感知有秒级延迟

4. 原理：五个组件的核心机制 ​

难度：懂原理

每个组件只讲"够用来判断对错的那一层"，细节留给各自的专篇。

4.1 Redis：单线程 + 内存 + 过期策略 ​

text
命令 → 内存里的数据结构直接执行 → 返回
  • 单线程执行命令 → 原子性天然成立（不用加锁），但也意味着一个慢命令会卡住全部（KEYS * 能把服务拖死）
  • 内存 → 读写是纳秒级，比磁盘快几个数量级
  • 单线程 ≠ 单连接：Redis 6.0 起 IO 多线程（网络读写并行），命令执行仍是单线程

过期策略：惰性删除 + 定期删除

做法后果
惰性删除访问到过期 key 才删不访问就一直占内存
定期删除每隔一段时间抽样删过期 key有延迟

两者配合，所以过期 key 可能在内存里多待一会儿——你的缓存 TTL 是"逻辑过期"，不是"物理消失"。

为什么 Redis 快：内存 + 单线程无锁 + IO 多线程 + 惰性删除。代价是单点（主从/Cluster 另说，见 Redis 入门）。

4.2 MQ：三个角色 + 偏移量 ​

mermaid
flowchart LR
    P["生产者"] -->|"投递"| Q["队列 / 分区"]
    Q -->|"拉取"| C1["消费者组 A"]
    Q -->|"拉取"| C2["消费者组 B"]
    Q -.->|"记录消费位置"| O["offset"]
  • 生产 → 队列：消息被持久化到 broker（Kafka 是分区日志文件，RabbitMQ 是队列结构）
  • 队列 → 消费者：消费者主动拉取（pull），不是 broker 推
  • offset：消费位置。一个消费者组内，offset 由组内协调——同组多个实例是抢消息（一条消息只被组内一个实例处理），不同组各自消费一份（广播）

这套模型决定了两个常见行为：

现象原因
同组多个实例，消息只被一个处理组内抢消费 + offset 记录在 broker 侧
重启后从上次位置继续offset 持久化了
但重启会丢正在处理的那条offset 是提交后才记录，宕机时正在处理的消息会重投

最后一条就是"消息可能重复"的根源——所以消费端必须幂等。

4.3 ES：倒排索引 ​

text
正向索引（MySQL 的方式）：文档 ID → 内容
倒排索引（ES 的方式）：  词 → 包含它的文档 ID 列表

"手机壳"这个关键词被分词成"手机 / 壳"，倒排表里记着"手机"出现在哪些文档、"壳"出现在哪些文档——查的时候不需要扫全表。

代价是写入变贵：每次写入都要更新倒排表，所以 ES 不适合频繁更新，也不适合当唯一数据源。

近实时（near real-time）：写入后不是立刻可搜，而是每隔 refresh_interval（默认 1 秒）把内存段刷成可搜索的 Lucene 段。"写完立刻查不到"是正常行为，不是 bug。

4.4 对象存储：Key + 扁平命名空间 ​

text
PUT  /my-bucket/photos/2026/11/06/a.jpg   → 存进去
GET  /my-bucket/photos/2026/11/06/a.jpg   → 取出来
DELETE /my-bucket/photos/.../a.jpg        → 删掉

没有真正的目录——photos/2026/11/06/ 只是 key 里的字符串，按 / 分割出来的"伪目录"。这带来两个特性：

特性说明
大文件要分片单个 PUT 上传 5GB 会失败 → 用 multipart upload 分片上传再合并
预签名 = 授人以限时的权限URL 里带签名和过期时间，过期即失效；所以不要把预签名 URL 存进日志或返回给不可信方

一致性：对象存储通常是最终一致（PUT 完成后可能短暂读不到）。如果业务要求"上传完立刻能读"，要么读走缓存，要么选支持强一致的实现。

4.5 Nacos：注册发现的 AP 设计 ​

text
服务启动 → 向 Nacos 注册（IP:端口 + 心跳）
服务调用 → 问 Nacos 要实例列表 → 【本地缓存】→ 负载均衡挑一个
服务挂掉 → 心跳超时 → 从列表剔除

关键在"本地缓存"三个字：Nacos 挂了，服务之间仍然能互相调用（用缓存的列表），只是感知不到新增/下线。这是有意的 AP（可用性优先） 设计——注册中心挂了导致全站不可用，比短时间数据不一致严重得多。

配置推送同理：客户端拉取配置后本地缓存，Nacos 挂了继续用本地配置。

5. 边界与坑 ​

难度：会用 + 懂原理

5.1 一张表先过一遍 ​

症状见
改了数据库，接口还返回旧数据5.2
Redis 里的数据莫名没了 / 读到别人的数据5.3
消息被消费了两次，业务执行了两遍5.4
MQ 消息堆积、消费越来越慢5.5
ES 里的数据搜不到刚写进去的5.6
用了 MQ 但数据库和消息对不上5.7
文件上传后 404 / 被拒绝5.8
Nacos 里服务实例下线了还在被调用5.9

5.2 缓存和数据库不一致 ​

症状：改了数据库，接口还返回旧数据；或者反之，缓存里是脏数据。

原因：旁路模式下，"写 DB + 删缓存"不是原子的。两个线程交错就出问题：

text
线程 A                    线程 B
读缓存 → miss
查 DB → 读到旧值 x
                          改 DB → 新值 y
                          删缓存
写缓存 x  ← 慢了一步，把旧值写进去了

解法：

方案做法适用
延迟双删改 DB → 删缓存 → 延迟几百毫秒再删一次最常用，代价是延迟
缓存 TTL 兜底缓存设个不太长的 TTL（如 5 分钟），最坏情况过期后自然一致简单场景够用
先删缓存再改 DB改 DB 之前先删仍有并发窗口，但比"先改后删"窗口小
订阅 binlogCanal 监听 DB 变更 → 删缓存彻底，但要引入 Canal

更根本的做法：不要缓存"会变的派生数据"。缓存的是能容忍旧值的静态数据（商品详情、配置），而不是余额、库存这类强一致数据。

5.3 Redis 数据"莫名消失" ​

症状：缓存里的数据没了，或者读到了别人的数据。

原因：Redis 的内存是有限的，默认有 maxmemory 限制，淘汰策略默认 allkeys-lru——内存满的时候随便一个 key 都可能被删掉。

更隐蔽的是另一个库/另一个应用连了同一个 Redis：key 命名空间撞了。

解法：

yaml
spring:
  data:
    redis:
      host: localhost
      database: 3                # ← 用不同 database 隔离
java
// key 前缀带上业务和版本，避免撞车
private static final String KEY = "mall:product:detail:v2:";

生产上还要注意：Redis 不能只靠持久化兜底——RDB 是快照（可能丢最近几秒），AOF 是追加写（丢得更少但文件大）。Redis 里的数据必须是"丢了也能重建"的（缓存就是）。

5.4 消息重复消费 ​

症状：同一笔业务被执行了两次（加了两遍积分、扣了两遍款）。

原因：见 4.2——offset 是处理成功后才提交的。处理中宕机，消息会重投。

解法：消费端幂等，三条路：

方案说明
唯一索引（最常用）INSERT IGNORE / ON DUPLICATE KEY，靠 DB 拦重复
状态机只允许 待支付 → 已支付，重复执行时状态不匹配就跳过
去重表单独一张表记已处理的消息 ID

别用"Redis 记个 processed 标记"——Redis 可能丢数据，标记丢了就又重复了。幂等要落在 DB 上。

5.5 MQ 消息堆积 ​

症状：消费越来越慢，队列深度持续上涨。

原因（按常见度排）：

原因判断方法
消费能力不足单条消费耗时 × QPS < 消息产生速率 → 就是不够
某条消息处理卡住队列头部不动，后面的全堵着（RabbitMQ 的队头阻塞）
下游挂了消费端在等下游超时重试，速率降为 0
没开并发消费端是单线程串行的

解法：

yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 10          # 消费者并发数
        max-concurrency: 20
        prefetch: 20            # 每次最多取多少（太小会浪费，太大会压垮下游）

调 prefetch 是关键：太小 → 吞吐低；太大 → 单个消费者囤积太多消息，一旦它挂了重投就是灾难。经验值：让"一个消费者处理完 prefetch 条"的时间略小于心跳间隔。

根本解法是"快速消费 + 异步处理"：收到消息只做入库（快），真正的耗时逻辑丢回业务队列。

5.6 ES 搜不到刚写的数据 ​

症状：写入成功了，查询没结果。

原因：ES 是近实时的——数据在内存里，要等 refresh_interval（默认 1 秒）才变成可搜索状态。

解法：

场景做法
正常业务等 1 秒，别在写完立刻查
测试/要求立即可见POST /product/_refresh 手动刷新
需要"写完立刻能查"这不是 ES 的强项 → 真数据放 MySQL，ES 只做检索

另一个原因：分词不一致。写入时用 ik_max_word（细粒度），查询时用 ik_smart（粗粒度），或者字段类型一个是 text 一个是 keyword → 搜不到。写入和查询必须用同一个分析器。

5.7 数据库和消息对不上 ​

症状：订单创建了，但积分没加；或者消息发出去了，订单却没创建。

原因：本地事务管不到 MQ。@Transactional 只保证 DB 事务，消息发送是另一条链路。

三种解法（按可靠性排序）：

方案做法代价
可靠消息最终一致（最常用）本地事务表：同一事务里写"业务表 + 消息表"，另一个线程扫消息表发 MQ要多一张表 + 定时任务
RocketMQ 事务消息半消息 → 本地事务提交 → broker 才投递依赖 MQ 特性
Seata AT全局事务，各节点自动提交/回滚侵入性大，性能损耗

95% 的业务用第一种就够了——"本地事务表"其实就是自己实现消息表 + 定时补偿。

5.8 文件上传失败 / 上传后访问不到 ​

症状：前端拿到上传地址但传不上去；或者传上去了但访问 403。

原因与对策：

症状原因解法
上传 403预签名过期（有效期太短）有效期调到 10 分钟；别复用同一个 URL 反复上传
上传 413文件超过限制检查 MinIO 的 fileSizeLimit 和网关的 max-file-size
访问 404bucket 不存在 / key 拼错启动时 bucketExists 检查，不存在就 makeBucket
跨域失败浏览器直传 MinIO 被 CORS 拦给 MinIO 配 MINIO_API_CORS_ALLOW_ORIGIN
文件能被猜到 URL 访问key 太简单（photo/1.jpg）key 加随机 UUID；敏感文件用私有桶 + 预签名访问

最危险的一条：别用 file.getOriginalFilename() 直接当 key——用户可以传 ../../etc/passwd 之类。key 应该自己生成（UUID + 扩展名）。

5.9 Nacos 实例下线了还在被调用 ​

症状：把服务实例从 Nacos 摘掉了，流量还往那儿打。

原因：

情况说明
正常下线没做客户端只感知心跳超时（默认几十秒），Nacos 手动摘除不会立即通知已缓存列表的客户端
调用方本地缓存没刷新客户端拉列表有间隔
服务没主动注销kill -9 时无法注销，只能等心跳超时

解法：

做法说明
优雅停机下线前调 Nacos 的注销接口 + 等一个心跳周期（配合 Spring Cloud 的 spring.cloud.nacos.discovery.shutdown.wait-time）
客户端主动剔除调用失败重试时换一个实例（Nacos 自带重试策略）
别手动摘除要下线就先停流量再停进程，顺序反了就会出现这个现象

K8s 场景另说：K8s 有自己的服务发现（Service + EndpointSlice），用 Nacos discovery 那套反而绕。
