Java（Spring Boot）高并发与高可用设计 ​

优先级：P1 — Java 后端的主流高并发框架是 Spring Boot（单体/微服务都能落）。核心认知：Java 是"原生支持并发编程"，但高并发是架构设计的结果——语言给能力，设计给容量。

一、Java 的并发模型（先看清地基） ​

传统 Spring Boot（Servlet 容器 Tomcat）模型：

一个请求 = 一个线程（Tomcat 线程池，默认 200）
  ├─ IO 阻塞时线程睡眠，OS 切换别的线程
  └─ 并发上限 ≈ 线程数（受内存/切换成本约束，通常几千到顶）

演进：JDK 21 虚拟线程（百万级轻量线程，每请求一虚拟线程）+ WebFlux（响应式，类似 Node 事件模型）——都在往"更省资源的高并发"走。

高并发的第一原则：瓶颈通常不在 Java 代码，而在 DB/连接池/外部依赖——先定位瓶颈在哪，再谈优化。

二、高并发设计（分层手段） ​

① 单机层：

手段做什么
线程池调优Tomcat 线程数、队列大小（别默认，按压测调）
连接池调优Druid/HikariCP 的 max-active（数据库连接才是真稀缺）
异步化非核心逻辑异步（MQ / @Async），别占请求线程
并发工具ConcurrentHashMap、线程池、锁用得对

② 架构层（高并发的真正主力）：

Redis 缓存    → 扛热点读（挡住 90% 重复查询打 DB）
MQ 削峰       → 突发流量先入队，消费者匀速处理（下单/秒杀）
水平扩展      → 多实例 + 负载均衡（加机器=加并发，这是最优解）
数据层        → 读写分离（主写从读）、分库分表（单库瓶颈才上）
限流          → Sentinel/Guava 令牌桶，超阈值直接拒绝（保护系统）

三、高可用设计（不挂/挂了能救） ​

手段做什么对应 mall/12306
集群 + 负载均衡多实例 + LB + 健康检查多台 mall-admin 前面挂 nginx
无状态化登录态/会话外置（Redis/JWT）mall 的 JWT 无状态天然可扩
熔断降级依赖挂了走兜底（Sentinel/Resilience4j）缓存失败降级查库（mall 的 @CacheException）
限流超阈值拒绝，保护自己秒杀场景必备
幂等重复请求不重复扣款/下单订单防重
分布式锁并发抢资源（库存扣减）12306 锁库存
监控Actuator/日志（ELK）/指标（Prometheus）先能看见，才能救

四、演进路径（从小到大的容量路线） ​

单体单机（mall） → 单机多实例 + nginx（加机器）
  → Redis 缓存扛读 + MQ 削峰
  → 读写分离 / 分库分表（DB 瓶颈）
  → 微服务拆分（12306，按业务域拆 + 独立扩容）

每一步解决一个瓶颈，别一开始就上微服务——先加缓存/加机器，便宜且快。

五、实践清单 ​

清单项为什么
先定位瓶颈代码/DB/连接池？优化错地方白干
缓存扛热点读多写少先上 Redis
MQ 削峰突发写用队列匀速消化
加机器 > 调代码水平扩展是最优解，代码优化是瓶颈期才做
连接池不是越大越好连接数是 DB 上限，超了排队更糟
无状态化前置不然扩不了实例
限流/熔断/降级高可用的三件套，出事能活
监控先上线容量规划靠数据，不是拍脑袋

一句话 ​

Java 高并发的正确姿势：先承认"语言不是瓶颈，架构才是"——单机靠线程池/异步压榨，真正容量来自 Redis 扛读 + MQ 削峰 + 多实例水平扩展 + 数据层拆分；高可用靠集群 + 无状态 + 限流熔断降级 + 监控。演进路径"单体 → 加缓存/加机器 → 分库 → 微服务"，一步解决一个瓶颈。
