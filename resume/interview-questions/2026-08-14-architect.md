# 架构师思维练习 - 2026.08.14

> 练习"做架构决策"而不是背知识点。按难度分四层：L1 判断权衡 → L2 边界与契约 → L3 演进与综合 → L4 压力追问。
> 每题先**独立作答**（口头讲出来或写下来），再看参考答案要点自评。
>
> **自评标准**：你的回答里出现以下"架构语言"越多，得分越高——
> 约束（什么条件下）、边界（谁管什么）、契约（接口固化）、权衡（代价是什么）、可逆性（错了能不能换）、机制（怎么落地而不是靠自觉）。

## L1 判断权衡（练"权衡账"：每个选择都要说清代价）

### 1.1 微前端 vs 巨石应用

**场景**：公司要整合 5 条客服业务线（工作台、IM、知识库、质检、后台）为统一平台。业务线各自有独立团队、独立发布节奏，部分存量系统不能推翻重来。

**问题**：你作为架构负责人，选"巨石应用"还是"微前端"？请说出你的决策和**放弃的那个方案的代价**。

**考察点**：选型不是报答案，是把约束摆出来，再说明"为什么这个约束下损失最小"。

<details>
<summary>参考答案要点</summary>

- 决策依据三句话：① 多团队并行 → 需要独立部署；② 存量系统 → 需要渐进改造；③ 业务线隔离 → 需要边界。
- 放弃巨石：代价是"多团队一个仓库互相踩、发布互相阻塞、回归爆炸"——在 5 条业务线规模下不可接受。
- 放弃 iframe：代价是"体验割裂、通信弱、刷新丢状态"——客服工作台高频操作场景体验是核心指标。
- 一句话收尾：**微前端不是最优架构，是"多团队独立交付"这个约束下的损失最小解**。
</details>

### 1.2 自研组件库 vs 开源组件库

**场景**：金融 SaaS 平台要做视觉规范统一，业务涉及表单、表格、文档模板等强业务组件。

**问题**：基础组件层（Button、Input 之类）用 Antd，还是自研？业务组件层（信贷表单、模板渲染）呢？各自怎么选、理由是什么？

**考察点**：组件库分层思维——基础层和业务层的决策依据完全不同。

<details>
<summary>参考答案要点</summary>

- 基础层：用开源（Antd）。理由：生态、无障碍、维护成本——**自研基础组件的代价（长期维护）远大于收益（定制感）**，除非视觉规范与开源差异极大。
- 业务层：自研。理由：业务组件承载业务契约（数据模型、交互规则），开源没有；且跨项目复用价值高。
- 关键边界：**自研业务组件依赖开源基础组件，反向禁止**——基础层升级不影响业务层契约。
</details>

### 1.3 状态管理选型

**场景**：SaaS 表单系统，状态分三类：表单局部状态（用户正在填的内容）、跨页面全局状态（登录用户、权限）、服务端数据（贷款列表、模板列表，带缓存需求）。

**问题**：三类状态分别用什么方案管理？选型依据是什么？

**考察点**：不迷信某个库，按状态特征分类决策。

<details>
<summary>参考答案要点</summary>

- 表单局部状态：组件内 state / 表单库内部管理——**谁用谁管**。
- 全局状态：轻量集中（Zustand/Redux 看团队），只放"身份类"信息。
- 服务端数据：请求层缓存（React Query/SWR）——**服务端状态不该进全局 store**，它是"远端数据的本地缓存"，有自己的生命周期（失效、重试、乐观更新）。
- 常见错误：把服务端数据全部塞进全局 store，缓存逻辑、失效策略全得手写。
</details>

## L2 边界与契约（练"这个逻辑放哪"和"怎么固化边界"）

### 2.1 双层架构划边界

**场景**：一个信贷资料补充功能：后端返回表单 schema（字段、规则、值），前端要渲染表单、校验、提交；同套 schema 还用于"编辑态"和"只读展示态"。

**问题**：数据构建层和 UI 展示层各自管什么？画一下职责清单。什么情况下这个边界是"过度设计"？

**考察点**：边界判断 + 不过度设计的自知力。

<details>
<summary>参考答案要点</summary>

- 数据层：schema 解析、默认值、校验逻辑（纯函数，无 DOM）、提交数据的组装。
- 展示层：表单控件渲染、布局、交互反馈。
- 边界收益：编辑态和展示态复用同一数据层 → 校验逻辑只写一份。
- 过度设计的判定：如果这个功能只有一种形态、schema 永远不会变，双层就是过度设计——**边界跟着"变化频率差异"走，不跟着理论走**。
</details>

### 2.2 模板编辑器与生产渲染的契约

**场景**：模板编辑器产出文档模板，生产环境要按同一模板渲染出正式信件（邮件/PDF）。业务人员要求"编辑器里预览的 = 最终发出去的"。

**问题**：怎么设计这条全链路，保证"所见即所得"？契约应该定义在哪？

**考察点**：契约先于实现——把"一致"变成机制而不是承诺。

<details>
<summary>参考答案要点</summary>

- 核心决策：**编辑器和生产共用同一渲染内核**——预览渲染和生产渲染是同一个函数，这是"所见即所得"唯一可靠的实现方式。
- 契约定义：模板数据结构（DocNode/schema）是双端契约，版本化演进；渲染内核是共享资产。
- 反面：编辑器用一套渲染、生产又写一套 → 再努力对齐也必然出现偏差，问题出在架构上不是实现上。
</details>

### 2.3 多子应用统一权限

**场景**：微前端平台，5+ 子应用，每个子应用有自己的页面权限需求。平台要求：登录一次，所有子应用可用（SSO），权限统一管理。

**问题**：身份认证和授权分别放哪层？子应用要查"用户有没有某按钮权限"，怎么设计这个契约？

**考察点**：身份（你是谁）和授权（你能干嘛）分离的边界思维。

<details>
<summary>参考答案要点</summary>

- 身份认证：基座统一（登录、SSO、token 刷新），子应用不碰。
- 授权模型：基座提供"权限数据 + 查询能力"（当前用户、角色、权限点），**判定逻辑**（能不能点这个按钮）放子应用——基座管数据，业务管判定。
- 契约：子应用通过统一 API 查权限（而非自己存一份权限副本），权限变更靠刷新/推送生效。
- 常见错误：每个子应用各自维护登录和权限 → 改一次密码要登 5 次，权限加一个人要改 5 处。
</details>

## L3 演进与综合（练"渐进式改造"和完整决策）

### 3.1 技术栈渐进迁移

**场景**：存量系统 JS + Vue + 自研组件库，业务还要持续上新功能。你决定迁到 TS + React + 新组件库。

**问题**：设计迁移路线：新老共存期间架构上怎么保证不烂？列出至少 3 个机制性的决策（不是"大家注意点"）。

**考察点**：把不可逆的大改造拆成可逆小步骤的能力。

<details>
<summary>参考答案要点</summary>

- 新模块新栈、老模块按需迁（不搞大爆炸），边界上靠路由层隔离。
- 公共能力（请求、权限、埋点）先抽成框架无关层，双栈共用——**让两边都依赖"中间件"而不是互相依赖**。
- 组件库分层：基础组件优先统一（双栈都能用），业务组件按模块灰度迁移。
- 类型先行：数据模型/接口类型先 TS 化（纯数据层可独立迁移，风险最低）。
- 收尾标准：老栈代码占比降到阈值（如 <20%）再冻结；迁移期间埋点/监控双栈都接，灰度看指标。
</details>

### 3.2 AI 工作流门禁设计

**场景**：团队用 AI 辅助开发，发现 Agent 经常"跳步骤"：不测试就宣布完成、方案没评审就动手、编造测试通过。

**问题**：你是架构师，设计一套机制（不是提示词），让"假完成"无法通关。至少给出 3 层机制并说明各自的强度与成本。

**考察点**：把"不可靠的智能体"用确定性机制约束——软约束到硬约束的递进思维。

<details>
<summary>参考答案要点</summary>

- L0 提示词约束（软）：流程要求写进系统提示词——成本为零，但 Agent 会绕过，强度最弱。
- L1 结构化工作流（中）：YAML 定义阶段输入输出，产出物模板化（测试报告必须含"声明用例数/实际运行数"）——靠模板和阶段校验。
- L2 工具 + Hook 门禁（硬）：验证命令必须通过工具执行，结果落盘为证据；阶段产出校验不达标则阻塞（exit 2 拦截）——**证据链只能由工具产生，LLM 无法伪造**。
- 关键认知：**不能阻止 LLM 说谎，但可以让谎言无法通关**——说谎的代价是阶段永远过不去。
- 强度与成本成正比：L2 最强但要做工具和 hook，按问题频率选择层数。
</details>

### 3.3 微前端方案评审（逆向练习）

**场景**：新同事提交了一份微前端接入方案，你来做评审。方案要点：① 用 iframe 嵌入所有子应用；② 子应用间通信通过 window.postMessage 自由传递；③ 每个子应用独立打包 React（版本可能不同）；④ 基座通过定时器轮询 iframe 高度适配布局；⑤ 公共组件通过 npm 包发布，子应用各自安装任意版本。

**问题**：找出至少 5 个问题，按严重程度排序，并说明各属什么架构维度（边界/契约/性能/体验/演进）。

**考察点**：评审别人的架构——发现问题 + 排序优先级 + 归因维度。

<details>
<summary>参考答案要点</summary>

1. iframe 嵌入（体验）：割裂感、刷新丢状态、键盘/焦点问题——客服工作台场景是体验核心，最严重。
2. postMessage 自由传递（契约缺失）：没有消息协议定义，变成"蜘蛛网通信"，无法审计——定义统一消息协议 + 白名单。
3. 各自打包 React 版本不一（性能+包体积）：沙箱/多实例重复加载，内存翻倍——公共依赖 external + 版本锁定。
4. 轮询高度适配（性能）：高频轮询损耗 + 抖动——用 ResizeObserver 等事件驱动。
5. 组件库任意版本（演进）：版本碎片化，升级必然炸——semver + 升级策略（先灰度非核心）。
6. 排序逻辑：先"不可逆/伤体验"的（1、3），再"可治理"的（2、5），最后"性能细节"（4）。
</details>

## L4 压力追问（练"把决策讲成权衡账"）

### 4.1 连续追问模拟

**场景**：你刚讲完"客服平台用了微前端"，面试官开始连环追问：

1. 为什么不用 iframe？iframe 不是更简单吗？
2. 你们 5 个子应用，其实巨石应用也能管吧？
3. 微前端踩过最大的坑是什么？
4. 现在回头看，如果重新选，你还选微前端吗？

**问题**：模拟作答，注意每道追问都要有"承认代价 + 约束依据 + 当时信息"的结构。

**考察点**：不狡辩、不甩锅，承认代价但不推翻决策——这是架构师可信度的关键。

<details>
<summary>参考答案要点</summary>

1. iframe：承认"接入最简单"，但代价是体验割裂（无过渡、刷新丢状态）和通信弱——工作台高频操作场景扛不住；Qiankun 在"整合体验 vs 隔离"更平衡。
2. 巨石：如果只有 5 个人一个团队，巨石更划算，我承认；但约束是 5 条业务线独立团队独立发布，巨石意味着每次发布全员回归。
3. 坑：公共依赖治理（React 多实例内存翻倍）、跨子应用联调环境、老代码绕沙箱——讲具体 + 讲对策。
4. 重新选：还是会选微前端，但会**更早把接入契约做成脚手架**——早期人肉对齐的代价比预期大；顺便说"如果约束变了（团队合并、发布统一），撤掉微前端也是合理决策"——**架构决策跟着约束走，不恋战**。
</details>

## 练习方法建议

1. **每道题先口述**（对着手机录音），再对照要点——口头表达会暴露逻辑缺口
2. **给每个回答标注"架构语言"命中数**：约束/边界/契约/权衡/代价/可逆/机制，少于 3 个说明在报答案不是在讲决策
3. L1-L2 打基础，L3-3.3（评审题）最接近真实架构师日常，L4 用于面试前模拟
4. 做完后可以对照 [什么是架构师](/engineering/architect) 文章的框架检查自己是否漏了维度
