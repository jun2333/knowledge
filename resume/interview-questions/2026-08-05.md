### 1.2 闭包与内存

> 你在简历中提到"深入理解闭包"。请回答：
> 1. 闭包的本质是什么？用一句话概括。
> 2. 闭包在什么场景下会导致内存泄漏？在浏览器和 Node.js 中表现是否一致？
> 3. 你在实际项目中用过闭包的哪些场景？

**你的回答：**
1、函数内变量被其返回的函数引用，即使外层函数执行完毕也不会回收变量所占内存
2、在大量使用闭包但又没有及时清理下会导致内存泄漏，我不知道是不是表现一致，应该是不一致的吧
3、封装模块比如发布订阅模式的事件管理模块、异步api、回调函数等

**评分：6/10**

**参考答案：**
1. **闭包的本质**：函数 + 其引用的词法环境（lexical environment）的组合体。即使外部函数已返回，内部函数仍能访问外部函数的变量。一句话：**函数记住了它被创建时的作用域**。

2. **内存泄漏场景**：
   - 闭包持有大对象的引用，且闭包生命周期很长（如全局事件监听、定时器回调）
   - DOM 元素被闭包引用，即使 DOM 已从页面移除，GC 也无法回收
   - **浏览器 vs Node.js**：表现基本一致，闭包本身不会导致泄漏，关键在于是否被正确释放。但 Node.js 进程长期运行，如果闭包持有大量数据不释放，影响更明显。V8 的 GC 能回收不再被引用的闭包变量，但如果引用链一直存在就无法回收。

3. **实际应用场景**：
   - 模块模式（IIFE + 闭包实现私有变量）
   - 函数柯里化 / 偏函数
   - 防抖节流
   - React Hooks 底层就是闭包
   - 回调函数中访问外部变量

**不足**：第 2 题对浏览器和 Node.js 的差异没有给出明确判断，实际上机制是一致的，关键在于引用是否释放。第 3 题举例偏泛，可以更具体。

### 1.4 原型链与继承

> ES6 的 `class extends` 和 ES5 的寄生组合式继承，在底层机制上有什么本质区别？`super()` 到底做了什么？请从 `[[Prototype]]` 链的角度说明。

**你的回答：**
表现上的区别是es6是编译阶段实现的继承，而es6依赖运行；super执行实际上是利用call等函数在子类的作用域下执行了父类的构造函数；二者实质上都是基于原型的方式实现的继承

**评分：4/10**

**参考答案：**

**本质区别在于原型链的建立方式不同：**

**ES5 寄生组合式继承：**
```js
function Parent(name) { this.name = name; }
function Child(name) {
  Parent.call(this, name); // 借用构造函数继承实例属性
}
Child.prototype = Object.create(Parent.prototype); // 原型链继承
Child.prototype.constructor = Child;
```
- 实例的 `[[Prototype]]` → `Child.prototype`，`Child.prototype` 的 `[[Prototype]]` → `Parent.prototype`
- 通过 `Object.create` 手动建立原型链

**ES6 class extends：**
```js
class Child extends Parent {
  constructor(name) { super(name); }
}
```
- `super()` 做了两件事：
  1. 创建 `this` 对象（注意：ES6 中子类不先创建 `this`，而是由 `super()` 创建）
  2. 调用父类构造函数初始化 `this`
- **关键区别**：ES6 还建立了**构造函数的原型链**：`Child.__proto__ === Parent`（即 `Child.[[Prototype]] → Parent`），这意味着子类可以继承父类的静态方法。ES5 需要手动设置 `Child.__proto__ = Parent`

**不足**：
- "ES6 编译阶段实现" 不准确，ES6 class 也是运行时行为
- 没有提到 `super()` 的核心作用：在 ES6 中由 super() 创建 this（而非子类先创建）
- 没有提到构造函数原型链（`Child.__proto__ === Parent`）这个关键区别
- "都是基于原型" 是对的，但没有说清楚原型链建立方式的差异

**评分：5/10**

**参考答案：**
```js
Promise.allSettled = function(promises) {
  return new Promise((resolve) => {
    const iterable = Array.from(promises);
    if (iterable.length === 0) { // 边界情况
      resolve([]);
      return;
    }
    const results = [];
    let count = 0; // 用计数器来计算是否所有promise都完事了
    iterable.forEach((p, i) => {
      Promise.resolve(p).then(
        (value) => {
          results[i] = { status: 'fulfilled', value };
        },
        (reason) => {
          results[i] = { status: 'rejected', reason };
        }
      ).finally(() => {
        if (++count === iterable.length) resolve(results); // 关键代码
      });
    });
  });
};
```

**你的代码存在的问题：**
1. **不需要继承 Promise**，`allSettled` 是 Promise 的静态方法，不需要 `class MyPromise extends Promise`
2. `promises[i]()` 错误——传入的是 Promise 对象而非函数，应直接 `await promises[i]`
3. `status: 'fuilled'` 拼写错误，应为 `'fulfilled'`
4. rejected 时应该用 `reason` 字段而非 `value`
5. 用 `for...await` 串行执行，所有 Promise 是顺序执行的，失去了并发的意义。应该用 `Promise.resolve(p).then()` 并行注册
6. 没有处理空数组边界情况

### 1.8 手写：带并发限制的异步调度器

>
> ```ts

> scheduler.addTask(() => fetch('/api/a'));
> scheduler.addTask(() => fetch('/api/b'));
> scheduler.addTask(() => fetch('/api/c'));
> // 当某个任务完成时，自动启动队列中的下一个
> ```

**你的回答：**

```ts
// 在此作答
class Scheduler {
  maxLane:number
  retryNum:number = 3
  taskQueue:array<()=>Primise>
  construction(maxLane:number){
    this.maxLane = maxLane
  }
  addTask(task:()=>Primise){
    this.taskQueue.push(task)
  }
  run(){
    let lane = 0
    while(this.taskQueue.length > 0 && lane <= this.maxLane){
      const curTask = this.taskQueue.unshift()
      lane++
      let restRetryNum = this.retryNum
      function excuteOneTask(t){
        t().then(res=>{
          lane--
          this.run()
          return res
        }).catch(err=>{
          if(restRetryNum>0){
            excuteOneTask(t)
            restRetryNum--
          }else{ // 重试过了还是失败，抛出去
            lane--
            this.run()
            throw err
          }
        })
      }
      excuteOneTask(curTask)
    }
  }
}
```

**评分：4/10**

**思路方向正确**：有并发控制、队列、重试的概念。但代码有多处问题。

**参考答案：**
```ts
class Scheduler {
  private maxConcurrent: number;
  private running = 0;
  private queue: Array<() => Promise<any>> = [];

  constructor(maxConcurrent: number) {
    this.maxConcurrent = maxConcurrent;
  }

  addTask(task: () => Promise<any>) {
    this.queue.push(task);
    this.run();
  }

  private run() {
    while (this.running < this.maxConcurrent && this.queue.length > 0) {
      const task = this.queue.shift()!;
      this.running++;
      task()
        .finally(() => {
          this.running--;
          this.run(); // 任务完成（无论成功失败）后启动下一个
        });
    }
  }
}
```

**扩展：如果题目确实要求重试，怎么加才正确？**

核心原则：**重试逻辑独立封装，不污染调度核心；重试耗尽后错误必须传播出去**。

```ts
class Scheduler {
  private maxConcurrent: number;
  private running = 0;
  private queue: Array<() => Promise<any>> = [];
  private retryCount = 3;
  private retryDelay = 1000; // 基础退避间隔 ms

  constructor(maxConcurrent: number) {
    this.maxConcurrent = maxConcurrent;
  }

  addTask(task: () => Promise<any>) {
    this.queue.push(task);
    this.run();
  }

  private run() {
    while (this.running < this.maxConcurrent && this.queue.length > 0) {
      const task = this.queue.shift()!;
      this.running++;
      this.executeWithRetry(task)
        .catch((err) => {
          // 重试耗尽：错误在这里统一处理（上报/记录），或抛给调用方
          console.error('[Scheduler] task failed after retries:', err);
        })
        .finally(() => {
          this.running--;
          this.run(); // 无论成功、失败、重试耗尽，最终都释放 lane 并调度下一个
        });
    }
  }

  // 重试只负责"让任务最终 settle"：成功返回结果，重试耗尽抛错
  private async executeWithRetry(task: () => Promise<any>, attempt = 1): Promise<any> {
    try {
      return await task();
    } catch (err) {
      if (attempt >= this.retryCount) throw err; // 重试耗尽，向上抛
      await sleep(this.retryDelay * attempt);    // 线性退避（可用指数：delay * 2^attempt + 随机抖动）
      return this.executeWithRetry(task, attempt + 1);
    }
  }
}

function sleep(ms: number) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}
```

**与你重试版本的关键差异：**

| 问题 | 你的写法 | 正确写法 |
|---|---|---|
| 失败传播 | `throw err` 抛进无人接收的 Promise 链 → unhandled rejection，错误静默丢失 | 重试耗尽后抛给调用方，调度器统一 `catch` 处理 |
| 退避策略 | 失败立即重试（重试风暴，故障时 4 连发打挂接口） | `sleep` 线性/指数退避 + 抖动 |
| lane 管理 | 重试期间不释放 lane 也不调 `run()`，调度器整体停摆 | 重试期间 lane 保持占用（任务确实未完成），`finally` 保证最终释放 |
| 职责边界 | 调度、重试、错误处理揉在一个函数里 | 调度（run）与重试（executeWithRetry）分离，各管一件事 |
| 递归时机 | 先递归后递减，依赖闭包变量时序 | 递归与计数由 `attempt` 参数显式传递，无隐式顺序 |

注意重试期间的 lane 语义：重试时任务还没完成，**占用并发位是合理的**——真正的 bug 是你之前的版本在重试期间既没释放 lane 也没触发调度，且错误无处可去。

**你的代码存在的问题：**
1. `construction` 应为 `constructor`（拼写错误出现多次）
2. `taskQueue: array<()=>Primise>` — TypeScript 中应为 `Array<...>` 或 `...[]`，`Primise` 拼写错误
3. `this.taskQueue.unshift()` — `unshift` 是往头部添加元素，取出应该用 `shift()`
4. `lane` 是局部变量，在 while 循环中每次 run() 调用都重置为 0，无法追踪正在运行的任务数。应该用实例属性
5. `this.run()` 在 `.then`/`.catch` 回调中调用时，`this` 指向丢失（需要箭头函数或 bind）
6. 重试逻辑是题目没要求的，增加了复杂度但引入了更多 bug

**进阶扩展：完整版（cleanup + options + 变形 API）**

简化版只覆盖"收集 + 触发"。完整版还需要三样东西：**cleanup**（依赖精确性）、**scheduler/lazy**（执行时机控制）、以及基于 effect 的变形 API。核心：

```js
const bucket = new WeakMap();
let activeEffect;
const effectStack = [];

function track(target, key) {
  if (!activeEffect) return;
  let depsMap = bucket.get(target);
  if (!depsMap) bucket.set(target, (depsMap = new Map()));
  let deps = depsMap.get(key);
  if (!deps) depsMap.set(key, (deps = new Set()));
  deps.add(activeEffect);
  activeEffect.deps.push(deps);      // 反向记录 → 供 cleanup 退订
}

function trigger(target, key) {
  const depsMap = bucket.get(target);
  if (!depsMap) return;
  const effects = depsMap.get(key);
  const effectsToRun = new Set();
  effects && effects.forEach(fn => {
    if (fn !== activeEffect) effectsToRun.add(fn); // 防自触发死循环
  });
  effectsToRun.forEach(fn => {
    if (fn.options.scheduler) fn.options.scheduler(fn); // 有调度器 → 交给调度器决定何时执行
    else fn();                                          // 无调度器 → 立即执行
  });
}

function cleanup(fn) {
  fn.deps.forEach(dep => dep.delete(fn));
  fn.deps.length = 0;
}

function effect(fn, options = {}) {
  const effectFn = () => {
    cleanup(effectFn);          // 1. 清旧依赖（分支切换正确性）
    effectStack.push(effectFn);
    activeEffect = effectFn;
    const res = fn();           // 2. 执行，track 重新收集
    effectStack.pop();
    activeEffect = effectStack[effectStack.length - 1];
    return res;
  };
  effectFn.deps = [];
  effectFn.options = options;
  if (!options.lazy) effectFn();  // lazy：不立即执行，把执行权交给调用方
  return effectFn;
}
```

基于此实现三个变形 API：

```js
// computed：lazy + dirty 缓存 + scheduler 只标记不重算
function computed(getter) {
  let value;
  let dirty = true;
  const runner = effect(getter, {
    lazy: true,
    scheduler() {                 // 依赖变化时不立即重算（可能没被读）
      dirty = true;
      trigger(obj, 'value');      // 通知"依赖了该 computed"的外层 effect
    }
  });
  const obj = {
    get value() {
      if (dirty) {
        value = runner();         // 被读取时才重算（懒计算）
        dirty = false;
      }
      track(obj, 'value');        // computed 本身也是可被依赖的节点
      return value;
    }
  };
  return obj;
}

// watch：lazy + 手动新旧值比较 + scheduler 控制回调时机
function watch(source, cb, options = {}) {
  const getter = typeof source === 'function' ? source : () => source.value;
  let oldValue;
  const runner = effect(getter, {
    lazy: true,
    scheduler() {                 // 变化时由 flush 决定回调时机
      if (options.flush === 'post') Promise.resolve().then(job);
      else job();
    }
  });
  function job() {
    const newValue = runner();
    if (newValue !== oldValue) {
      cb(newValue, oldValue);
      oldValue = newValue;
    }
  }
  if (options.immediate) job();
  else oldValue = runner();       // 先取一次旧值，不触发回调
}

// watchEffect：effect 的薄封装（post flush 用微任务模拟 nextTick）
function watchEffect(fn) {
  const runner = effect(fn, {
    scheduler() { Promise.resolve().then(runner); }
  });
  return runner;
}
```

**四个 API 的关系**：

| API | 实现要点 | 与 effect 的关系 |
|---|---|---|
| `effect` | 立即执行 + 自动收集 | 地基 |
| `watchEffect` | effect + scheduler 推迟执行（post flush） | 薄封装 |
| `computed` | lazy + dirty 缓存 + scheduler 只标记 | effect + 缓存层 |
| `watch` | lazy 包 getter + 手动取新旧值 + scheduler 控制回调 | effect + 命令式拉取 |

**关键理解**：
1. **scheduler 的本质**：把"依赖变化 → 立即执行"改为"依赖变化 → 通知我，我自己决定何时/是否执行"。computed 靠它实现"变了但不重算"，watch 靠它实现"变了但不自动跑，由 job 控制"
2. **computed 的链式依赖**：内层 effect 收集 getter 的依赖，外层 effect 收集 computed 节点本身。改原始数据时：trigger 原始 key → 内层 scheduler 标记 dirty → trigger computed → 外层 effect 执行 → 读 value 发现 dirty 才重算
3. **watch 是命令式拉取**：变化通知里不含新值，job 里手动 `runner()` 取新值再比较
4. **lazy 的意义**：computed 和 watch 都需要手动控制执行时机，"lazy"就是把执行权从"自动"交还给"调用方"

**进阶扩展二：竞态处理（onCleanup / onInvalidate）**

watch 的副作用常是异步请求，用户快速操作时旧请求可能后返回、覆盖新结果。Vue 用 `onCleanup` 标记过期副作用（搜索请求是经典场景）：

```js
watch(keyword, async (val, _, onCleanup) => {
  let expired = false;
  onCleanup(() => { expired = true; });   // 注册：下次回调触发前执行
  const res = await search(val);
  if (!expired) results.value = res;      // 已过期则丢弃
});
```

实现原理：watch 内部维护一个 `cleanup` 变量，job 每次执行时**先调用上一次注册的 cleanup，再跑回调**——第二次触发会把第一次标记为过期。注意它**不是取消请求**（请求还在飞，只是结果被丢弃），真取消要配合 `AbortController`。Vue 3.5 升级为 `onWatcherCleanup`，支持在回调外部注册（依赖全局 activeWatcher），组件卸载时自动清理。

**React 的对应方案**（对比记忆，面试常被追问）：

```jsx
useEffect(() => {
  let ignore = false;
  fetchData(id).then(res => {
    if (!ignore) setData(res);
  });
  return () => { ignore = true; };   // effect 重跑前/卸载时执行
}, [id]);
```

- **机制同源**：都是"下一次副作用执行前，先清理上一次"。区别只在写法：Vue 是参数注册（`onCleanup(fn)`），React 是返回值（`return () => ...`）
- **设计初衷不同**：Vue 的 onCleanup 为竞态而生；React 的 cleanup 初衷是资源清理（监听/定时器/订阅），竞态处理是借用"重跑前执行清理"的时机
- **React 官方更激进**：建议别用 useEffect 做数据请求，交给请求库（react-query/SWR 内置竞态处理）、AbortController 或框架层（RSC）

3. ❌ **缺失**。ProxySandbox 失效/局限的场景：

   - **全局事件监听残留**：`window.addEventListener` 注册的监听器若不在卸载钩子里手动清除，会残留并继续影响主应用

**Qiankun 如何应对这些场景**（对照源码）：

1. **裸赋值逃逸** → has trap 做了兜底：`has: (p) => p in cachedGlobalObjects || p in target || p in globalContext`——真实 window 上已有的属性在 `with(fakeWindow)` 中被判定"存在"，裸赋值会绑定到 fakeWindow 上走 set trap（被拦截）。**但全新属性（三处都没有）仍会逃逸**，这是 Proxy 沙箱的硬边界，官方对策是约定子应用开严格模式（裸赋值直接抛 ReferenceError）
2. **eval** → get trap 对 `eval` 特殊处理（accessingSpiedGlobals，每次访问都返回模块作用域内的 eval 引用）：子应用裸 `eval(code)` 是直接 eval，继承 with 环境，代码仍在沙箱内执行；但 `(0, eval)(code)` 间接 eval 在全局作用域执行仍可逃逸——Qiankun 没有封死，甚至白名单里专门给 System.js 的间接 eval 开了后门（`globalVariableWhiteList` 中的 `System`/`__cjsWrapper`），属于权衡后的妥协
3. **共享全局属性** → set trap 默认**不写真实 window**：只有极少数白名单属性（System 等）同步到真实 window，其余一律写实例级 fakeWindow（每个沙箱实例独立，卸载直接丢弃，无需恢复）；getter 属性（location/top 等）get trap 从真实 window 读取保证行为一致；卸载时 inactive() 仅恢复白名单属性的原 descriptor
4. **document** → get trap 接管 `document` 访问并返回 `this.document`（可通过 `patchDocument()` 替换为 iframe 的 document），但 document 内部修改（title、DOM 操作）无法代理，靠样式隔离 + 子应用卸载钩子自觉清理
5. **事件监听残留** → `patchAtMounting`/`patchAtBootstrapping` 在 mount 时劫持 window/document 的 `addEventListener`/`removeEventListener`（也 patch 定时器），记录子应用注册的监听器，unmount 时 freer 统一移除，无需子应用手动清理

### 4.3 子应用通信

> 你用了 `initGlobalState` + 自定义事件做通信。请回答：
> 1. `initGlobalState` 的 `onGlobalStateChange` 是深监听还是浅监听？修改嵌套对象的属性会触发回调吗？
> 2. 子应用间需要传递一个复杂对象（如用户权限树），你会怎么设计通信方案？
> 3. 如果两个子应用需要同时操作同一个全局状态，怎么处理竞态？

**你的回答：**



**评分：0/10** ❌ 未作答

**参考答案：**

1. **浅监听**。`onGlobalStateChange` 只在 `setGlobalState` 被调用时触发，且只对比第一层属性的变化。修改嵌套对象的属性（如 `state.user.name = 'xxx'`）不会触发回调。

2. **复杂对象通信方案**：
   - 小数据：用 `initGlobalState` 直接存储
   - 大数据/频繁更新：用 **CustomEvent + 发布订阅**，避免全局状态膨胀
   - 共享只读数据：用 `window.__SHARED_DATA__` 挂载，子应用直接读取

3. **竞态处理**：
   - 全局状态操作收敛到主应用，子应用通过 action 请求修改
   - 使用不可变数据（immutable），每次 `setGlobalState` 返回新对象
   - 乐观锁或版本号机制

**补充：initGlobalState 机制与通信方案选型**

**用法回顾**：

```js
// 主应用
import { initGlobalState } from 'qiankun';
const actions = initGlobalState({ userInfo: null, permissions: [] });
actions.onGlobalStateChange((state, prev) => {}, true);  // 订阅（true = 立即回调拿当前值）
actions.setGlobalState({ userInfo: {...} });             // 更新 + 同步广播

// 子应用（从 mount 的 props 里拿，不要自己 initGlobalState——会初始化一份新的空状态）
export async function mount(props) {
  const { onGlobalStateChange, setGlobalState } = props;
  onGlobalStateChange((state) => {}, true);
}
```

**核心机制**：
- `setGlobalState` 是**同步**的：浅合并（`{ ...state, ...newState }`）+ 同步广播所有订阅者，**无直接 get 接口**
- `onGlobalStateChange` 是**浅监听**：只有调用 `setGlobalState` 才触发回调；直接改嵌套属性（`state.user.name = 'x'`）不触发，必须整体替换嵌套对象
- 同步模型下读-写无竞态窗口（单线程原子执行）；**异步请求乱序覆盖是真竞态**，globalState 不管，需业务自保（请求序号/单一来源写入）

**优势**：可变状态跨应用同步广播；子应用写的是共享状态而非真实 window，卸载无污染；官方 API 简单
**劣势**：读取要绕订阅回调（无 get）；mount 之后才拿得到；每个子应用要写"接收 + 分发"样板；浅合并对嵌套对象是整体替换，多人改同一对象会互相覆盖

**三种场景通信方案对比**：

| 方案 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| `window.__SHARED_DATA__` | 只读配置（网关、版本号、特性开关） | 读取最便捷、任意时机可读、零样板 | 必须约定只读；要命名空间防冲突；不放敏感数据 |
| `initGlobalState` | 可变全局状态（登录态、权限），需跨应用同步 | 同步广播、写隔离、官方支持 | 读取绕、mount 后才有、样板多、浅合并粒度坑 |
| 自定义事件（EventBus/dispatchEvent） | 一次性消息/动作通知（刷新列表、跳转指令） | 解耦、事件即语义、可携带数据、不依赖生命周期 | 无状态不持久、订阅要管理退订、传对象是引用需防篡改 |

**选型口诀**：只读配置挂 window，可变状态走 globalState，一次性动作发事件；挂载时的初始化快照可以直接走 `registerMicroApps` 的 props。

  ```js
  window.addEventListener('error', (e) => {
  ```

**2. 子应用加载耗时监控（链路拆解）**

```
路由切换 → beforeLoad → JS/CSS 下载 → bootstrap → mount → 首帧可用
```

- 生命周期钩子打 PerformanceMark：`beforeLoad/afterLoad/beforeMount/afterMount`，`performance.measure` 算各段
- JS/CSS 下载：`performance.getEntriesByType('resource')` 按子应用 entry 前缀过滤，取 `duration`

- **Trace ID 生成**：主应用路由切换时 `crypto.randomUUID()`，存 sessionStorage，经 globalState/props 传给子应用
- **传递链**：前端 → 后端：所有请求头带 `X-Trace-ID`（axios 拦截器统一加）；前端 → 平台：上报数据带 traceId + spanId
- **串联点**：路由切换(span1) → 子应用加载(span2，含 download/bootstrap/mount 子 span) → 首屏接口(span3) → 错误(span4 挂到当前 span)
- 平台端按 traceId 聚合生成瀑布图，错误与对应链路关联

**4. 上报通道与采样（原答案缺失）**

- **批量**：SDK buffer 累计 N 条或 1s 定时 flush，减少请求数
- **卸载可靠送达**：`navigator.sendBeacon`，不支持时降级 img 1x1
- **采样**：性能类 10%（大流量成本控制），错误 100% 全量
- **去重**：同 app + 同 stack + 同行号在时间窗口内只报一次（错误刷屏会打爆上报通道）
- **告警**：子应用错误率环比突增、白屏检测（加载成功但容器无内容）、entry 拉取失败——三者即时告警

### 5.1 Vite vs Webpack

> 你两个都用过。请从以下维度对比：
> 1. 开发环境启动速度差异的根本原因
> 2. HMR 机制的区别
> 3. 生产构建时 Vite 为什么还要用 Rollup？
> 4. 在大型项目中 Vite 有什么已知的性能问题？

**你的回答：**



**评分：0/10** ❌ 未作答

**参考答案：**

1. **启动速度差异根本原因**：Webpack 先打包所有模块再启动（bundle-based），Vite 利用浏览器原生 ES Module 按需编译（native ESM），只编译当前页面用到的模块。

2. **HMR 区别**：两者机制骨架相同——都是**本地服务通过 WebSocket 推送变更通知 + 客户端重新拉取最新代码**（不是轮询）。差异在粒度：
   - **Webpack**：文件变更 → 重新编译**受影响的模块链**（依赖该模块的所有模块都进 outdated 链）→ 服务端推送更新包，客户端用 JSONP（`webpackHotUpdate`）拉取补丁 chunk，再按依赖关系**级联重新执行**链上模块；遇到不接受热更新的模块就向上冒泡，直到整页 reload。构建时间与项目规模相关。
   - **Vite**：文件变更 → 服务端只对**变更的那一个模块**做 transform（unbundle，其他模块不重编译）→ WebSocket 推送该模块的 URL + 版本号 → 浏览器重新 `import` 该模块（带 `?t=时间戳` 版本参数）→ 触发 `import.meta.hot` 回调。与项目规模无关。

3. **为什么用 Rollup**：Rollup 对 ESM 的 tree shaking 更彻底，产物更干净，适合 library 和 application 的生产构建。Vite 的开发服务器用的是 esbuild（极快但不适合生产构建）。

4. **大型项目的性能问题**（都有解）：
   - **冷启动慢**：dev server 启动时要预构建全部依赖（Rolldown 打包，Vite 8 起；此前 esbuild，大项目 10s+）。但预构建产物**磁盘缓存**在 `node_modules/.vite/deps`，只有 lockfile / 补丁目录 / 配置 / NODE_ENV 变化才重新构建，日常启动秒开；CI 可把缓存目录做制品共享，同事 clone 后直接命中
   - **请求瀑布**：不预构建的话，`import` 一个依赖会展开成几百个小文件请求（如 lodash-es 600+ 模块，浏览器同域并发 ~6）。`optimizeDeps` 预构建把 node_modules 合并成少量 ESM bundle，顺带解决 CJS 兼容问题
   - **optimizeDeps 配置经验**：`include` 加三类——动态 import / 插件转换产生的依赖（扫描发现不了，不加会运行时重构建 + 页面 reload）、大而 CJS 的依赖、monorepo 中非 ESM 的链接依赖；`exclude` 加小而纯 ESM 的依赖（让浏览器直接加载，省预构建时间）；链接依赖改动不生效时 `--force` 重启
   - **首屏模块树解析量大**：首次访问某路由要现场编译整棵模块树。解法：路由懒加载、`server.warmup.clientFiles` 预热高频模块（提前 transform 进内存缓存）
   - **生产构建慢**：Rollup 打包大项目慢。**Rolldown 1.0 已发布**（Rust 重写 Rollup，快 10-30 倍），Vite 8 已集成接替 Rollup
   - **dev 内存占用高**：模块图 + transform 缓存常驻，属于已知短板，一般机器可扛
   - 一句话权衡：Vite 是"**一次性付费**（冷启动预构建）+ 日常秒开"，webpack 是"每次改代码都随规模退化的持续成本"

### 6.2 长列表优化

> 你需要渲染一个 10 万行的数据表格。请设计你的方案：
> 1. 虚拟滚动的实现原理是什么？
> 2. 如果每行高度不固定，虚拟滚动怎么处理？

2. 预设估计高度，并根据实际渲染高度动态调整后面的
3. 上下保留缓冲区

**评分：6.5/10** 方向全对，但每问都只有结论没有机制，面试会被追问到

**批注：**
- 第 1 问缺核心细节：**总高度撑起滚动条**（用一个空白占位元素设置总高度）、**绝对定位/transform 位移**（可视区窗口随滚动移动）、**start/end index 动态计算**、**DOM 复用**（不是销毁重建而是更新内容）
- 第 2 问"动态调整后面的"——对，但可补充：已测量高度要**缓存**（避免重复测量）、定位用**二分查找**（累计高度数组）而不是线性扫描
- 第 3 问"上下保留缓冲区"——对，但没说清为什么有效：缓冲区的意义是**提前渲染**，让滚动时新行已经在 DOM 里，而不是滚动瞬间才创建（白屏是创建延迟造成的）；可叠加 rIC（空闲渲染）

**参考答案：**
1. **虚拟滚动原理**：只渲染可视区 + 缓冲区内的行。外层容器固定高度（overflow: auto），内部一个"总高占位"元素（height = 总行数 × 行高）撑出真实滚动条；可视区内容用绝对定位容器，滚动时计算 `start = floor(scrollTop / rowHeight)`、`end = start + 可视行数`，只渲染 [start-overscan, end+overscan] 的行；行内容更新走**复用**（key 对应行 index，滚动时只改内容不改 DOM 数量）
2. **动态高度**：先按**预估高度**（如 40px）排布 → 行渲染后**实测高度** → 存入高度缓存数组（每行的真实高度）→ 滚动定位用**前缀和 + 二分查找**（二分找 start 行）；未测量行用预估高度兜底
3. **白屏闪烁**：上下各加 overscan 缓冲区（如 5-10 行）提前渲染；滚动用 `requestAnimationFrame` 节流 + `content-visibility`；把渲染时机放在滚动帧而不是滚动事件回调里

### 6.3 流式渲染原理

> 你在 AI 聊天中用了 SSE + rAF 做流式渲染。请回答：
> 1. 为什么不直接用 `fetch` 的 `ReadableStream`？SSE 和 ReadableStream 有什么区别？
> 2. rAF 节流的具体实现是怎样的？如果 token 到达速率超过 60fps 怎么处理？
> 3. 如果用户快速滚动页面，流式渲染区域需要做什么特殊处理？

**你的回答：**
1. 我就是用fetch的ReadableStream啊，这不就是SSE吗？通过fetch一次连接，服务端流式返回内容中途不结束连接
2. 因为是通过直接操作DOM，使用innerHTML渲染内容，内部通过rafId的设置注册式调用requestAnimationFrame，所以用rAF既有节流又有防止闪烁的效果，如果超60fps也是按照屏幕显示器的渲染频率逐帧更新
3. 有啥需要处理的吗？除了长列表性能优化之外

**评分：7.5/10** 第 1 问的反问有道理（fetch 读流就是主流实践），但没讲清两者关系；第 3 问缺"视口外暂停渲染"

**批注：**
- 第 1 问：你的实践（fetch + ReadableStream）是对的，但面试官要的是**概念区分**：SSE 是"服务端推送协议"（`EventSource` API：自动重连、`Last-Event-ID` 断点续传、`event:` 事件类型）；`fetch` 的 `response.body` 是**通用流接口**，可以读任意流式响应（SSE、ndjson、纯文本）。fetch 方案的优点：能带自定义 Header（鉴权）、能 POST、能 AbortController 取消；缺点：没有自动重连（要自己实现）。所以"SSE 和 ReadableStream"不是二选一——**SSE 是协议，ReadableStream 是传输载体**，ChatGPT 等产品都是 fetch + ReadableStream 读 SSE 格式
- 第 2 问：rAF 注册式调用（保存 rafId，下一帧先 cancel 再重新注册）避免队列堆积——对；"超过 60fps 也按屏幕刷新率逐帧"——对，rAF 天然绑定显示刷新率（120Hz 屏就是 120 帧）
- 第 3 问：**有**！流式渲染区域在视口外时，持续高频改 DOM 会浪费渲染开销。处理：`IntersectionObserver` 检测流式区域是否在视口内——不在视口内**暂停 DOM 更新**（但继续消费流、累积文本），回到视口一次性渲染。你说"除了长列表之外"其实方向对了，但要明确是"离屏暂停渲染"

**参考答案：**
1. **SSE vs fetch ReadableStream**：SSE 是协议（EventSource 自动重连、事件类型、断点续传），ReadableStream 是流载体；fetch 读流更灵活（自定义 header/POST/取消），但需自己处理重连；EventSource 简单但有局限（只能 GET、不能自定义 header）。实践中 AI 聊天用 fetch + ReadableStream 是标准做法（需要 POST + 鉴权）
2. **rAF 节流**：注册式调用（`cancelAnimationFrame(rafId)` + 重新注册），保证一帧内最多一次 DOM 更新；token 速率再快也以帧率为上限，积压内容在下一帧合并渲染
3. **滚动/视口处理**：IntersectionObserver 监听流式区域——视口外暂停渲染（继续读流、攒文本），回视口后一次补渲染；避免滚动时频繁 DOM 变更造成卡顿

**参考答案：**
1. **preload vs prefetch**：preload = 当前页关键资源提前加载（高优先级，必须配合 `as` 属性），用于 LCP 图片、字体、首屏脚本；prefetch = 未来页面资源空闲时预取（低优先级），用于路由懒加载的下一跳预取。区别核心：**时间点（当前 vs 未来）+ 优先级（高 vs 低）**
2. **defer vs async**：defer = 下载并行、执行延后到解析完、按顺序；async = 下载并行、下载完立即执行、不保证顺序、可能阻塞解析。场景：defer 用于依赖顺序的脚本；async 用于独立无依赖的脚本（埋点、统计）
3. **Server Push vs 103 Early Hints**：Server Push 是服务器"自作主张"推资源（已废弃——无法感知浏览器缓存、推送不可取消）；103 Early Hints 是服务器"提示"浏览器（`Link: rel=preload`），由浏览器自己发起请求（尊重缓存、可取消）。**103 是 Server Push 的现代替代**，推荐回答里点出"Server Push 已废弃"是加分项
4. **决定哪些资源 preload**：LCP 元素对应的资源（图片/字体/首屏 CSS）、渲染阻塞的关键资源；一般原则：**能不发 preload 就不发**（滥用会抢占带宽），只对 LCP 和关键资源用；路由级资源用 prefetch

### 7.1 Koa 中间件原理

> 3. Koa 的错误处理中间件为什么要放在最外层？

**你的回答：**
1. 我感觉洋葱执行就像递归，由外到内再从内到外

```javascript
  console.log('end', state)

```

**评分：6.5/10** 第 1、3 问方向对但缺机制表述；第 2 问只说对了一半

**批注：**
- 第 1 问：递归类比是对的，但 Koa 的洋葱本质是 **Promise 链**：`await next()` 返回的是下一个中间件返回的 Promise，每个中间件的"后半段"挂在这个 Promise 的 then 上。用递归代码演示"由外到内再由内到外"可以，但最好补一句"每个 next() 返回 Promise，compose 把它们串成链"
- 第 2 问关键遗漏：忘记 `await next()` 不只是"不抛错"，而是**后续中间件永远不会执行**——包括负责生成响应体的中间件（router/响应逻辑），请求会**一直挂起直到超时**（浏览器转圈）。"next 前的逻辑照常执行"对，但后果要说全
- 第 3 问：对。错误处理中间件放最外层 = try/catch 包住整个洋葱；如果放中间，只能捕获它内层的错误，它外层的中间件抛错就接不住。补充：错误中间件要 `await next()` 包在 try 里，catch 后设置 ctx.status/body

**参考答案：**
1. **洋葱模型**：Koa 用 `compose` 把中间件串成 Promise 链。执行顺序：请求 → mw1 前半 → mw2 前半 → mw3 前半 →（`next()` 返回）→ mw3 后半 → mw2 后半 → mw1 后半 → 响应。本质是**嵌套的 Promise**，`await next()` 等待的是内层中间件的 Promise resolve
```js
// 等价于手动嵌套：
const chain = () =>
  mw1(ctx, () =>        // next 1
    mw2(ctx, () =>      // next 2
      mw3(ctx, () => Promise.resolve())  // next 3
    )
  );
```
2. **忘记 await next()**：后面的中间件不执行；若路由/响应逻辑在链后面，**响应永远不返回**（挂起超时）。这通常是 bug 而不是"安全的跳过"
3. **错误处理在最外层**：它 `try { await next() } catch (err)` 能捕获**所有内层中间件**的同步异常和 rejected Promise；放中间则外层的错误漏掉。Koa 还支持 `ctx.onerror` 兜底

**你的回答：**

（未作答）

**评分：0/10** ❌ 未作答——系统设计题是高级岗位的核心区分题，务必准备

**参考答案：**
**整体架构**：客户端（编辑器内核 + WebSocket 客户端）↔ 网关 ↔ 协同服务（OT/CRDT 运算 + 文档存储 + 广播）↔ 数据库/对象存储。文档状态机在**服务端**（权威），客户端提交操作、接收操作合并。

1. **数据模型：OT vs CRDT**
   - **OT（Operational Transformation）**：把编辑转成操作（insert/delete/retain），并发操作通过**转换**（transform）消除冲突（如 A 在位置 5 插入，B 在位置 3 插入 → 转换后 A 的插入变成位置 6）。代表：Google Docs、富文本主流。优点：文档格式自由（可处理富文本）；缺点：实现复杂（转换算法 + 服务端有序化），需要服务端做**操作排序**（centralized server）
   - **CRDT（Conflict-free Replicated Data Types）**：每个节点独立合并操作，**不需要中心排序**（基于 LWW/字符序等数学保证收敛）。代表：Yjs（底层 YATA）。优点：**天然支持离线**（本地先应用，联网后合并）、P2P 可选；缺点：文档结构要适配 CRDT 类型（Yjs 用 Y.Text/Y.Map），富文本边界情况多，历史/undo 复杂
   - **选型**：在线文档主流——**CRDT（Yjs）**：离线支持 + 免服务端排序；团队能力强可选 OT。面试答"CRDT + Yjs + 服务端广播"是当下主流方案
2. **实时同步：WebSocket**（不是 WebRTC——WebRTC 是 P2P，文档场景需要中心权威 + 权限 + 持久化，WebSocket 长连接最合适）。同步协议：**操作增量**（不是全量文档），客户端发 op → 服务端应用 + 广播给其他客户端
3. **冲突解决**：① 客户端**乐观更新**（本地立即应用自己的操作，不等服务端）；② 服务端收到并发操作按顺序应用（CRDT 收敛或 OT 转换）；③ **版本号/向量时钟**检测乱序（本地版本落后时先拉缺失操作再应用）
4. **离线编辑与重同步**：客户端本地维护操作队列（或 Yjs 本地状态）；重连后：**增量同步**（上传离线期间的操作，服务端合并/回放）→ 若本地与服务端分叉太多，做**三方合并**（服务端版本 + 本地版本 + 共同祖先）；冲突不可自动解决时提示用户（保留两个版本让用户选）
5. **光标同步**：光标位置是**临时状态**（不入文档历史）。方案：客户端把光标位置（Yjs 的相对位置/OT 的操作位置）随操作或单独通道（频率节流 100ms）广播；**相对位置**而非绝对偏移（别人插入文字时光标不跳）；收到对方光标数据渲染远端光标（不同用户不同颜色）

```js
// debounce：immediate 首次立即执行；cancel 可取消
function debounce(fn, delay, immediate = false) {
  let timer = null;
  let isInvoked = false;   // immediate 下 delay 窗口内只执行一次
  const debounced = function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      isInvoked = false;
      if (!immediate) fn.apply(this, args);
    }, delay);
    if (immediate && !isInvoked) {
      isInvoked = true;
      fn.apply(this, args);
    }
  };
  debounced.cancel = () => { clearTimeout(timer); timer = null; };
  return debounced;
}

// throttle：leading 立即执行 + trailing 尾部执行 + cancel
function throttle(fn, interval, { leading = true, trailing = false } = {}) {
  let lastTime = 0;
  let timer = null;
  const throttled = function (...args) {
    const now = Date.now();
    if (leading && now - lastTime >= interval) {
      lastTime = now;
      fn.apply(this, args);
      return;
    }
    if (trailing && !timer) {
      timer = setTimeout(() => {
        timer = null;
        lastTime = Date.now();
        fn.apply(this, args);
      }, interval);
    }
  };
  throttled.cancel = () => { clearTimeout(timer); timer = null; };
  return throttled;
}
```

```js
function deepClone(obj, map = new WeakMap()) {
  if (obj === null || typeof obj !== 'object') return obj;  // 基本类型/函数
  if (map.has(obj)) return map.get(obj);                    // 循环引用

  const clone = Array.isArray(obj) ? [] : Object.create(Object.getPrototypeOf(obj));
  map.set(obj, clone);

  // 特殊类型
  if (obj instanceof Date) return new Date(obj.getTime());
  if (obj instanceof RegExp) return new RegExp(obj.source, obj.flags);
  if (obj instanceof Map) {
    const m = new Map();
    map.set(obj, m);
    obj.forEach((v, k) => m.set(deepClone(k, map), deepClone(v, map)));
    return m;
  }
  if (obj instanceof Set) {
    const s = new Set();
    map.set(obj, s);
    obj.forEach(v => s.add(deepClone(v, map)));
    return s;
  }

  // Symbol key 也要拷贝
  for (const key of Reflect.ownKeys(obj)) {
    clone[key] = deepClone(obj[key], map);
  }
  return clone;
}
```
关键点：① WeakMap 记录已克隆对象（循环引用）；② `Reflect.ownKeys` 包含 Symbol key（`Object.keys` 不含）；③ Date/RegExp/Map/Set 单独处理；④ 保留原型（`Object.getPrototypeOf`）；⑤ 函数直接引用（不拷贝）

```js
class EventEmitter {
  constructor() {
    this.events = new Map();   // event -> [{ fn, once, maxCount, count }]
  }

  on(event, fn, options = {}) {
    const { once = false, maxCount = Infinity } = options;
    const handler = { fn, once, maxCount, count: 0 };
    if (!this.events.has(event)) this.events.set(event, []);
    this.events.get(event).push(handler);
    return () => this.off(event, fn);   // 返回取消订阅函数
  }

  off(event, fn) {
    if (!this.events.has(event)) return;
    this.events.set(event, this.events.get(event).filter(h => h.fn !== fn));
  }

  emit(event, ...args) {
    if (!this.events.has(event)) return;
    const handlers = this.events.get(event);
    for (const h of [...handlers]) {          // 拷贝遍历：回调里可能增删监听
      h.count++;
      if (h.count >= h.maxCount) this.off(event, h.fn);  // 达到次数先移除（once 也走这里）
      h.fn.apply(this, args);
      if (h.once) this.off(event, h.fn);       // once 执行后移除
    }
  }
}
```
关键点：① once 和 maxCount 都在 emit 里判断并移除；② 遍历时拷贝数组（回调中注册/注销不影响本轮）；③ `off` 用 `filter` 按函数引用移除；④ `on` 返回取消函数方便解绑（防泄漏）

```js
function render(template, data) {
  let code = 'let result = "";\n';
  let cursor = 0;
  // 用正则把模板切成"普通文本"和"逻辑片段"
  const re = /\{\{(.*?)\}\}/gs;
  let match, index = 0;
  while ((match = re.exec(template))) {
    const text = template.slice(index, match.index);
    code += `result += ${JSON.stringify(text)};\n`;   // 普通文本直接拼
    const expr = match[1].trim();
    if (expr.startsWith('if ')) {
      code += `if (${expr.slice(3)}) {\n`;
    } else if (expr === '/if') {
      code += '}\n';
    } else if (expr.startsWith('each ')) {
      const [, itemVar, listVar] = expr.match(/each\s+(\w+)\s+(.+)/) || [];
      code += `for (const ${itemVar} of (${listVar} || [])) {\n`;
    } else if (expr === '/each') {
      code += '}\n';
    } else {
      code += `result += ${expr};\n`;    // 变量替换
    }
    index = re.lastIndex;
  }
  code += `result += ${JSON.stringify(template.slice(index))};\n`;
  code += 'return result;';
  return new Function('data', code)(data);
}
```

>   put(key: string, value: number): void {}
> }
> ```

**参考答案：**
```ts
class LRUCache {
  private capacity: number;
  private map: Map<string, number>;   // key -> value
  constructor(capacity: number) {
    this.capacity = capacity;
    this.map = new Map();              // Map 本身维护插入顺序（迭代序 = 插入序）
  }
  get(key: string): number {
    if (!this.map.has(key)) return -1;
    const value = this.map.get(key)!;
    this.map.delete(key);              // 先删再插 → 移到末尾（最近使用）
    this.map.set(key, value);
    return value;
  }
  put(key: string, value: number): void {
    if (this.map.has(key)) this.map.delete(key);
    this.map.set(key, value);
    if (this.map.size > this.capacity) {
      const oldest = this.map.keys().next().value;  // 迭代序第一个 = 最久未用
      this.map.delete(oldest);
    }
  }
}
```
**核心**：JS 的 `Map` 迭代顺序 = 插入顺序，天然实现 LRU 的"双向链表"语义——`get` 时先删后插把 key 挪到末尾（最近使用），淘汰时删掉迭代序第一个（最久未用）。`Map.get/set/delete` 均 O(1)，满足要求。若面试官追问"不用 Map 怎么实现"：手写**哈希表 + 双向链表**（head/tail 哨兵节点，get 命中把节点移到头部，淘汰移除尾部节点）
