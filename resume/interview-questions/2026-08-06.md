## 一、浏览器与渲染机制（5 题）

### 1.1 渲染流水线

> 从输入 URL 到页面完全展示，浏览器经历了哪些关键阶段？其中"解析 HTML → 构建 DOM → 样式计算 → 布局 → 绘制 → 合成"这条流水线中，哪些阶段会影响首屏时间？哪个阶段最容易成为性能瓶颈？

**你的回答：**
详细来说应该会经历以下阶段：
页面卸载事件回调(若注册了且存在未保存的表单)->浏览器缓存是否命中->若未命中则dns寻址，否则直接返回资源->tcp连接->http请求->http响应资源html资源->浏览器解析HTML和css->构建render tree->布局->绘制->合成

其中资源的网络请求、浏览器渲染过程都会影响首屏时间，其中浏览器渲染过程最容易成为性能瓶颈，主要是由于js单线程的特性，包括js同步代码执行阻塞渲染流程以及css资源下载和解析会阻塞render tree这一步的合成，简单说就是当css未就绪之前是无法合成渲染树进入到下一步的，这也是环环相扣，影响前端性能最大的阻碍一直都是I/O瓶颈，I/O会影响资源交付，资源交付则会阻塞渲染。



**评分：8/10** 流程完整、意识到 JS/CSS 阻塞渲染，但"瓶颈阶段"的回答可以更准，缺关键渲染路径（CRP）概念

**批注：**
- 流程完整（卸载事件 → 缓存 → DNS → TCP → 请求 → 解析 → 渲染），比大多数回答全面
- "渲染过程最容易成为性能瓶颈"表述可以更准：首屏瓶颈通常是**网络阶段（I/O）**和 **JS 执行/脚本阻塞**；渲染流水线内部，Layout 和 Paint 在大 DOM 场景才明显
- 建议补**关键渲染路径（CRP）**概念：HTML 解析 → CSSOM → DOM → 布局 → 绘制 → 合成，其中 CSS 阻塞渲染、JS 阻塞解析

**参考答案：**
1. 完整阶段：URL 输入 →（重定向/缓存命中判断）→ DNS 解析 → TCP 连接（HTTPS 多一次 TLS 握手）→ HTTP 请求 → 响应 → HTML 解析构建 DOM（边解析边发现资源）→ CSS 解析构建 CSSOM → DOM + CSSOM 合并成 Render Tree → 样式计算 → 布局（Layout）→ 绘制（Paint）→ 合成（Composite）
2. 影响首屏：网络请求时间、HTML/CSS/JS 下载、CSS 阻塞渲染、JS 阻塞解析、渲染本身
3. 最容易瓶颈：① 网络（首屏最大头）；② JS 执行（下载 + 执行都阻塞解析和渲染）；③ 大 DOM 下的 Layout/Paint；④ CSS 未就绪不渲染

### 1.2 重排与重绘

> 1. 修改一个元素的 `width`、`transform`、`color`、`opacity` 分别触发什么？（重排/重绘/合成）
> 2. 为什么 `transform` 动画性能优于 `top/left` 动画？
> 3. 连续多次修改 DOM 样式，如何合并重排？`documentFragment` 和 `display: none` 的原理分别是什么？

**你的回答：**
1. 修改width触发重排，transform触发合成，color和opacity触发重绘
2. 因为后者触发重排，几乎是重新渲染；而transform是通过GPU加速合成的技术完成动画渲染，性能远高于重排方式实现动画
3. 使用documentFragment离屏渲染DOM树，等连续修改完样式之后再一次性提交；documentFragment是用于离屏一次性构建DOM的虚拟节点，它本身不参与浏览器渲染，它的子节点会透过它挂在其父节点下，离屏一次性构建所有子节点并批量修改DOM样式，然后一次性提交则只会触发一次重排重绘，`display: none`是隐藏展示，虽然DOM在文档中存在，但是不会渲染到屏幕里，所以它们的区别是一个不存在于文档树但子节点渲染到屏幕中，另一个存在于文档树，但其本身及其子节点不会被渲染到屏幕中


**评分：8.5/10** 四类触发和 fragment/display:none 原理都答对了，理解到位

**批注：**
- 补充细节：opacity 严格说是"重绘 + 合成"；如果元素已被提升为合成层（will-change/transform），opacity 动画可以只走合成，不重绘
- fragment vs display:none 的理解对。补充：fragment 提交后子节点进入真实 DOM（fragment 本身变空）；display:none 时元素在 DOM 中但不在渲染树里，子节点也不渲染

**参考答案：**
1. `width` → 重排；`transform` → 合成（配合合成层，不触发重排重绘）；`color` → 重绘；`opacity` → 重绘（提升为合成层后可只走合成）
2. `top/left` 动画每帧触发重排（重新布局 + 绘制 + 合成）；`transform` 只改变合成属性，由 GPU 合成，不经过 layout/paint
3. 合并重排手段：① documentFragment 离屏批量构建，一次性提交（只触发一次 layout）；② `display: none` 脱离渲染，改完再显示；③ 批量改 className 而非逐条改 style；④ 读写分离（避免强制同步布局）。原理：fragment 不在文档树（无渲染成本），display:none 在 DOM 但不在渲染树（同样无渲染成本）

> 1. Performance 面板中如何识别长任务（Long Task）？
> 2. 有哪些手段可以把长任务拆碎？（提示：yield、requestIdleCallback、Web Worker）
> 3. Web Worker 能解决所有卡顿问题吗？哪些场景用不了？

**你的回答：**
1. 看script执行时间是否大于50ms，并且不是异步阻塞了渲染
2. 时间切片，将任务拆成小任务然后利用浏览器空闲时间执行(rIC)；另起一个线程异步执行，完事后通知主线程(Web Worker)
3. 不能，Web Worker只适用于可异步的长任务，让线程腾出手去做别的工作，对于同步场景则还是需要拆细任务，流式输出结果比较合适


**评分：7.5/10** 识别和拆碎手段方向对，Worker 的边界表述不准确

**批注：**
- 识别长任务补充具体操作：Performance 录制 → Main 面板火焰图里找**红色任务块**（Long Task，>50ms），看 Self Time 和调用栈
- 拆碎手段补充：时间切片（for 分批 + 每批让出）、`yield`、requestIdleCallback（空闲才执行）

**参考答案：**
1. Performance → 录制交互 → Main 面板看任务块，长任务标红（Long Task，>50ms），点开看耗时分布和调用栈（Self Time）
2. 拆碎：时间切片（分批 + await 让出主线程）、yield/setTimeout 分片、requestIdleCallback 利用空闲时间、Web Worker 并行、Scheduler API
3. Worker 不能解决所有：不能访问 DOM、不能做 UI 更新、消息传递有序列化开销；同步依赖页面状态的逻辑丢不进去。适用：图像处理、数据解析、加密计算等纯数据任务

### 1.5 存储方案选型

> 你的项目需要缓存一份 5MB 的离线业务数据，支持跨页面共享，你会选 localStorage / sessionStorage / IndexedDB 中的哪个？为什么？如果数据只有 200KB 但需要频繁读写，又怎么选？请说明各存储的容量、同步/异步、作用域差异。

**你的回答：**
选localStorage，最大容量5m且支持跨页面共享数据；如果数据只有200kb但需要频繁读写则选indexedDB，查询写入高效。
localStorage和sessionStorage最大容量5M，仅存储字符串同步读取和存储，前者永久保存在浏览器除非手动清理，作用域是同源以及子域，后者仅当前标签页有效，因此作用域仅标签页共享；indexedDB容量大于5M，通常达到50M+，存储类型为键值对支持多种类型，同源共享，异步api


**评分：8/10** 选型和差异都答对了，细节可再补

**批注：**

2. 200KB 高频读写 → IndexedDB：容量不是关键，关键是**异步 API 不阻塞主线程** + 支持索引查询和事务
3. 对比：localStorage/sessionStorage 约 5MB、仅字符串、同步、同源/标签页级；IndexedDB 容量大（数百 MB 级）、支持对象/Binary、异步 + 事务 + 索引、同源共享

## 二、HTTP 与网络（5 题）

### 2.1 缓存策略实战

> 你的 SPA 项目静态资源更新后，用户总是看到旧版本。请回答：
> 1. HTML 文件和 JS/CSS 文件分别应该用什么缓存策略（Cache-Control 取值）？
> 2. 带 hash 的文件名解决了什么问题？
> 3. 如果某次发布后 JS 文件内容变了但文件名没变，怎么处理？（提示：CDN 刷新、版本号）

**你的回答：**
1. HTML文件不缓存，js/css文件用长期的强缓存策略
2. 防止更新引用之后还是看到旧版本，每次发版都会重新生成hash，这样就不会命中旧的文件了
3. 这个就是有构建问题，长期处理的话需要修改构建策略，内容变化hash肯定得变化，可以加上版本号或者时间等因素，去生成唯一的hash值；短期应急处理则可以清空cdn缓存，但如果是用户本地浏览器缓存就没办法了，只能根治之后重新发版解决问题


**评分：7.5/10** 缓存策略思路正确，第 3 问缺"基于内容的 hash 内容变了必变，没变 = 资源未走 hash 流程 / 发布没生效"的关键洞察

**批注：**
- 补充标准细节：HTML 用 no-cache（协商缓存，每次回源验证）；JS/CSS 带 hash 用 `max-age=31536000, immutable`（一年强缓存）
- 第 3 问核心：**基于内容的 hash，内容变了文件名必变**（碰撞概率可忽略）——"没变"的真实原因是：① 资源没走 hash 流程（public/ 目录拷贝、asset 未配 `[hash]`、HTML 硬编码外部固定 URL）；② 发布没生效（构建没重跑/回滚）；③ 用户拿到被缓存的旧 HTML（引用旧文件名）。应急：CDN 强制刷新 + URL 加版本参数；用户本地缓存无法远程清除
- 你答的"加版本号/时间因素生成唯一 hash"体现了对 hash 唯一性（碰撞）的考虑，思路正确：时间戳驱动能保证文件名必变。但这是"兜底增强"而非主线——答题应先点出"hash 是内容驱动的，内容变了必变"，时间戳方案的副作用是内容没变也换名、缓存白白失效

**参考答案：**
1. HTML：`Cache-Control: no-cache`（或 `max-age=0` + ETag 协商缓存）；JS/CSS（带内容 hash）：`Cache-Control: public, max-age=31536000, immutable`
2. hash 解决"内容更新但 URL 不变导致命中旧缓存"：文件名变化 = 新 URL = 强制重新下载，无需人工清缓存
3. 内容变 hash 没变基本不会发生（基于内容的 hash，内容变了必变）——真发生了说明：① 资源没走 hash 流程（public/ 拷贝、asset 未配 `[hash]`、固定 URL）；② 发布没生效（构建没重跑/回滚）；③ 用户命中被缓存的旧 HTML。根治：让资源走 contenthash 流程重新发版（URL 自动失效）；应急：CDN 强制刷新 + URL 加版本参数（?v=2）

### 2.2 HTTP/2 与 HTTP/3

> 1. HTTP/2 的多路复用解决了 HTTP/1.1 的什么问题？有没有引入新问题？（提示：队头阻塞、TCP 丢包）
> 2. HTTP/3 为什么用 QUIC？它如何解决 HTTP/2 遗留的问题？
> 3. 在你的项目中，开启 HTTP/2 后还需要做资源合并（雪碧图、concatenation）吗？为什么？

**你的回答：**
1. 解决了1.1无法并行请求的问题，但依旧没觉得队头阻塞问题，单个tcp丢包会导致所有流重传
2. QUIC是多队列独立协议，TCP是单队列有序协议；前者保证每个流独立传输，丢包也只影响自己，自身重传即可；后者一旦产生丢包则所有流重传
3. 不需要，http2的多路复用能并发请求


**评分：8.5/10** 三个问题都答到点子上，尤其"TCP 层队头阻塞"这个关键坑抓得准

**批注：**
- 补充：HTTP/2 还引入 HPACK 头部压缩、二进制分帧；HTTP/3 除独立流外还有 0-RTT 快速握手、连接迁移（WiFi/4G 切换不断连）
- 第 3 问补充：HTTP/2 下不再需要雪碧图/合并，但小文件过多（几百个）时并发流有上限，适度合并仍有意义；HTTP/3 基于 UDP，部分网络环境可能被限制

**参考答案：**
1. 多路复用解决 HTTP/1.1 的队头阻塞（一个连接只能串行请求）+ 连接数限制（浏览器 6 个）；新问题：**TCP 层队头阻塞**——单连接内一个 TCP 包丢失，所有流都等待重传
2. QUIC（基于 UDP）直击 HTTP/2 的 **TCP 层队头阻塞**：① **流级独立传输**——每个流独立编号、独立确认、独立重传，丢包只阻塞自己的流，其他流照常传输（队头阻塞被消除）；② **0-RTT 握手**——重连场景免握手 RTT（HTTP/2 需 TCP+TLS 完整握手）；③ **连接迁移**——用 Connection ID 而非四元组标识连接，WiFi/4G 切换不断连（TCP 会直接断开）；④ **内置 TLS 1.3**——加密默认开启，减少协商开销
3. HTTP/2 后不需要雪碧图/concatenation（多路复用并发请求），但要注意并发流上限（约 100 个），文件数量极端多时适度合并

### 2.3 WebSocket 长连接

> 客服平台的 IM 在线客服用了 WebSocket。请回答：
> 1. 客户端如何感知连接已断开？心跳机制怎么做？
> 2. 断线重连的退避策略是什么？如何防止"同时重连风暴"？
> 3. WebSocket 和 SSE 的使用场景有什么区别？为什么 IM 用 WebSocket 而 AI 对话用 SSE？

**你的回答：**
1. 心跳机制去感知，客户端定期向服务端发送ping请求，询问连接是否正常，服务端需要响应pong表达自己正常收到
2. 每次重新请求连接需要随机延时，防止大量客户端同时重连给服务端带来巨大压力
3. sse是服务端向客户端单向通信，而ws是全双工通信，前者只是需要服务端主动向客户端推送消息，比如用于一些站内消息、AI对话等场景，而ws则用于IM等聊天场景；我感觉AI对话场景比较简单只是一问一答只用SSE即可，这样会轻量一点，但如果需要打断、双向控制等高频互推场景也可以用ws


**评分：8.5/10** 答得不错，第三问还主动分析了"AI 对话也可以用 WS"的边界

**批注：**
- 补充心跳细节：浏览器 WebSocket API **没有内置 ping**，需要应用层心跳（客户端定时发 `{type:'ping'}`，服务端回 pong；N 次无响应判定断开）；断线也可靠 onclose/onerror + 超时检测
- 重连风暴补充：**指数退避（1s→2s→4s→8s，封顶 30s）+ 随机抖动（±20%）**，让客户端重连时间错开

**参考答案：**
1. 感知断开：应用层心跳（客户端定时 ping → 服务端 pong，超时未回判定断线）+ 网络事件（visibilitychange/online）+ onclose/onerror。服务端侧：定期探测死连接并踢掉
2. 退避：指数退避（1s 起翻倍，封顶 30s）+ 随机抖动（±20%）；防风暴：抖动让重连时间错开 + 服务端熔断限流

- 第 1 问补关键点：CSRF 之所以能成立，是因为**浏览器发请求时自动携带 Cookie**——攻击者不需要拿到你的 Cookie，只需要诱导你的浏览器发出请求
- SameSite 三取值必背：**Strict** = 任何跨站请求都不带 Cookie（最安全，但站外链接跳转会丢登录态）；**Lax** = 仅 GET 顶级导航可带（Chrome 默认值）；**None** = 跨站也带（必须配合 Secure，仅 HTTPS）

2. 防御：① SameSite=Lax/Strict；② CSRF Token（请求头带随机 token，服务端比对）；③ 校验 Origin/Referer；④ 敏感操作二次验证（验证码/密码）。SameSite：Strict=跨站都不带；Lax=GET 顶级导航可带（默认）；None=都带（需 Secure，慎用）

### 3.3 CSP 内容安全策略

> 1. CSP 的作用是什么？`default-src`、`script-src`、`connect-src` 分别控制什么？
> 2. 你的知识库网站引入了外部字体和 AI 接口，如何配置 CSP 而不影响功能？

**你的回答：**

**评分：0/10** 未作答——作为信息安全背景，CSP 是必考题，三个指令和 nonce/hash 必背

**批注：**
- CSP（Content-Security-Policy）通过 HTTP 响应头声明"页面允许加载哪些来源的资源"，浏览器拦截违规加载——即使 XSS 注入成功，恶意脚本也执行不了
- 三个核心指令：`default-src`（兜底，所有资源类型的默认策略）、`script-src`（脚本来源，含内联/eval 控制）、`connect-src`（fetch/XHR/WebSocket 等网络请求）；还有 img-src、style-src、font-src 等
- 内联脚本被拦截的三种解法：**nonce**（每次响应生成随机值，script 标签带同值 nonce）、**hash**（把内联脚本内容哈希写进策略）、**外链**（最彻底，抽成独立文件让 `script-src 'self'` 即可）

**参考答案：**
1. 作用：响应头 `Content-Security-Policy: ...` 声明资源来源白名单，违规资源被浏览器拦截。指令：default-src（兜底默认策略）、script-src（脚本：外链域名/内联/eval）、connect-src（XHR/fetch/WS 请求目标）、font-src/img-src/style-src 等
2. 知识库站点示例：`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self' https://fonts.gstatic.com; connect-src 'self' https://api.xxx.com`——外部字体域名进 font-src、AI 接口域名进 connect-src（构建工具可能注入内联样式/脚本，需要 'unsafe-inline' 或 hash/nonce）
3. 内联脚本被拦截：① nonce：`script-src 'self' 'nonce-随机值'`，script 标签加同值 nonce（每次响应换新）；② hash：脚本内容 sha256 写进策略（适合固定不变的脚本）；③ 抽成外链文件（最干净，策略只需 'self'）

**批注：**
- 第 1 问答得很好。补充一个关键点：不可变 + 引用比较是 O(1) 判断变化的前提，也是 React.memo 生效的前提
- 第 2 问补 immer 原理：**Proxy 拦截写入 + 结构共享**——`produce(state, draft => { draft.a.b.c = 1 })`，只有修改路径上的节点被复制，未修改的子树复用原引用，深层嵌套更新比手写展开更安全高效
- 第 3 问的 bug 很典型：直接改对象属性后 setState 传同一个引用 → React 全等比较认为没变 → 不更新。这是 React 经典面试场景，面试时讲这个例子很有说服力

**参考答案：**
1. 不可变数据价值：① **引用比较（===）** O(1) 判断是否变化——React diff、React.memo、bailout 都依赖它（props 引用没变直接跳过重渲染）；② 组件 type 全等判断节点复用；③ 时间旅行/撤销（每次更新都是新快照）；④ 可预测、无共享可变状态
2. 替代方案：**immer**（Proxy 拦截写入，可变写法产生不可变结果）+ **结构共享**（只复制修改路径节点，未修改子树复用原引用）——深层嵌套更新不用手写展开，避免写错
3. 实例：`obj.attr = x; setState(obj)`——引用没变，React 全等判断认为状态没变，不重渲染。修复：`setState({ ...obj, attr: x })` 或 immer 的 produce
