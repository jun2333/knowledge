## 二、技术问题

### JavaScript/TypeScript

**Q: 说说你对事件循环的理解？**

> JS 是单线程的，通过事件循环实现异步。核心机制是：执行栈中的同步代码先执行，遇到异步任务（setTimeout、Promise、DOM 事件等）会把回调注册到对应的任务队列。微任务（Promise.then、MutationObserver）在当前宏任务结束后立即执行，宏任务（setTimeout、setInterval）在下一轮事件循环中执行。
>
> 实际开发中这个知识影响很大，比如 React 的批量更新就是利用微任务来合并 state 变更，Vue 的 nextTick 也是同理。在做流式渲染时，我用 requestAnimationFrame 做节流，它本质上是在浏览器重绘前执行，比 setTimeout(fn, 0) 更精准。

**Q: TypeScript 的类型系统你用到什么程度？**

> 日常开发中我会用泛型、条件类型、映射类型、infer 等高级特性。比如在模板编辑器里，Command 模式的命令对象用泛型约束输入输出类型；在数据构建层用映射类型自动从 API 响应类型派生出 UI 组件的 Props 类型。
>
> 我也做过从 JS 到 TS 的迁移方案，核心策略是先加 tsconfig 的 allowJs，逐步给模块加类型声明，优先覆盖公共接口和数据层的类型，UI 层可以后补。

### React/Vue 框架

**Q: React Fiber 架构解决了什么问题？**

> 核心是解决大应用的渲染卡顿。React 15 的 reconciler 是递归的同步过程，一旦开始就无法中断，如果组件树很深，reconciliation 会长时间占用主线程导致掉帧。
>
> Fiber 把渲染过程拆成了两个阶段：Render 阶段（可中断，构建 Fiber 树，计算 diff）和 Commit 阶段（不可中断，操作 DOM）。每个 Fiber 节点是一个工作单元，通过 requestIdleCallback（实际用的是 MessageChannel 模拟）在浏览器空闲时逐个处理，这样就能让出主线程给高优先级任务（用户输入、动画等）。
>
> 另外 Fiber 还支持优先级调度（Lane 模型），比如用户点击的更新优先级高于数据请求的更新。

**Q: Vue 的响应式原理？React 和 Vue 的核心区别？**

> Vue 2 用 Object.defineProperty，Vue 3 用 Proxy 做数据劫持，配合 Dep 和 Watcher 实现依赖收集和变更通知。React 没有响应式，靠 setState 触发重新渲染，通过 Fiber + diff 算法最小化 DOM 操作。
>
> 核心区别在于心智模型：Vue 是"数据变了，自动更新视图"，React 是"状态变了，重新计算视图"。Vue 更开箱即用，React 更灵活但需要更多手动优化（useMemo、useCallback）。
>
> 在实际项目中，Vue 适合快速交付的业务系统，React 适合需要精细控制渲染性能的复杂应用。两个框架我都深入用过，选型时主要看团队技术栈和业务复杂度。

### 微前端

**Q: Qiankun 的微前端方案你具体怎么落地的？**

> 在众安客服平台，我用 Qiankun 把 5+ 个子应用（ARK 工作台、IM 在线客服、知识库、质量管理等）集成到一个主应用中。
>
> 核心设计：
> 1. **路由方案**：主应用基于 react-router 做路由分发，通过 activeRule 匹配子应用。子应用内部有自己的路由，通过 basename 隔离。
> 2. **通信机制**：用 Qiankun 的 initGlobalState 做全局状态共享（用户信息、权限等），子应用间通信用自定义事件。
> 3. **样式隔离**：开启 strictStyleIsolation（Shadow DOM），对不兼容的组件用 postcss 前缀方案兜底。
> 4. **公共依赖**：通过 webpack externals + CDN 共享 React、Antd 等公共依赖，减少子应用体积。
>
> 踩过的坑：子应用的登录态同步、CSS 变量穿透 Shadow DOM、子应用卸载时的事件监听清理。

**Q: 微前端的性能怎么优化？**

> 1. **预加载**：用 Qiankun 的 prefetch 在主应用空闲时预加载子应用资源
> 2. **公共依赖缓存**：externals + CDN，子应用共享依赖不重复加载
> 3. **按需加载**：子应用路由级别的 code splitting
> 4. **沙箱性能**：ProxySandbox 比 SnapshotSandbox 性能好，优先用 Proxy 方案
> 5. **子应用缓存**：对不常变更的子应用做整体缓存，避免重复解析 JS

### AI 应用开发

**Q: RAG 的原理是什么？你怎么做的？**

> RAG（Retrieval Augmented Generation）的核心思路是：先从知识库中检索相关文档，再把检索结果作为上下文注入到 LLM 的 Prompt 中，让模型基于真实资料回答，减少幻觉。
>
> 我的实现流程：
> 1. **文档处理**：扫描 Markdown 文件，用 RecursiveCharacterTextSplitter 按 1000 字符切分，200 字符重叠
> 2. **向量化**：用 mxbai-embed-large 模型（1024 维）将文本块转为向量，存入 Chroma
> 3. **检索**：用户提问时，将问题向量化，在 Chroma 中做余弦相似度检索，取 Top 5 相关文档
> 4. **生成**：将检索到的文档 + 用户问题 + System Prompt 组装成完整 Prompt，调用 LLM 流式生成回答
>
> 优化点：Embedding 模型的中文支持很关键，我测试过 nomic-embed-text 对中文检索质量差，换成 mxbai-embed-large 后明显改善。

**Q: 流式渲染你是怎么做的？为什么不用 Vue 的响应式？**

> Vue/React 的响应式更新是异步批量的，每次 setState 不会立即触发 DOM 更新，而是等到下一个微任务或渲染周期批量处理。这在逐字输出场景下会导致延迟感和闪烁。
>
> 我的方案是绕过框架响应式，直接操作 DOM + requestAnimationFrame 节流：
> 1. SSE 流式接收 token，拼接到 buffer
> 2. 通过 rAF 在浏览器重绘前统一刷新 DOM（innerHTML）
> 3. 同一帧内多次 token 到达只触发一次渲染
>
> 这样既保证了逐字输出的即时感，又避免了过度渲染。主流 AI 产品（ChatGPT、Claude）也是类似方案。

**Q: 你设计的 AI 开发工作流框架具体是什么？**

> 核心思路是用结构化 Prompt 和 YAML 工作流约束 AI Agent 的行为，让它按标准化流程执行开发任务，而不是随意写代码。
>
> 架构分两层：
> 1. **工作流层**：YAML 定义阶段序列（设计→规划→实现→测试→评审），每个阶段有输入输出规范和门控（用户审批）
> 2. **技能层**：每个阶段对应一个 Skill（Markdown 格式的 Prompt），定义角色、上下文加载规则、执行步骤、输出模板
>
> 关键设计：
> - **反合理化约束**：列出 AI 常见的"偷懒想法"（如"测试差不多能过就行"）并设置纠正规则
> - **确定性/语义分离**：要求 AI 区分"从实际状态读取的事实"和"自己的推断"
> - **知识沉淀**：任务完成后自动收集经验教训，存入知识库供后续复用
> - **Skill 演进**：通过 Skill 执行日志分析不足，持续改进 Prompt

## 三、项目深挖

### 自研模板编辑器

**Q: Command 设计模式具体怎么用的？**

> 编辑器的每个操作（加粗、插入变量、条件块、撤销、重做）都封装为一个 Command 对象，包含 execute() 和 undo() 方法。这样做的好处：
> 1. **可扩展**：新增工具只需实现一个 Command 类，不用改核心逻辑
> 2. **撤销/重做**：维护一个命令栈，undo 时弹出栈顶命令调用其 undo()
> 3. **可组合**：多个 Command 可以组合成宏命令
> 4. **可序列化**：命令可以序列化为 JSON，支持操作录制和回放

**Q: FreeMarker 语法怎么和富文本编辑器结合的？**

> 富文本部分用 contentEditable 实现所见即所得的排版，FreeMarker 语法（`${变量}`、`<#if>` 条件块等）以特殊样式的高亮标签嵌入。渲染时，将富文本 HTML 和 FreeMarker 语法合并输出为完整模板，服务端用 FreeMarker 引擎注入数据生成最终文档。
>
> 难点在于 FreeMarker 标签在富文本中的光标定位和选区处理，需要自定义 Selection 逻辑。

### 金融 SaaS 平台

**Q: JS + Vue 迁移到 TS + React 的过程怎么做的？**

> 新版本不是简单的技术栈替换，而是整体重构——除了 UI 交互保持和旧版本一致之外，内部架构全部重做。核心设计有三块：
>
> **1. DFD（Define Fields Definition）统一字段定义**
> 金融 SaaS 的底层业务字段（如客户信息、抵押物属性）在贷前审批、贷后管理、报表看板等不同模块都有展示，但各处定义和存储方式不一致，导致数据冗余和展示差异。DFD 方案将所有业务字段统一定义为一套 Schema，各应用层通过 Rule Engine 和 Transformer 按需适配展示形态，从根源上解决了"同一字段多处定义、多处存储"的问题。
>
> **2. JSON Schema 驱动页面 + Rule Engine 实现 Product Feature**
> 旧版本是多租户巨石架构，每个租户的差异化配置散落在代码各处，维护成本极高。新版本用 JSON Schema 描述页面结构和内容，配合 Rule Engine 实现产品特性（Product Feature）的差异化配置。这样做的好处：配置和代码彻底分离，新增租户或调整功能只需改 Schema，不动代码；同时推动多版本向单一版本收敛，大幅降低维护成本。
>
> **3. AI 工作流工程化**
> 定义了完整的 Claude 开发工作流：需求 → 设计 → 规划 → 实现 → 测试 → Review，每个阶段有明确的输入输出规范和门控。开发和调试环节也各自有独立的工作流定义，确保 AI 辅助开发过程可控、可追溯。
>
> 技术栈方面，状态管理从 Vuex 换成 Zustand，选型理由是更轻量、API 更简洁、TS 支持更好。
>
> 我离职前新版本还在开发中，未完成全量切换。整体架构方案是我主导设计的，后续由团队继续推进。

## 六、面试小贴士

1. **STAR 法则**：回答项目问题时按 Situation（背景）→ Task（任务）→ Action（行动）→ Result（结果）组织
2. **数据说话**：尽量用数据量化成果（用户量、性能指标、效率提升）
3. **坦诚不会**：遇到不会的问题，说"这块我了解不深，但我的理解是..."比硬编好
4. **引导到擅长领域**：回答时自然地把话题引向你擅长的方向，比如问性能优化可以扯到流式渲染的 rAF 方案
