# RAG 检索优化：常用手段与各自的坑

> 检索质量直接决定 RAG 的回答质量。这里整理检索链路上最常见的几个优化手段，以及它们**什么时候有用、什么时候反而有害** —— 后面几项很多团队实测是负结果。
>
> 文中不写具体指标数字（每套语料、每个模型都不一样），只讲**判断依据**。

## 一、先看清问题在哪

检索不准，症状通常有两种，**先分清再优化**：

| 症状 | 可能原因 | 该动的地方 |
|---|---|---|
| Top5 能命中期望文档，但排名靠后 | 排序不够准 | 混合检索 / 重排 |
| Top5 完全不包含期望文档 | 语料本身没有 / 被同质内容挤占 | **索引范围治理** |

**这是最容易搞混的地方**：很多团队一上来就加 Rerank，但根因其实是**索引里混进了不该进的内容** —— 排序再准也捞不出一个没被索引的文档。

## 二、评估：先把尺子量准

优化之前必须有一把可信的尺子，否则所有改动都无法判断好坏。

### 三个核心指标

- **Top5 命中率（宽松）**：期望文档在前 5 里就算命中
- **Top1 命中率（严格）**：期望文档排第一才算命中
- **MRR（平均倒数排名）**：看期望文档**排在第几名**，用它取倒数再平均 —— 排得越靠前，得分越高

### MRR 怎么算：拿三道题走一遍

「倒数」这个词容易劝退，其实就是**用排名换分数**，越靠前分数越接近 1。

假设有三道题，每道题里期望文档的实际排名如下：

| 题目 | 期望文档排在第几 | 取倒数 | 说明 |
|---|---|---|---|
| A | 第 1 名 | 1/1 = **1.00** | 排第一，满分 |
| B | 第 2 名 | 1/2 = **0.50** | 排第二，一半分 |
| C | 没进前 5 | **0** | 没命中，记0 分 |

```
MRR = (1.00 + 0.50 + 0) / 3 = 0.50
```

两个关键点：

**1. 为什么要「倒数」：因为排得靠前的位置，退步的代价应该更大**

关键不是「排第1 和排第 2 差多少分」，而是**从第几名往后挪一位，损失差多少**：

| 往后挪一位 | 分数变化 | 损失 |
|---|---|---|
| **第 1 → 第 2** | 1.00 → 0.50 | **0.50** |
| 第 2 → 第 3 | 0.50 → 0.33 | 0.17 |
| 第 10 → 第 11 | 0.10 → 0.09 | **0.009** |

「从第 1 掉到第 2」和「从第 10 掉到第 11」都是往后挪一位，但惩罚差了约 **55 倍** —— 这才是合理的：用户打开页面，第一条不是他要的就是明显变差；第 10 和第 11 排他根本看不到，掉一位没有任何感觉。

对比一下「直接算平均排名」：那种算法里，第 1→2 和第 10→11 都只算「掉了 1 名」，**惩罚完全一样**。它只知道「掉了几名」，不知道「掉在哪」—— 这就是必须取倒数的原因。

**2. 没命中记 0 分**，不是记倒数。所以 MRR 会同时被「排得靠前」和「有没有命中」两件事影响。

**它和 Top1 的区别**：Top1 只看「有没有排第一」，第 2 名和第 10 名都算失败；而 MRR 会告诉你「差多少」—— 0.5 说明**大部分时候排第二**，只要把排序微调一下就能提上去，是很明确的改进信号。

范围是 0 ~ 1，越接近 1 越好。

### 为什么不能只看 Top5

**Top5 很容易饱和**。语料一大、查询一泛化，它常年100%，此时任何优化都测不出差异 —— 你会以为改动有效，其实只是指标太钝。

> **实践建议**：拿一批真实 query 跑一遍，如果 Top5 已经 100%，说明这批题太容易，应该换成更有区分度的题（或者直接看 Top1 / MRR），否则后面的实验全是白做。

### 别忘了看来源多样性

一个容易被忽略的信号：**Top5 里有多少是同一篇文档**。

如果 5 个结果里有 4 个来自同一文件，说明召回被单篇霸占了 —— LLM 拿到的上下文其实很单一，信息量远少于"5 条结果"看起来那么多。

## 三、手段一：索引范围治理（最容易被忽略，收益往往最大）

### 问题

索引脚本通常扫全目录，于是**同质内容**被一并索引：问答式笔记、草稿、待归档的临时文件、README。

这类内容和正式正文讲的是**同一批知识点**，但它是精炼问答体 —— **和提问的相似度天然更高**。于是它会大量挤占检索结果。

### 典型现象

> 问「什么是跨域」，Top1 命中的是一份问答笔记，而不是讲跨域的正文章节。

判断很简单：**期望答案在那份文档里吗？** 在，却没被召回 → 被同质内容挤了。

### 解法

在索引配置里显式排除：站点说明页、快速上手、问答式笔记、个人草稿目录、归档区。

### 为什么它比"调参"性价比高

- 成本是**零**（不调模型、不加延迟）
- 生效是**立即**的
- 不引入新的失败模式

**一句话**：不是"能检索的都塞进去"。索引范围是一等公民，值得当成第一件事来审。

> ⚠️ 常见副作用：排除之后**记得重建索引**，否则老块还在库里。排查时先确认"库里到底有没有这份文档"，再谈排序。

## 四、手段二：混合检索（向量 + 关键词）

### 为什么向量不够

纯向量检索擅长**语义相似**，但对**精确匹配**天然弱：

- 用户问 `useEffect` 的第二个参数是干什么的 —— 标识符、API 名、缩写，这些是关键词的强项
- 反过来，问「页面卡顿怎么优化」时，纯 BM25 又抓不到「性能 / 长列表渲染」

两者**互补**，不是谁更强。

### 典型做法

```
向量检索 ─┐
          ├─→ 融合 → （可选）重排 → 按来源去重 → 取 topK
BM25 关键词 ┘
```

### 成本

BM25 是纯词频与逆文档频率计算，**无模型调用、微秒级**。这是它相比 Rerank 的最大优势 —— 很多场景下先用混合检索拿到大部分收益就够了。

### 融合权重怎么定

通常是加权分数融合（如向量分 × w + BM25 分 × (1-w)）。

**务实做法**：先按经验值给个0.5 左右，跑评估看MRR，再微调。**不建议一上来就把权重当调参目标** —— 语料规模、embedding 模型、query 长度分布都会影响最优值，投入产出比通常不如先把索引范围和去重做好。

## 五、手段三：重排（Rerank）—— 看着专业，实测常常是负结果

Rerank 的想法很自然：召回阶段只管"捞回来"，排序交给更精确的模型。于是向量召回 top20→ cross-encoder 对 `(query, doc)` 一起编码打分 → 取 top5。

### 工作流程

分两个阶段：**召回**要快、要全（宁多勿漏），**重排**要准（不关心快）。所以重排不是替代召回，而是排在召回后面的第二道关。

```
用户提问
   ↓
① 向量召回 top20          ← 快，但排序粗糙，只保证「捞得回来」
   ↓
② cross-encoder 逐条打分    ← 慢但准，对 20 条逐一算相关性
   ↓
③ 按分数排序，取 top5
   ↓
交给 LLM 生成
```

第 ② 步的实现（本地 ONNX 模型，模型只加载一次复用）：

```ts
const inputs = await tokenizer(
  docs.map(() => query),                        // query 作为第一段
  {
    text_pair: docs.map((d) => d.pageContent),   // 每个 doc 作为第二段
    padding: true, truncation: true, max_length: 512,
  },
)
const scores = (await model(inputs)).logits.data  // 每对 (query, doc) 出一个分数
```

**它把每一对 (query, doc) 拼成一段文本送进模型** —— 20 条候选就是 20 次前向计算，这就是慢的原因。

### 原理：为什么比向量检索准

关键在于**向量检索（bi-encoder）和 cross-encoder 的架构差异**：

| | 向量检索（bi-encoder） | 重排（cross-encoder） |
|---|---|---|
| 怎么算 | **文档和query 各自**编码成向量，再算距离 | **query 和 doc 拼在一起**编码，直接输出分数 |
| 文档侧 | 编码一次，**存起来复用** | 不预编码，**每次现算** |
| 能否交互 | ❌ 编码时看不到对方 | ✅ 注意力可以逐词比对 |
| 精度 | 快、粗 | 慢、准 |
| 适用 | 亿级候选的粗筛 | 几十条候选的精排 |

**向量检索的根本局限**：文档被编码成向量时，它不知道你将来会问什么。「苹果手机很贵」这句话，向量里只有「苹果/手机/贵」的语义 —— **如果提问是「iPhone 的售价」**，虽然指向同一件事，但向量空间里「苹果」和「iPhone」不一定挨着。

**cross-encoder 解决了这个**：它把「iPhone 的售价」和「苹果手机很贵」拼成一句话送进模型，**注意力机制能让「iPhone」和「苹果」直接对上**。代价是必须现算 —— 没法预存。

> 一句话：**向量检索是「先各自理解，再比相似」；cross-encoder 是「放在一起逐词对照」。后者更准，但无法提前算。**

### 为什么它常常有害

原理清楚不代表效果一定好。实测这个项目里 Top1 命中率从 83% 掉到 58%，三个原因：

**① 同文档块互相挤压（最主要的原因）**

召回 top20 里可能有 8 个块来自同一篇文档。cross-encoder 会给同篇的每个块都打高分，于是**正确的文档被自己的同胞挤出去**。

典型：期望 `error-monitoring.md`，重排后前4 名全是 `monitoring.md`。

**② 截断吃掉关键信息**

cross-encoder 有最大长度限制（常见 512 token）。中文 1000 字符约 500~700 token —— **长块的后半段直接被丢掉**，而答案可能就在后半段。

**③ 小模型判别力不够**

278M 级别的 reranker 对中文技术文档的判别力，可能**不如你已经在用的多语言 embedding**。这时 Rerank 不是"锦上添花"，而是"用更弱的模型覆盖更强的模型"。

### 重排前必做：sanity check

怀疑 Rerank 有问题时，先拿**一条明显相关 + 一条明显不相关**的候选打一遍分：

```
 7.309   | 闭包是指函数可以记住并访问所在的词法作用域…← 相关
-10.041  | 本文讲解 Vue 的响应式原理…                ← 不相关
```

- 分数差距明显 → **调用是正确的**，问题在模型/策略
- 分数都很接近或顺序错了 → 是实现问题，别急着下结论说"rerank 没用"

> 这一步能省掉大量误判。很多人看到指标掉了就直接放弃，却没发现是调用写错了。

### 替代方案：按来源去重（几乎总是更划算）

针对"同篇占满 TopK"，**先做去重**（同一篇只保留最相关的一块）：

- 指标**基本持平**（不会掉）
- **来源多样性明显变好** —— LLM 拿到的上下文更丰富

经验上，**去重 + 关闭 Rerank** 往往优于"去重 + 打开 Rerank"。

### 结论

**默认关闭，代码保留、随时可开。** 若以后要重试，优先换更强的 reranker（如支持中文更好的 large 级模型）并放宽截断，而不是继续在原方案上调参。

## 六、手段四：按标题层级切分 —— 看起来更优雅，未必更好

### 想法

用标题栈维护 `h1 > h2 > h3` 的归属，给每个块加**面包屑前缀**：

```
【文档标题 > 二级标题 > 三级标题】
块正文……
```

动机很实在：纯按长度切分时，长章节被切开后，后面的块**不知道自己属于哪个章节**，检索和生成都容易"断章取义"。加上面包屑后，块自带上下文。

### 实测常见结果：指标不升反降

原因分析：

- **块更小、竞争更激烈**：按标题切让块数近乎翻倍，同一文档产生大量小块，检索时互相抢 Top5，反而挤掉了更"整段"的相关内容
- **面包屑稀释语义**：前缀里混入了带 emoji 的标题、层级编号等噪声，对纯语义向量检索可能是干扰
- **指标本身的局限**：文件级命中这个指标测不出面包屑的真实价值 —— 它的收益本应体现在**给 LLM 的上下文更完整**（即生成质量），而那是另一个评估维度

### 关键结论

> **切分粒度是双刃剑**：更细不一定更准。块太小会丢上下文、增加竞争。

判断该不该用标题切分，要看你**评估的是哪一环**：
- 只看"检索命中哪个文件"→ 标题切分多半无收益
- 看"给 LLM 的上下文是否完整" → 可能有收益（需要另一个评估集，比如让 LLM 判断回答是否引用了正确章节）

**别用"设计上更优雅"替代"实测更有效"。** 负结果也是结果 —— 记下来能避免以后重复踩坑。

## 七、手段五：让 LLM 自己找文件（Agent 工具式检索）

前面四个手段都是「**系统替LLM 检索**」。还有一条完全不同的路：**给 LLM 工具，让它自己决定搜什么、读哪篇。**

### 两种思路的对比

| | 传统 RAG（手段一~四） | Agent 工具式 |
|---|---|---|
| 流程 | 系统一次检索 → 塞进 context | LLM 决定何时检索、搜什么 |
| 上下文 | **切片**（可能断章取义） | **原文全文** |
| 轮次 | 1 轮 | 多轮（检索 → 看结果 → 再查） |
| 可控性 | 高（链路固定） | 低（取决于模型行为） |

### 三种具体形态

**① 检索 + 取全文（两段式，最常见）**

```
工具一：search_knowledge(query, top_k)   → 语义检索，返回片段 + [来源N]
工具二：get_doc_content(path)             → 读某篇完整原文
```

LLM 先检索，看片段够不够；不够就自己调第二个工具读全文。**适合需要跨文章对比、或用户要求总结全文的场景。**

**② 直接 grep（关键词驱动）**

```
LLM → bash: grep -rn "跨域" docs/ → 命中行 + 路径 → 再 read 具体文件
```

这是 Claude Code / Cursor 这类编程 Agent 的做法。它们天生带 `grep` / `glob` / `read` 工具。

**为什么编程 Agent 几乎都用 grep 而不是向量库**：

| | grep | 向量检索 |
|---|---|---|
| 擅长 | **精确词**（函数名、报错码、标识符） | 模糊语义 |
| 前提 | **文件在磁盘上就行** | 必须先建索引 |
| 新鲜度 | **永远最新** | 改了文件得重建索引 |
| 成本 | 扫全库 | 预计算 |

**关键优势是新鲜度** —— 向量库有「改了文件但忘了重建索引」的漂移问题，grep 没有。

**③ 直接翻全目录（最暴力）**

给 `list_files` + `read_file`，让 LLM 自己翻。适合**语料很小**（几十个文件）的场景。

### 什么时候值得加

**判断依据是语料里「精确符号」的比例。** 如果知识库是技术文档，里面会有大量这类内容：

```
patchVnode、openBlock、beginWork、Lane、SchedulerPriority
ERR_PNPM_IGNORED_BUILDS、useLog、setState、HashMap
```

这些是**向量检索的长尾弱项** —— 语义上「相近」的文档很多，但只有一篇真讲了它。

### 但别直接给 LLM 裸grep

**LLM 不会写正则**，而且 grep 只返回命中行，**上下文还得靠 `-A/-B` 拿**。业界更常见的做法是给个语义化的封装：

```
search_code(symbol: string)   ← 内部做 grep，但参数是「符号名」而非正则
read_file(path: string)       ← 读全文而不是命中行
```

比暴露 `bash` + 让模型自己拼 `grep -rn "pattern" docs/ --include=*.md` 稳定得多 —— 后者会写出错误的 pattern、漏掉转义、或者扫进不该扫的目录。

### 代价

- **多一轮工具调用** → 延迟增加（本地 8B 模型尤其明显，一次工具往返就是好几秒）
- **不确定性** → 模型可能不调工具就瞎答，或反复调同一个工具
- **需要评估手段变复杂** → 「检索指标」不再适用，得看「最终回答对不对」

### 实践建议

> **先做「检索 + 取全文」这一半** —— 成本最低（两个工具的事），收益在没有全文需求时为零，但一旦用户要「总结某篇文章」就必需。
>
> **grep 通道留给真正被精确符号卡住的时候**：如果评估集里「含代码标识符」的题目召回率明显偏低，再加不迟。

## 八、落地顺序建议

```
1. 先量准评估（Top5 饱和了就换指标）
2. 审索引范围（排除同质/低质内容）        ← 成本最低、收益往往最大
3. 加混合检索（向量 + 关键词）            ← 零模型成本
4. 按来源去重（提升上下文多样性）        ← 指标不掉、只赚
5. 加「取全文」工具                      ← 需要全文/对比时才用得上
6. Rerank / 标题切分                      ← 前面都做了还有问题再说
```

大多数团队在第 2、3 步就拿到了主要收益。**先做便宜的、有确定收益的，把需要额外依赖和延迟的都留到最后。**

## 九、经验总结

1. **先升级评估，再做优化** —— 饱和的指标会掩盖所有差异
2. **索引范围是一等公民** —— 不是"能检索的都塞进去"
3. **Top5 命中率不代表体验好** —— 还要看 Top1、MRR 和来源多样性
4. **切分粒度是双刃剑** —— 更细不一定更准
5. **Rerank 不是免费的午餐** —— 先sanity check，再用去重替代
6. **负结果也是结果** —— 把它记下来，比"看着专业就上"值钱

## 附：标题路径切分的实现思路（实验用）

若你的评估维度是"生成质量"，标题切分值得重新考虑：
