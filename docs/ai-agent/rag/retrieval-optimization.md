# RAG 检索优化实践：切分策略与索引范围

> 本知识库的 RAG 检索链路（Chroma + bge-m3 + qwen3:8b）做过一轮优化，用 12 题的回归测试集量化验证了两个手段。
> 结果一个是**正效果**（排除干扰内容），一个是**负结果**（标题路径切分没提升）——把过程和结论记下来，避免以后重复踩坑。

## 一、背景与问题

RAG 的检索质量直接决定回答质量。这轮排查发现两个可疑点：

1. **块的章节归属丢失**：切分用 `RecursiveCharacterTextSplitter`，长章节被 `\n\n` 二次切分后，后面的块只剩正文、不知道自己在哪个 `##/###` 标题下，检索和生成都容易"断章取义"。
2. **索引范围失控**：`rag:index` 扫描 `docs` 下**所有** md，把个人笔记类内容（尤其 `interview-questions/` 面试题）也索引进去了。面试题和知识正文**同质**（都是同一批知识点），但它是精炼问答、和 query 的相似度还特别高，于是大量挤占检索结果。

## 二、评估方法

单看"命中率"不够——原来的测试集太容易，12 题 `Top5 命中率` 全是 100%，任何优化都测不出来。所以先把评估升级为更有区分度的指标：

- **Top5 命中率**：期望文档是否出现在前 5（宽松）
- **Top1 命中率**：期望文档是否排第一（严格）
- **MRR**（平均倒数排名）：期望文档排名的倒数的平均，越接近 1 越好

测试集：12 道典型问题（`server/scripts/rag-eval.ts`），每题标注期望命中的文档，`Top5`/`Top1`/`MRR` 三个指标一起看。

## 三、实验数据

三组对照（同一测试集、同一模型）：

| 方案 | 切分策略 | 索引范围 | Top5 | Top1 | MRR | 块数 |
|------|---------|---------|------|------|-----|------|
| ① | 标题路径 | 含面试题 | 100% | 7/12 (58%) | 0.743 | 4597 |
| ② | 标题路径 | 排除面试题 | 100% | 9/12 (75%) | 0.861 | 4115 |
| ③ | 纯字符切分 | 排除面试题 | 100% | **10/12 (83%)** | **0.917** | 2602 |
| ④ | ③ + Rerank（未去重） | 排除面试题 | 100% | 7/12 (58%) | 0.739 | 召回 20 重排 |
| ⑤ | ③ + 按来源去重 | 排除面试题 | 100% | **10/12 (83%)** | **0.917** | 2602 |
| ⑥ | ⑤ + Rerank | 排除面试题 | 100% | 7/12 (58%) | 0.764 | 召回 20 重排 |

### 手段一：索引范围治理（① → ②，有效）

把 `interview-questions/**` 从索引里排除，**Top1 命中率 58% → 75%，MRR 0.743 → 0.861**。

典型对比（问题"什么是跨域"）：
- 含面试题时 top1 是 `interview-questions/2026-08-07.md`（面试题里的跨域问答）
- 排除后 top1 回到 `browser/cross-origin.md`（本该命中的知识正文）

**结论：同质内容会污染检索，索引范围要治理。**

### 手段二：标题路径切分（② vs ③，负结果）

给切分加"标题栈 + 面包屑"（每个块前缀拼 `【文档标题 > 二级标题 > 三级标题】`），块数从 2602 涨到 4115。但指标不升反降：**Top1 75% → 83%（换成纯字符切分反而更高），MRR 0.861 → 0.917**。

**结论：在"文件级检索命中"这个指标上，标题路径没有带来收益，甚至略降。**

## 四、为什么标题路径没帮上？

- **切分更细，块更小**：标题切分让块数近乎翻倍，单块上下文变少；同一文档产生大量小块，检索时互相竞争 top5，反而挤掉了更"整段"的相关内容。
- **面包屑稀释语义**：前缀里混入了带 emoji 的标题（如 `📖 核心概念`）等噪声，对纯语义向量检索可能是干扰。
- **指标本身的局限**：本测试集测的是"检索命中哪个文件"，而标题路径的价值本应在**给 LLM 的上下文更完整**（提升生成质量）——这是"文件级命中"测不出来的。
- **样本量小**：12 题、1 题之差（8%），也可能是噪声。

## 五、手段三：Rerank 重排（也是负结果）

**方案**：向量召回 top20 候选 → 本地 cross-encoder（`Xenova/bge-reranker-base`，ONNX）对 `(query, doc)` 一起编码打分 → 取 top5。

**实测**：Top1 83% → 58%，MRR 0.917 → 0.739，**明显下降**。

典型失败：问题「前端错误监控如何实现？」期望 `performance/error-monitoring.md`，重排后前 4 名全是 `performance/monitoring.md`，期望文档被挤到第 5。

### 先验证是不是实现有问题

拿一条明显相关、一条明显不相关的候选做 sanity check：

```
7.309   | 闭包是指函数可以记住并访问所在的词法作用域…   ← 相关
-10.041 | 本文讲解 Vue 的响应式原理…                  ← 不相关
```

分数差距很大，**说明调用是正确的**，问题出在模型/策略本身，不是代码 bug。

### 为什么会变差

- **同文档块互相挤压**：top5 常被同一篇的多个块占满（「前端错误监控」前 4 名全是 `performance/monitoring.md`），reranker 给同篇各块都打高分，把正确文档挤下去。
- **512 token 截断**：块最长 1000 字符，中文约 500~700 token，长块后半段被截掉。
- **模型区分度不足**：`bge-reranker-base`（278M）对中文技术文档的判别力，不如已经在用的 `bge-m3` 向量。

### 顺带做的改进：按来源去重

针对"同篇占满 top5"，加了**去重**（同一篇文档只保留最相关的一块）。Top1/MRR 指标持平（83% / 0.917），但**多样性明显变好**——同一道「前端错误监控」题，top3 从"同一篇重复 4 次"变成 `error-monitoring → monitoring → react/error-handling`，给 LLM 的上下文更丰富，所以去重保留。

**即便先去重再上 rerank（方案⑥），仍只有 58% / 0.764**，因此 **Rerank 默认关闭**（`config.rerankEnabled = false`），代码保留、随时可开。

> 若以后要重试 Rerank，优先换更强的模型（`bge-reranker-v2-m3` / large）并放宽截断，而不是继续调 base 版。

## 六、最终取舍与经验

**采用方案 ⑤**：纯字符切分 + 排除面试题 + 保留 h1 兜底（文档没 frontmatter title 时用正文一级标题）+ **按来源去重**。

经验总结：

1. **先升级评估，再做优化**：饱和的指标（Top5 全 100%）会掩盖所有差异，要换成 `Top1`/`MRR` 之类有区分度的指标。
2. **索引范围是一等公民**：不是"能检索的都塞进去"，同质/低质内容（面试题、草稿）要主动排除。
3. **负结果也是结果**：标题路径"看起来更专业"，但实测无收益，那就别上——避免用"设计上更优雅"替代"实测更有效"。
4. **切分粒度是双刃剑**：更细不一定更准，块太小会丢上下文、增加竞争。
