## 逻辑复用
逻辑复用是编程必须掌握的技巧，对于前端而言组件化思想也是一种逻辑复用。纵观vue、react等框架的进化史，基本上都是经历了如下阶段：
1. mixins(Vue、React)
2. HOC(React)
3. Render Props(React)
4. React Hooks、Vue composition API

组件的表达方式从类组件到函数组件的一个转变，目的就是将状态、逻辑与组件本身解耦开来，与组件的生命周期解耦开来(React的函数组件已经没有生命周期钩子了)
为啥类组件慢慢走向了函数组件呢？
我的理解是，首先javascript这个语言本身就不是像java那样按照面向对象编程去设计的；它的对象是基于原型和原型链的设计、是动态的，相较面向对象、基于类的写法，还是对象委托关联的复用手段表达更为确切，虽然es6也支持了class语法，但是其底层依旧是基于对象委托关联，并且与传统类的特点也有所差异，如类是静态的，而js里的却是动态；类的继承、实例化是基于复制，而js仍然是通过原型委托关联
以上是对js类的理解，回到js本身，函数是javascript的第一公民，函数的使用比类更为简洁简单，并且可以将**状态逻辑**等代码与**函数组件**解耦，使得项目代码逻辑更为清晰，也更好维护；Vue的composition API和React Hooks的出现就是为了解决逻辑复用问题。

因此React更推崇函数组件描述UI，通过Hooks的方式切入状态逻辑，逐步弃用将逻辑写在各个生命周期钩子中，从而避免逻辑分散
Vue的话，也大致是这个方向，由原来的option api转成composition api，通过一个setup函数统一收拢所有逻辑

### mixins混合
在vue3之前以及react HOC之前都是用的这种方式实现逻辑复用。
实质上就是将一个大的组件实例对象按照功能拆分，分解成多个对象，最后执行的时候再合并。
这样最大的问题就是命名冲突和逻辑分散，拿vue单文件组件来举例：
每个mixin文件都可以定义自己的data、watch、computed、methods，这就势必会引发两个问题：
1. 除了生命周期命名冲突导致覆盖
2. 状态和逻辑可能会分散与各个生命周期，多个mixin文件可能用到同一个状态，代码混乱难以维护。比如想了解一个状态被哪些逻辑控制，可能需要依次找遍组件引用的所有mixin查看。
3. 代码无法良好分割导致产生大量重复代码

### HOC
其实就是React对装饰器模式的一种实现，实质上就是一个函数接收一个组件(函数/类)作为入参，然后经过包装再返回一个新的组件
常见的手段有两种：
1. 属性代理
2. 反向继承

### 属性代理
接收一个组件，返回一个新的组件
优点：属性代理可以与业务组件低耦合甚至零耦合，无须直到组件内部逻辑，可以增强其属性或者控制条件渲染
缺陷：
1. 无法得知业务组件内部状态，可能需要ref手段控制业务组件
2. 无法直接继承静态属性，需要手动处理或者借助第三方库集中处理(hoist-non-react-statics)
3. 本质上是一个新组件需要forwardRef转发ref

### 反向继承
优点：
1. 方便获取组件内部状态，比如 state ，props ，生命周期，绑定的事件函数等。
2. es6继承可以良好继承静态属性。所以无须对静态属性和方法进行额外的处理。
缺点：
1. 函数组件无法使用。
2. 和被包装的组件耦合度高，需要知道被包装的原始组件的内部状态，具体做了些什么？
3. 如果多个反向继承 HOC 嵌套在一起，当前状态会覆盖上一个状态。这样带来的隐患是非常大的，比如说有多个 componentDidMount ，当前 componentDidMount 会覆盖上一个 componentDidMount 。这样副作用串联起来，影响很大

### HOC应用
1. 强化props
2. 渲染劫持
3. 配合import实现动态加载
4. 组件赋能：可以对组件添加一些类似于事件监听、错误监控

#### HOC注意事项
1. 谨慎修改原型
2. 不要在函数组件内部使用HOC
3. ref处理
4. 静态属性处理
5. 注意多个 HOC 嵌套顺序问题
6. 约定displayName

#### HOC缺陷
1. 不遵守约定可能造成props冲突
2. 嵌套泛滥,多层抽象同样增加了复杂度和理解成本，这是最关键的缺陷
3. Ref传递缺陷
### Hooks
将逻辑复用转变成hook的组合，React 16以后推出了很多内置hook，有与状态有关的useState，与生命周期有关的useEffect等等。
这样就可以将代码逻辑和状态随意组合成一个自定义hook，我们可以封装很多通用hook从而达到代码复用的目的。
同时函数组件代替类组件，使得开发更为简洁简单，理解成本更低

当然Hooks也有一些缺陷：
1. 额外的学习成本，主要在于 Functional Component 与 Class Component 之间的比较上
2. 写法上有限制(不能出现在条件、循环中)，并且写法限制增加了重构成本
3. 闭包陷阱，可能使用到旧值
4. React.memo 并不能完全替代 shouldComponentUpdate (因为拿不到 state change，只针对 props change)
5. useState设计上的不完美

#### Hooks注意事项
1. 不是所有的依赖都必须放到依赖数组中
2. deps 参数不能缓解闭包问题，需要真正理解闭包问题产生的原因
3. 延迟调用会存在闭包问题，如setTimeout、setInterval、Promise.then等----在有延迟调用场景时，可以通过 ref 来解决闭包问题
产生原因由于异步api回调函数引用的参数可能是一个过期的值，这里存在一个闭包引用
1. useCallback 建议不使用。
useCallback 可以记住函数，避免函数重复生成，这样函数在传递给子组件时，可以避免子组件重复渲染，提高性能。但是使用前提是，子组件必须使用了 shouldComponentUpdate 或者 React.memo 来忽略同样的参数重复渲染。否则 useCallback 不仅没有提升性能，反而让代码可读性变的很差。建议一般项目中不用考虑性能优化的问题，也就是不要使用 useCallback 了，除非有个别非常复杂的组件，单独使用即可。期望不要用 useCallback，直接裸写函数就好
1. useMemo 建议适当使用
2. useState 要正确使用
6-1. 能用其他状态计算出来就不用单独声明状态：一个 state 必须不能通过其它 state/props 直接计算出来，否则就不用定义 state
6-2. 保证数据源唯一。在项目中同一个数据，保证只存储在一个地方。不要既存在 redux 中，又在组件中定义了一个 state 存储。不要既存在父级组件中，又在当前组件中定义了一个 state 存储。不要既存在 url query 中，又在组件中定义了一个 state 存储。
6-3. useState 适当合并。大量使用了 useSetState 来代替 useState，来管理复杂类型的 state

### 总结
React在逻辑复用上，从mixins到HOC，从HOC到Render Props再到现在的Hooks，几乎都是为了开发者能更好的进行代码复用，写出更清晰、更好维护的代码
