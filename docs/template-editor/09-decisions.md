## 一、关键设计决策

| 决策 | 选择 | 理由 | 来源 |
|------|------|------|------|
| 对外形态 | Web Component | 宿主技术栈不可控，需要框架无关的接入方式 | 【文档】 |
| 内容样式 | 内联样式 | 内容会导出到编辑器之外（邮件客户端 / PDF 渲染器），那里没有你的 CSS 文件 | 【文档】 |
| 交互样式 | Tailwind + Shadow DOM | 只活在编辑器内部，快速开发且需隔离 | 【文档】 |
| 数据源 | DocNode 为 Single Source of Truth | DOM 不适合直接持久化 / diff / 跨端渲染 | 【文档】 |
| 操作封装 | Command 模式 | 所有编辑操作统一收口，新增工具不动引擎 | 【文档】 |
| Command 通信 | 经 CommandContext 代理 | Command 不引用 Manager，可独立单测、拿不到不该拿的状态 | 【文档】 |
| 撤销机制 | 快照 + diff，而非逆操作 | 复合操作（拖入变量 = 插入 + 绑数据 + 应用样式）逆操作难写易错 | 【文档】 |

## 二、真实难点复盘

> 下面这些是原设计记录里真实写出的坑，面试讲这些比讲"我用了 XX 模式"更有说服力。

### 难点 1：Undo 恢复 DOM 时污染历史（`isRestoring`）

**现象**：程序性恢复 DOM 会触发 contentEditable 的 `input`，被 `handleInput` 当成新编辑推入历史栈，连续 Ctrl+Z 出现"撤销又被顶回去"。

**本质**：**程序性 DOM 变更与用户输入走同一个事件通道**，不区分来源就会互相污染。

**解**：恢复期间上 `isRestoring` 锁，`handleInput` 检测到直接 return；所有恢复路径（undo / redo / `setTemplate`）共用同一把锁。详见 [07 · Undo/Redo](./07-history.md)。

### 难点 2：DOM 重建后光标丢失

**现象**：模型更新会重建 / patch DOM，浏览器 Selection 随之失效。

**解**：编辑器自己维护**模型坐标**选区（`nodeId + offset`），DOM 变更前保存、变更后 `positionToDOM` 翻译回浏览器 Range。前提是节点 ID 稳定。详见 [02 · 文档模型与选区](./02-document-model.md)。

### 难点 3：中文输入法（IME）与选区冲突

**现象**：拼音输入过程中会触发多次中间态，若每次都更新选区 / 模型，会打断输入。

**解**：`compositionstart` 时冻结选区更新，`compositionend` 后一次性提交。详见 [02 · 文档模型与选区](./02-document-model.md)。

### 难点 4：首次加载和后续更新两套逻辑容易分叉

**解**：统一 `reconcile` 接口，容器空不空都由它判断，首次加载只是"oldChildren 为空"的特例；首次挂载再用 DocumentFragment 离屏构建，减少 reflow。详见 [04 · 渲染引擎](./04-render-engine.md)。

### 难点 5：复杂容器重建会丢状态、子节点闪动

**现象**：condition / loop 内部有折叠状态和较深的子树，若属性一变就整块重建，会丢失折叠状态并造成子节点闪动。

**解**：Handler 的 `update` 做成**可选**——复杂组件实现 `update` 原地 patch 自身属性（再递归 reconcile 子节点），简单组件不实现、直接重建。详见 [04 · 渲染引擎](./04-render-engine.md)。

### 难点 6：连续打字产生几十条历史

**解**：快照 `push` 做 500ms 节流，连续输入合并为一次快照，避免一次 undo 只退一个字符。详见 [07 · Undo/Redo](./07-history.md)。

### 补充：输入受控 vs 工具受控

这是原项目在面试复盘时明确过的设计选择：**输入不受控（用户直接敲 contentEditable，DOM 先变、再同步回模型），工具操作受控（走 Command 改模型、再渲染 DOM）**。前者保证打字手感，后者保证结构可控。

## 四、高频追问 Q&A

> 按"问题 / 答题要点"给框架，具体数字和细节请按你的真实经历替换。

**Q1：为什么自研，不直接用 Quill / Slate / CKEditor？**
要点：通用富文本编辑器面向"排版"，而这个项目的核心是**结构化语义节点**（变量、条件、循环）→ 需要在编辑态就保留语义、并能精确序列化成 FreeMarker；接入任意富文本编辑器都要把它的模型映射成 DocNode，映射成本 + 失控风险高于自研内核。【推导】

**Q2：自研编辑器最大的风险是什么，怎么控制？**
要点：编辑器难点集中在**选区 / 光标、输入法、DOM 与模型同步**。控制手段：模型坐标选区 + 稳定 ID（抗 DOM 重建）、`isRestoring` 锁隔离程序性变更、统一 reconcile 收敛渲染逻辑、Command + Handler 把"改模型"和"改 DOM"彻底分开。【文档 + 推导】

**Q3：编辑器整体架构画一下？**
要点：四层（Web Component → React 外壳 → Core Engine → 样式策略），Core Engine 再分 model / engine / render / serialize 四包，依赖单向。见 [01](./01-overview.md)。

**Q4：一次操作（比如插入变量）从点击到界面更新，经过哪些步骤？**
要点：拖拽 drop → 计算模型 `Position` → `InsertVariableCommand` → Manager 存快照 + 建 Context → Command 改 DocNode → 靶向插入 / reconcile 更新 DOM → 派发 `template-change`。见 [03](./03-command-engine.md) / [04](./04-render-engine.md)。

**Q5：为什么撤销用快照不用逆操作？**
要点：复合操作逆操作难写易错；快照天然覆盖任意复杂操作；DocNode JSON 体积可控 + 500ms 节流 + diff 靶向更新兜住性能。见 [07](./07-history.md)。

**Q6：Undo 怎么做到不全量重渲染？**
要点：diffDocNodes 找出 `dirtyIds` → 逐个 patch（删除 / 恢复 / 属性变更三类），复用未变的 DOM。见 [07](./07-history.md)。

**Q7：模板保存和渲染的契约是什么？**
要点：**单一数据源**——数据库只存 DocNode JSON，模板字符串是派生物；编辑、预览、生产渲染都从同一份 JSON 派生，因此"预览 = 实际发出"是机制保证而非人工对齐。见 [06](./06-serialization.md)。

**Q8：新增一种工具（比如"插入签名"）要改哪些地方？**
要点：**三处，不动引擎**——新增一个 Command（改模型）、一个 DOMHandler（渲染该节点类型）、一个触发入口（工具栏 / 拖拽）；只改 `handlerMap` 注册。见 [05 · 工具设计](./05-tools.md) 开篇。

**Q9：邮件客户端兼容怎么处理？**
要点：内容样式内联、Email 模式走表格布局 + 受限 CSS 子集、按 `compatibility` 设置区分兼容级别；本质上"编辑即输出"，所以兼容约束落在渲染 / 序列化环节而不是事后修。见 [01](./01-overview.md)。

**Q10：为什么不用 diff 做日常编辑，却用它做 Undo？**
要点：日常编辑的事件**知道改了什么**（操作类型 + 目标 + 内容），直接靶向更新；只有从快照恢复时"不知道该改哪里"，才需要 diff。见 [04](./04-render-engine.md)。

**Q11：如果支持多人协作，架构要怎么改？**
要点（扩展性追问，项目未实现，讲思路即可）：DocNode 是天然 CRDT / OT 的作用对象；模型坐标选区可映射成协同光标；Command 是操作单元，可作为协作操作的传输单元。分层已经把"数据"和"视图"分开，接入协同主要在 engine 层。【推导】

**Q12：如果重做一遍，会有什么不同？**
要点：把 Handler 契约、`update` 的边界、`isRestoring` 这类"程序性 vs 用户性变更"的区分在架构层就固化；把内容样式的内联生成做成独立可测的子层。**按你的真实反思替换**。【推导】

## 五、一句话总结

这个项目的架构主线可以概括为：**用一棵文档树（DocNode）当唯一事实来源，用 Command 收口所有操作，用可选的 Handler 契约 + 统一 reconcile 同步视图，用快照兜住撤销**——每一层都在为"编辑器产出必须可控、可序列化、所见即所得"服务。
