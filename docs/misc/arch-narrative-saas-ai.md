# 金融 SaaS 平台架构叙事：演进与 AI 工程化

::: tip 用途
面试讲述稿（3~5 分钟版）。主菜是「架构演进 + AI 辅助开发工程化」，适合 AI 全栈方向岗位。按「约束背景 → 结构性决策 → 权衡 → 结果与代价 → 追问准备」组织。**加粗内容为简历事实，其余为讲述话术，请按真实情况核对调整。**

## 一句话故事主线

> 一个金融抵押贷款 SaaS 平台，在既有系统上完成了**双层架构梳理**和**技术栈整体迁移**，并用**模板编辑器打通文档生成全链路**；同时我把架构思维用到了 AI 辅助开发上——用结构化 Prompt + YAML 工作流把 Agent 约束成"设计→规划→实现→测试→评审"的标准化流程，让 AI 协作可复现、可沉淀。

---

## 一、约束与背景（为什么做）

**项目背景：** 基于金融资产抵押贷款场景的 SaaS 平台，分 **贷前**（抵押物评估、贷款申请审批）和 **贷后**（还款管理、逾期催收、抵押资产管理、风险定级与合规追踪、数据分析报表）两大业务模块。**Forms Gallery** 是贷后独立模块，管理文档模板，支撑信贷资料补充、重新签名、客户正式信件等场景，实现文档生成流程的标准化与自动化。

**当时的困境：**

1. **旧系统结构混乱**：旧版本基于 JS + Vue + Vite + 自研组件库，业务逻辑和 UI 混在一起，新业务（贷后模块）扩展困难
2. **文档生成是手工活**：信贷资料、正式信件的模板靠开发人员逐一维护静态模板，业务人员改个措辞都要提需求排期
3. **AI 协作不可控**：用 AI 辅助开发时，Agent 经常"跳步骤"——不测试就宣布完成、方案没评审就动手，结果不可复现

**我的角色：** 高级前端开发工程师，负责核心模块设计与开发、技术架构优化。

---

## 二、结构性决策（讲清楚"为什么"）

### 决策 1：双层架构 —— 数据构建层与 UI 展示层分离

**核心决策：** 前端拆成 **数据构建层 + UI 展示层** 两层。

- **数据构建层**：负责业务数据的组装——表单 schema、文档模板的数据结构、状态管理，不关心长什么样
- **UI 展示层**：负责渲染与交互，从数据层取数，不关心数据从哪来

**为什么这么切（权衡）：**

- 金融业务表单多、规则复杂，数据结构和展示经常要各自演进（后端接口变了只改数据层，视觉改版只动展示层）
- **Forms Gallery 与模板编辑器深度集成**：模板从编辑、预览到生产环境渲染**全链路打通**——编辑器的产出（模板结构）就是生产环境的输入，双层架构让"编辑器数据"和"渲染展示"天然解耦，这是全链路能成立的前提

**这个决策的含义**：把"数据"当资产，把"UI"当消耗品——数据层可以喂给任何展示端（编辑态、预览态、生产渲染），这是架构里"契约先于实现"的典型。

### 决策 2：技术栈整体迁移 —— JS + Vue → TS + React

**决策与权衡：**

| 维度 | 旧（JS + Vue + Vite） | 新（TS + React + Vite + Zustand + 自研组件库） |
|------|----------------------|---------------------|
| 类型安全 | 弱，重构靠人肉 | TS 全量覆盖，重构有编译器兜底 |
| 状态管理 | 分散 | Zustand 轻量集中 |
| 组件体系 | 旧自研库 | 新自研组件库（对齐新设计规范） |

**为什么敢迁（架构师语言）：**

- 迁移是**渐进式**的（简历写"新版本迁移"，意味着新旧并存）——新模块用新栈，老模块按需迁移，不搞"大爆炸"
- **双层架构是迁移的底气**：数据层先迁（纯逻辑，风险低），UI 层跟随——把不可逆的大改动拆成可逆的小步骤，这是"让决策可逆"的实践
- 用 AI 辅助（Cursor）主导模块重构，显著提升重构效率

### 决策 3：AI 辅助开发的工程化框架 —— 架构思维用在 Agent 上

**这是差异化亮点，面试时要重点展开：**

**问题**：AI 协作不可控——Agent 跳步骤、不测试就宣布完成、结果不可复现，和"测试应该能过先声明完成吧"的合理化是一样的病。

**方案（对应你正在做的 harness 工程）：**

- **结构化 Prompt 约束**：把任务上下文、输出格式、质量要求结构化，减少 Agent 的自由发挥空间
- **YAML 工作流约束流程**：设计 → 规划 → 实现 → 测试 → 评审的标准化流程，每阶段有明确的输入输出，Agent 按流程执行
- **Skill 封装复用**：把高频动作（知识初始化、技术审计、状态检查点）封装成可复用技能
- **经验教训自动沉淀**：每轮任务结束自动记录经验，知识越用越多
- **多 Agent 协同编排（Agent Teams）**：多个 Agent 分工协作，用工作流编排串起来

**为什么这是架构决策**：和微前端定边界、定契约是同一套思维——**把不确定性（Agent 的自由发挥）用机制约束住，让产出可复现、可校验**。你后来做的 hook 门禁（验证证据链、阶段产出校验）就是这个框架的深化。

## 三、演进与验证（结果与代价）

**结果（简历事实）：**

- **主导 Forms Gallery 模块**需求分析与技术方案设计，从 0 到 1 开发并上线
- Forms Gallery 与自研模板编辑器深度集成，**模板编辑 → 预览 → 生产渲染全链路打通**
- 通过 AI 协作开发显著提升重构效率与交付质量
- 沉淀了 Skill 封装复用与经验教训自动沉淀的机制

**代价与踩过的坑：**

- **迁移期双栈并存**：新旧技术栈同时在跑，公共组件库要同时兼容两套——靠组件库分层 + 按模块灰度迁移解决
- **AI 输出质量波动**：同一条 Prompt 不同模型、不同上下文产出差异大——靠工作流强制阶段校验兜底（这也正是后来做 hook 门禁的动机）
- **模板与生产的对齐**：编辑器预览必须等于生产渲染，否则业务人员"所见非所得"——靠统一渲染内核解决（编辑器和生产共用同一套渲染）

**如果重来会改什么**：会把 **AI 工作流框架的"测试门禁"更早做成硬校验**——早期靠 Prompt 提醒，Agent 还是会跳，后来发现只有机制（工具 + hook）才能真正拦住。

## 四、面试追问准备

| 追问 | 回答要点 |
|------|---------|
| 迁移期间新旧并存，公共组件库怎么处理？ | 分层：基础组件（框架无关）优先统一，业务组件按模块灰度；新代码强制新栈，旧代码按需迁移 |
| 为什么选 Zustand 而不是 Redux？ | 迁移期要轻量渐进，Zustand 心智负担低、TS 支持好；Redux 的规范在双栈并存期是负担 |
| 数据构建层和 UI 展示层会不会过度设计？ | 边界来自真实痛点：表单 schema 和视觉改版频率完全不一致，分离后两边独立演进；如果业务简单就不需要 |
| 模板编辑器为什么能和 Forms Gallery 打通？ | 统一渲染内核：编辑器预览和生产渲染共用同一套渲染逻辑，编辑产出即生产输入 |
| 结构化 Prompt 和普通 Prompt 有什么区别？ | 结构化约束了角色、上下文、输出格式、质量标准，普通 Prompt 靠模型自觉 |
| YAML 工作流怎么保证 Agent 不跳步骤？ | 每阶段有输入输出契约 + 阶段校验；后来升级为工具 + hook 门禁（验证证据链）——软约束变硬约束 |
| AI 辅助开发最大的坑是什么？ | 假完成（说测试过了其实没跑）；对策是证据链：测试报告必须附真实执行记录 |
| 你怎么看"AI 会取代架构师"？ | AI 擅长在约束内生成方案，但"定义约束"（边界、权衡、取舍）是人的活——架构决策的难点从来不是找答案，而是定问题 |
