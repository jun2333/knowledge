# 客服平台架构叙事：一次微前端架构决策

::: tip 用途
面试讲述稿（3~5 分钟版）。按「约束背景 → 结构性决策 → 权衡 → 结果与代价 → 追问准备」组织，可作为回答"你做过哪些架构决策 / 讲一个你主导的项目"的主线。**加粗内容为简历事实，其余为讲述话术，请按真实情况核对调整。**
:::

## 一句话故事主线

> 一个客服场景碎片化、多业务线各自为战的公司，我用**微前端架构 + 工程化体系**把 5+ 个子应用整合进统一平台，让多团队能并行交付、独立发布，连续两年获得集团项目评比奖项。

---

## 一、约束与背景（为什么做）

**项目背景：** 面向全公司的客服场景通用解决方案，由 **ARK（B 端客服工作台）、IM（C 端在线客服）、知识库配置平台、质量管理平台、后台管理系统**等多个子系统组成，还有集成了操作台基座、组件库、通信库、权限系统和 SSO 的业务操作中台 **BBC**。

**当时的困境（讲述重点，要讲"痛"）：**

1. 多个客服业务线各自为战：每个子系统技术形态、发布节奏、账号体系都不一样，用户（客服人员）要在多个系统间来回切换
2. 新业务接入成本高：每来一条客服业务线，都要重复搭建框架、接入权限、做导航
3. 团队协作效率低：公共能力（组件、通信、权限）没有沉淀，各系统重复造轮子
4. 没法统一运营：质检、知识库、IM 的数据和入口是割裂的

**我的角色：** 客服中台前端 Leader，负责架构设计、团队管理与跨团队协调。

---

## 二、结构性决策（讲清楚"为什么"）

### 决策 1：统一平台用什么形态 —— 为什么选微前端

**候选方案与权衡：**

| 方案 | 优点 | 代价 | 结论 |
|------|------|------|------|
| 把所有子系统合并成一个大应用 | 简单，共享彻底 | 多团队同时改一个仓库，发布互相踩，回归爆炸 | 否 |
| iframe 嵌套 | 隔离最彻底，接入最快 | 体验割裂（无过渡动画、刷新丢状态）、通信靠 postMessage 很弱、SEO 无解 | 否 |
| **Qiankun 微前端** | **独立开发、独立部署、渐进改造，子应用技术栈不受限** | 沙箱/路由/通信有学习成本，公共依赖要治理 | ✅ |

**决策依据（架构师语言）**：约束是多条业务线要并行交付、发布节奏不同、存量系统不能推翻重来——**微前端是唯一同时满足"渐进改造"和"独立部署"的方案**。选 Qiankun 而不是自研，是因为核心矛盾在业务整合而非框架创新，生态成熟度值得押注。

### 决策 2：边界怎么划 —— 基座与子应用的职责

**核心原则：按业务域切子应用，基座只留"平台能力"。**

- **ARK 作为主应用**：承载导航、登录态、权限、路由分发——所有子应用共享的平台能力
- **各子应用自治**：ARK、IM、知识库、质检、后台管理各管各的业务页面和状态
- **BBC（业务操作中台）**：把操作台基座、组件库、通信库、权限、SSO 沉淀为**公共层**——新业务线接入时不再重复实现

**这个边界决策的含义**：子应用内部怎么实现是各团队的自由，但"接入基座要遵守什么契约"是平台定的。**边界定在"平台能力 vs 业务能力"之间**——业务永远不碰平台内部，平台永远不掺和业务逻辑。

### 决策 3：契约怎么定 —— 子应用之间的"法律"

- **路由与挂载契约**：子应用暴露统一的生命周期（bootstrap / mount / unmount），基座按路由注册表加载
- **通信契约**：跨子应用场景（如 IM 会话里打开质检）走统一的通信机制，不允许多子应用直接操作对方的全局状态
- **状态边界**：全局状态只放"身份类"信息（用户、权限、SSO 令牌），业务状态各子应用内部持有
- **公共库契约**：公共组件库 + 业务组件库分层，业务组件库依赖公共组件库，反向禁止

### 决策 4：工程化体系 —— 让架构决策可复制

- **项目生成器**：新子应用一键生成，脚手架内建统一的规范、目录结构、构建配置——新团队接入时"没得选"，规范自动对齐
- **在线开发文档体系**：接入指南、契约文档、组件用法，降低不同业务线开发人员上手成本

**为什么这算架构决策**：单靠文档和口头约定，规范必然走样。**把规范固化进脚手架和组件库，是"让架构决策落地为机制"**——这跟我后来做 AI 工作流约束 Agent 是同一个思路。

## 三、演进与验证（结果与代价）

**结果（简历事实）：**

- **5+ 个子应用平稳集成**，覆盖多条客服业务线
- 新业务线接入成本显著下降（项目生成器 + 文档 + 公共库）
- **项目连续两年在集团项目评比中获奖**

**代价与踩过的坑（讲"代价"才有说服力）：**

- **公共依赖治理**：React、Antd 等公共依赖要统一版本，否则沙箱内重复加载、内存翻倍——用 external + CDN 或统一 npm 版本策略解决
- **联调复杂度上升**：跨子应用场景需要基座统一环境才能联调，后来通过路由配置支持本地子应用 + 远程基座解决
- **沙箱边界问题**：个别老代码绕过沙箱直接操作全局变量，靠代码评审 + 沙箱策略收紧兜底

**如果重来会改什么（收尾升华）**：会**更早地把"接入契约"文档化并做成脚手架**——早期靠人肉对齐，后期才发现规范化越早越省。

## 四、面试追问准备

| 追问 | 回答要点 |
|------|---------|
| 为什么不用 iframe？ | iframe 隔离强但体验割裂、通信弱；Qiankun 沙箱 + 通信机制在"整合体验"和"隔离"之间更平衡 |
| 沙箱隔离的原理是什么？ | JS 沙箱（快照 / Proxy）+ CSS 隔离（scoped）；讲清楚 Proxy 劫持全局对象即可，不用背源码 |
| 公共库升级怎么不炸子应用？ | 契约分层：公共组件库 semver + 升级前全量回归；破坏性变更走灰度（先升级非核心子应用） |
| 子应用间怎么共享状态？ | 尽量不共享；身份类信息放基座全局，业务状态各自持有；确有跨应用场景走通信机制而非直接改全局 |
| 微前端的缺点你踩过哪些？ | 依赖治理、联调复杂度、沙箱边界——讲上面的"代价"部分 |
| 现在回头看，微前端是必须的吗？ | 诚实回答：如果团队只有一个，巨石应用可能更划算；微前端的收益来自"多团队独立交付"，没有这个约束就不该上 |
| 你和"画架构图的人"有什么区别？ | 架构落地为机制：生成器、组件库、契约文档，而不是 PPT |
