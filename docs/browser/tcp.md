## 三次握手
1. 客户端向服务器发起SYN连接请求SYN=1，同时发送序列号seq=x；客户端进入SYN_SEND状态
2. 服务端收到客户端的SYN连接请求后，也回应SYN=1，同时返回seq=y和ack=x+1；服务器进入SYN_RECV状态
3. 客户端收到服务端的响应之后进入ESTABLISHED状态；同时发送ACK=1,ack=y+1,seq=x+1给服务端，后面服务端收到也进入ESTABLISHED状态;连接建立成功!

### 为啥是三次握手，而不是两次或者四次
首先明确的是两次握手是最基本的，这样客户端才知道服务端收到了自己发出的连接请求
为什么需要三次，是为了防止由于网络或者其他原因导致一些失效的连接请求后面被发送到了服务器，若是两次握手的话，服务器会立马连接，然后等待客服端发送数据，而客服端都不会用到这条连接了，所以造成了服务器资源的浪费。这就是三次握手的必要性~
至于四次五次那就有些浪费了...

### 若已经建立好的连接，但是客服端出现了故障怎么办
TCP连接有保活机制，有个计时器，到时间后会探测客服端是否正常运行；若多次长时间没响应就会关闭释放连接，并不会造成浪费。

## 四次挥手
四次挥手发生在连接断开阶段：
1. 客户端向服务器发起断开连接请求：FIN=1,seq=u；进入到FIN-WAIT-1状态
2. 服务器收到之后回应客户端收到信息：ACK=1,seq=v,ack=u+1；进入到CLOSE-WAIT(关闭等待)状态。客户端收到之后进入FIN-WAIT-2阶段，等待服务端回应释放连接信号
3. 服务端发送完最后的数据之后向客户端发起断开连接响应：FIN=1,seq=w,ack=u+1；进入LAST-ACK(最后确认)状态
4. 客户端收到服务器的连接释放报文后，向服务端发出确认应答，报文头：ACK=1，ack=w+1，seq=u+1，此时，客户端就进入了TIME-WAIT（时间等待）状态。该状态会持续 2MSL（最长报文段寿命）时间，这个期间 TCP 连接还未释放，若该时间段内没有服务端的重发请求的话，客户端就进入 CLOSED 状态，服务端只要收到了客户端发出的确认，立即进入 CLOSED 状态。就结束了这次的 TCP 连接。可以看到，服务器结束 TCP 连接的时间要比客户端早一些。

### 为啥断开连接不能三次挥手搞定，非要四次？
服务器收到客户端的FIN请求之后，有些收尾工作，如还有需要传输给客户端的数据，或者一些途中数据发到服务端，这些都需要收尾
所以ACK和FIN会分开发，多了一次挥手

### 为什么客户端最后还要等待 2MSL？
MSL 最大分段寿命（Maximum Segment Lifetime），是一个 TCP 分段可以存在于互联网系统中的最大时间。TCP 允许不同的实现可以设置不同的MSL值。

第一，保证客户端发送的最后一个 ACK 报文能够到达服务器。因为这个 ACK 报文可能丢失，站在服务器的角度看来，我已经发送了FIN+ACK 报文请求断开了，客户端还没有给我回应，应该是我发送的请求断开报文它没有收到，于是服务器又会重新发送一次，而客户端就能在这个 2MSL 时间段内收到这个重传的报文，接着给出回应报文，并且会重启 2MSL 计时器。(简言之就是稍微等一下，万一服务端没收到ACK会再来要的)

第二，防止类似与 三次握手 中提到了的 已经失效的连接请求报文段 出现在本连接中。客户端发送完最后一个确认报文后，在这个 2MSL 时间中，就可以使本连接持续的时间内所产生的所有报文段都从网络中消失。这样新的连接中不会出现旧连接的请求报文
