# Islands 架构

Islands（孤岛）架构是一种前端渲染优化方案，通过**局部水合（Partial Hydration）** 提升页面性能。

## 背景：MPA vs SPA

| 特性 | MPA（多页应用） | SPA（单页应用） |
|------|----------------|----------------|
| **页面加载** | 每次切换重新请求服务器 | 首次加载，后续局部更新 |
| **路由** | 无路由概念 | 客户端路由 |
| **首屏速度** | 快（服务器直接返回 HTML） | 慢（需要下载 JS 后渲染） |
| **SEO** | ✅ 友好 | ❌ 不友好 |
| **交互体验** | 一般（页面刷新） | ✅ 流畅 |

### SSR 的问题

SSR 和 CSR 同构虽然兼顾了首屏和 SEO，但存在问题：

```
用户访问 → 服务器返回 HTML → 下载全量 JS → 全量 Hydration → 可交互
                                        ↑
                                    这里很慢！
```

**问题**：首次访问仍需下载全量 JS bundle 并全量 hydration，**TTI（可交互时间）并没有提升**，甚至不如 SPA。

**本质原因**：CSR 的渲染是一步到位的（创建 DOM + 绑定事件连贯完成），而 SSR 的 hydration 是"二次加工"——DOM 已由服务器生成，React 仍需创建虚拟 DOM 并与真实 DOM 做对比验证，再绑定事件。这个对比过程是 CSR 没有的纯额外开销，页面越大、组件越多，hydration 成本越高，TTI 劣势越明显。

**思考**：能否**局部 hydration**？将需要交互的部分和不需要交互的部分区分开来？

## Islands 架构

### 核心思想

将需要交互的**动态组件**和不需要交互的**静态组件**区分开来，让静态组件**不参与 hydration**，大大提高 hydration 速度。

```
传统 SSR：
┌─────────────────────────────────┐
│  全量 Hydration（慢）           │
─────────────────────────────────┘

Islands 架构：
┌─────────────────────────────────┐
│  静态内容（不 hydration）       │
│  ┌─────────┐   ┌─────────┐    │
│  │ Island 1│   │ Island 2│    │  ← 只有这些需要交互的组件 hydration
│  └─────────┘   └─────────┘    │
│  静态内容（不 hydration）       │
└─────────────────────────────────┘
```

需要交互的动态组件就像一座座**孤岛（Island）**，因此被称为 Islands 架构。

### 工作原理

```mermaid
graph LR
    A[服务器渲染 HTML] --> B[返回静态 HTML]
    B --> C[浏览器解析]
    C --> D[只加载 Island 组件的 JS]
    D --> E[局部 Hydration]
    E --> F[页面可交互]
```

**关键**：静态组件只输出 HTML，不输出 JS；Island 组件才输出 JS 并 hydration。

## Islands 实践：Astro

### 什么是 Astro

Astro 是一个基于 Islands 架构的静态站点生成器（SSG），默认所有组件都是静态的，需要显式声明 Island 组件。

### 核心特性

| 特性 | 说明 |
|------|------|
| **Islands 架构** | 默认静态，按需 hydration |
| **框架无关** | 支持 Vue、React、Svelte 等 |
| **零 JS 默认** | 静态组件不输出 JS |
| **MPA 方案** | 不支持 SPA 路由和状态管理 |

### 使用示例

```astro
---
// 页面组件（静态，不 hydration）
import Header from '../components/Header.astro';
import Counter from '../components/Counter.jsx';
---

<html>
  <body>
    <Header />  <!-- 静态，不加载 JS -->
    
    <!-- Island 组件，需要交互 -->
    <Counter client:load />
    
    <footer>静态内容</footer>
  </body>
</html>
```

**Island 声明方式**：

```astro
<!-- 立即加载 -->
<Counter client:load />

<!-- 可见时加载 -->
<Counter client:visible />

<!-- 空闲时加载 -->
<Counter client:idle />

<!-- 媒体查询加载 -->
<Counter client:media="(max-width: 50em)" />

<!-- 仅客户端渲染（不 SSR） -->
<Counter client:only="react" />
```

### Astro 的优势

1. **Islands 架构**：解决传统 SSR/SSG 的全量 hydration 问题，JS 开销最小化（甚至 0 JS）
2. **学习成本低**：.astro 语法类似 .jsx 和 .vue
3. **使用灵活**：可在一个项目中同时使用 Vue、React 组件
4. **构建迅速**：基于 Vite 和 Esbuild，启动速度快

### 对比 React Selective Hydration

| 特性 | Astro | React Selective Hydration |
|------|-------|--------------------------|
| **框架依赖** | ✅ 框架无关 | ❌ 依赖 React |
| **JS 下载** | ✅ 只下载 Island 组件 JS | ❌ 仍需全量下载 JS bundle |
| **服务端要求** | ✅ 无特殊要求 | ❌ 需要流式渲染（chunked） |
| **成熟度** | ⚠️ 较新 | ✅ React 官方支持 |

## Islands 架构优缺点

### 优点

| 优点 | 说明 |
|------|------|
| **减少 TTI** | 传统 SSR 优势下，进一步减少可交互时间 |
| **关键内容优先** | 静态内容先展示，交互组件后加载 |
| **组件化** | 基于组件架构，复用性好 |
| **SEO 友好** | 服务器渲染完整 HTML |
| **JS 开销小** | 静态组件不输出 JS |

### 缺点

| 缺点 | 说明 |
|------|------|
| **框架生态少** | 支持 Islands 的框架较少（主要是 Astro） |
| **不适合复杂交互** | 大量交互的应用不适合（如后台管理系统） |
| **MPA 限制** | 不支持 SPA 路由和全局状态管理 |
| **学习成本** | 需要理解 Islands 概念和 hydration 策略 |

## 适用场景

| 场景 | 推荐度 | 说明 |
|------|--------|------|
| **内容型网站** | ✅ 强烈推荐 | 博客、文档、新闻站点 |
| **电商网站** | ✅ 推荐 | 商品详情页、列表页 |
| **营销页面** | ✅ 推荐 | 落地页、活动页 |
| **后台管理系统** | ❌ 不推荐 | 大量交互，适合 SPA |
| **复杂 Web 应用** | ❌ 不推荐 | 如在线编辑器、协作工具 |

## 与其他架构对比

| 架构 | 首屏 | SEO | 交互 | TTI | 适用场景 |
|------|------|-----|------|-----|---------|
| **MPA** | ✅ 快 | ✅ 好 |  差 | 中 | 简单网站 |
| **SPA** | ❌ 慢 | ❌ 差 | ✅ 好 | 慢 | 后台系统 |
| **SSR** | ✅ 快 | ✅ 好 | ✅ 好 | 中 | 通用 |
| **SSG** | ✅ 快 | ✅ 好 | ✅ 好 | 中 | 静态内容 |
| **Islands** | ✅ 快 | ✅ 好 | ✅ 好 | ✅ 快 | 内容型网站 |

## 总结

| 要点 | 说明 |
|------|------|
| **核心思想** | 静态组件不 hydration，只有 Island 组件 hydration |
| **代表框架** | Astro |
| **优势** | 减少 TTI、JS 开销小、SEO 友好 |
| **劣势** | 不适合复杂交互应用 |
| **适用场景** | 内容型网站、电商、营销页面 |
