# 数据分布场景与锁设计（单库 / 主从 / 分片 / 分布式库）

> **优先级：P1** — 面试与架构里最容易被绕晕的一组概念：多实例、主从、分库分表、分布式数据库——它们的数据存放方式不同，"锁/一致/并发"的问题也完全不同。本文用一张地基图分清四种形态，逐个讲"数据和锁怎么设计"。

## 一、地基：数据分布的四种形态（先分清，别混）

```
① 单库（多应用实例共享）  ：一份数据，所有实例连同一个 MySQL
② 主从复制 / 读写分离     ：同一份数据"多副本"，主库写、从库读
③ 分库分表                ：数据"切片"分散，每个库存一部分（不同数据）
④ 分布式数据库（TiDB）    ：数据切片 + 每片多副本，底层封装成"一个库"
```

**最容易混的两个**：
- ② 主从 = **同一份数据**多副本（每台都是全量）
- ③ 分库 = **不同数据**分散（每台存一部分）

| 形态 | 数据是"切"还是"复制" | 一致性 | 扩展方向 |
|------|---------------------|--------|---------|
| ① 单库 | 一份 | 强一致（DB 保证） | 加应用实例（水平） |
| ② 主从 | **复制**（全量副本） | 最终一致（异步复制） | **读**扩展 |
| ③ 分片 | **切分**（各存部分） | 各片独立（跨片要分布式事务） | 写 + 读扩展 |
| ④ TiDB | 切分 + 副本 | 底层封装（对外像单库） | 自动扩展 |

---

## 二、场景①：多应用实例 + 单库

**数据**：一份，所有实例连同一个 MySQL。

**锁设计**：
- **数据一致性 → DB 锁**（行锁/乐观锁/原子 SQL）——共享 DB，行锁**天然跨实例**，不管几个应用实例都有效
- **代码互斥 → Redis 锁**——"定时任务只跑一次"这类**与数据行无关**的逻辑互斥，DB 管不了，用 Redis 锁（key 粒度决定并发度）

```
数据行 → DB 行锁（自动，跨实例）
代码段 → Redis 锁（自己加，跨实例）
```

**核心认知**：应用再多实例，只要共享 DB，数据一致就靠 DB；Redis 锁只补"代码互斥"这块。

## 三、场景②：主从复制 / 读写分离（最常见的部署形态）

**架构**：主库写、从库读，主库把 binlog 异步复制给从库。**主从 = 同一份数据的多个全量副本**。

### 它解决什么（并发）

```
读并发大 → 加从库（每台从库分担一部分读流量）→ 读水平扩展
写并发   → 瓶颈仍在主库（单点写）→ 主从不解决写扩展（要写扩展走分库）
```

**写一致性还在主库**：所有写都走主库，主库的行锁和单库场景一样管并发写——**从库只读，没有写并发问题**。

### 真正的难点：复制延迟导致的一致问题

主库写完，binlog 异步复制到从库——**从库会暂时落后**：

```
用户下单 → 写主库成功 → 跳转订单页 → 读的是从库 → 可能还没复制到 → "订单不存在"？
```

**主从是"最终一致"**：从库迟早追上，但追上之前的窗口内，读到的是旧数据。

### 解决策略（不是加锁！是复制与路由策略）

| 手段 | 做法 | 解决 |
|------|------|------|
| **半同步复制** | 写主库时**等至少一个从库 ACK 才返回成功** | 缩小延迟窗口（从"毫秒级不确定"到"至少一个从库确认"） |
| **关键读走主库** | 刚写过的数据（如自己的订单）路由到主库读 | 避免"写后读不到自己写的数据" |
| **读从库容忍延迟** | 报表/列表这类可接受最终一致的读从库 | 榨干从库读能力 |
| **复制延迟监控** | 监控主从落后秒数，超阈值告警/切主读 | 别让延迟悄悄放大 |

```
写 → 主库（行锁保证写一致）→ 半同步等从库确认 → 返回成功
读关键数据 → 主库（要读到刚写的）
读可容忍数据 → 从库（可能旧几毫秒/秒，最终一致）
```

**关键认知**：主从的一致风险来自**复制延迟**（时序问题），**不是并发写冲突**（写都集中主库、按行锁串行）。所以"锁"在这里**不解决一致**——一致靠复制策略（半同步/路由）。**这是主从和单库场景最大的思维差异：单库靠锁，主从靠复制策略**。

### 主从切换的坑（顺带）

主库宕机切从库时，可能丢"还没复制过去的写"——半同步 + GTID 定位可减少损失。**主从是容灾 + 读扩展方案，不是数据零丢失方案**（强零丢失得靠分布式 DB/同步复制）。

## 四、场景③：分库分表（数据切片）

**数据**：按**分片键**（如 user_id、order_id）切到多个库，每库只存一部分。

### 锁设计核心：让锁"局部化"

```
同一条数据 → 只在一个分片里 → 行锁在该分片自动生效（和单库一样）
跨分片的操作 → 一次改多个库的数据 → 需要分布式事务（代价大）
```

**所以分片键设计是最高优先级的"锁设计"**——让需要一起操作的数据落在同一分片：

```
❌ 订单按 user_id 分片，但"订单 + 订单明细 + 该订单库存扣减"散在不同片 → 跨片事务
✅ 让"一个订单的聚合"同片 → 单分片内行锁局部有效，无需跨库协调
```

### 分片后的配套问题

| 问题 | 方案 |
|------|------|
| 自增主键失效（各片独立自增会撞） | **分布式 ID**（雪花：时间戳+机器+序号） |
| 跨分片事务 | 分布式事务（2PC/TCC/Saga，能避免就避免） |
| 跨库无唯一约束 | 幂等表 / Redis 幂等记录 |
| 热点分片（某 key 特别热） | 拆 key（加后缀分散）/ 本地缓存 |

**判断准则**：**能局部锁就别跨节点**——分片键设计的目标是让 90% 操作落在单片内（局部行锁），只有极少数跨片才付分布式事务的代价。

## 五、场景④：分布式数据库（TiDB / CockroachDB，了解一下）

**本质**：分片（Region）+ 每片多副本（Raft 共识）+ 分布式事务（TiDB 用 Google Percolator 模型）——**全部封装在存储层**，对外是一个 MySQL 兼容的库。

```
你写：UPDATE stock SET stock=stock-1 WHERE id=1
底层：找到 id 所在 Region → 多副本 Raft 达成一致 → 行锁/MVCC 内部协调
```

**对应用透明**：行锁、事务隔离级别和单库一样，**不需要你设计锁/分片/副本**——数据库全包了。

**代价**：引入运维复杂度（TiDB 集群本身要管）、强一致写有跨节点协调开销。适用：**单库扛不住又不愿自己搞分库分表的团队**。

---

## 六、对照总结（学透这张表就够了）

| 场景 | 数据形态 | 写一致靠 | 读扩展 | 写扩展 | 你要"设计"的 |
|------|---------|---------|--------|--------|-------------|
| ① 多实例单库 | 一份 | **DB 行锁** | 加实例 | 加实例（受单库上限） | Redis 锁管代码互斥 |
| ② 主从 | 全量多副本 | 主库行锁 + **复制策略** | **加从库** | ❌（主库单点） | 半同步/读写路由/延迟监控 |
| ③ 分片 | 各存部分 | 片内行锁 + 跨片事务 | 加片 | 加片 | **分片键**/分布式ID/幂等 |
| ④ TiDB | 切片+副本 | **内部封装** | 自动 | 自动 | 基本不用 |

**贯穿主线一句话**：**能局部锁就别跨节点**——单库靠 DB 行锁，主从靠复制策略（不是锁），分片靠分片键让锁局部化，分布式库靠底层封装。
