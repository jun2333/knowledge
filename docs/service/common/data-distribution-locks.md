# 数据分布场景与锁设计（单库 / 主从 / 分片 / 分布式库）

> 本质一句话：**数据怎么摆，决定了锁在哪生效**。单库靠 DB 行锁、主从靠复制策略、分片靠分片键让锁局部化、分布式库靠底层封装——**四个场景，四套完全不同的"一致性武器"**。

**优先级 P1**：面试与架构里最容易被绕晕的一组概念：多实例、主从、分库分表、分布式数据库——它们的数据存放方式不同，"锁 / 一致 / 并发"的问题也完全不同。

::: tip 这篇的定位
这篇是**一张地图 + 一条主线**，不是每个方案的实现细节。目的是让你在面试和架构评审里**不被绕进去**：别人说"我们上了分库分表"，你能立刻说出"那你们的跨片事务怎么办"。

四个形态的实现细节分别见：[MySQL 进阶](/service/common/mysql-advanced)（主从）、[分布式基础](/service/common/distributed-basics)（CAP、分布式事务、分布式 ID）、[并发锁应用](/service/common/concurrency-locks)（锁本身）。
:::

## 1. 用途：什么时候会走到这些形态

> 难度：了解

### 1.1 演进触发点

**不是"数据大了就分片"，是每种形态解决一个特定瓶颈**：

```text
① 单库
   瓶颈：应用实例多了 → 数据库连接数不够 → 加应用实例（水平扩展）
   ↓ 读流量压垮单库
② 主从（读写分离）
   瓶颈：写还是单点 → 但读已经扩展不动了
   ↓ 单表真的到亿级
③ 分库分表
   瓶颈：写扩展 + 单表索引效率
   ↓ 不想自己搞分片、跨片事务、分布式 ID
④ 分布式数据库（TiDB / CockroachDB）
```

**每一步都是"用新复杂度换旧瓶颈"**，所以**不该跳级**——单库能扛的就不上主从，主从能扛的就不分片。

### 1.2 什么时候该考虑从①往上走

| 症状 | 目标形态 | 先做什么 |
|---|---|---|
| 读 QPS 压顶，**写还不高** | ② 主从 | 加从库 + 读写路由 |
| 单表索引变慢（千万级） | ③ 分片（按业务维度） | 先优化索引和慢查询 |
| 写 QPS 压顶（单机写不动） | ③ 分片 / ④ 分布式库 | 先做库表拆分设计 |
| **运维能力不足** | 停在 ① 或 ② | 别上③④，TiDB 集群本身也要人管 |

**最后一行很重要**：分布式数据库不是"更简单的数据库"，它是**把复杂度从你转移到运维团队**的产品。没有能人管 TiDB 集群的团队，上 TiDB 只是把数据库问题换成集群问题。

## 2. 最小可用：一条 SQL 在四种形态下

> 难度：了解

**场景**：扣减商品库存，防止超卖。

```sql
UPDATE stock SET stock = stock - 1 WHERE sku_id = 100 AND stock > 0;
```

**同一条 SQL，四种形态下含义完全不同**：

| 形态 | 这条 SQL 打在哪个库 | 谁能同时执行 | 一致性靠什么 |
|---|---|---|---|
| **① 单库** | 主库（唯一） | 所有实例的这条 SQL → **DB 行锁串行** | DB 行锁 + 事务 |
| **② 主从** | **必须是主库** | 同上（写都在主库） | 主库行锁 + **复制策略**（读从库有延迟） |
| **③ 分片** | `sku_id` 哈希到的那个分片 | 只有**同一个分片**内的请求会互斥 | 片内行锁；跨片要分布式事务 |
| **④ TiDB** | 逻辑上"一个库" | 全局由存储层协调 | 内部 Region + Raft，**对应用透明** |

**三个立刻能得出的结论**：

1. **② 主从下，写操作必须走主库**——写到从库就废了（从库是只读副本）。
2. **③ 分片下，"防超卖"只在分片内成立**——如果库存和订单在不同分片，"扣库存 + 建订单"就是跨片事务。
3. **④ TiDB 下这条 SQL 不用改**——它对外就是一个 MySQL 兼容库。

> **自检**：分库分表后，`UPDATE stock ... WHERE sku_id = 100` 这条 SQL 的执行范围是什么？多个应用实例同时下同一单会怎样？

::: details 参考答案
**执行范围**：只落在 `sku_id=100` 哈希到的**那一个分片**（假设按 sku_id 分片）。其他分片完全不参与。

**多实例同时下同一单**：
- **同一个 sku_id** → 同一个分片 → **分片内的 DB 行锁**（或 MVCC 下的原子更新）保证串行 → `AND stock > 0` 这个条件让只有一个请求成功，**不会超卖**。这和单库完全一样。
- **不同 sku_id** → 不同分片 → 各走各的，**天然并行**，互不阻塞。

所以"分片后锁还有效吗"这个问题，答案是：**对同一分片的数据有效（局部锁），对跨分片的数据无效（要分布式事务）**。

**这正是分片键设计的意义**：让需要互斥的数据落在同一片。如果库存按 sku_id 分片、订单按 order_id 分片，那"扣库存 + 建订单"就跨片了，每次下单都要走分布式事务——代价极高。
:::

## 3. 用法：四种形态各自的"一致性武器"

> 难度：会用

### 3.1 场景①：多应用实例 + 单库

**数据**：一份，所有实例连同一个 MySQL。

**锁设计分两类，不要混**：

```text
数据行 → DB 行锁（自动，跨实例）
代码段 → Redis 锁（自己加，跨实例）
```

| 要互斥的东西 | 用什么 | 为什么 |
|---|---|---|
| **数据行**（同一行的更新） | **DB 行锁 / 乐观锁 / 原子 SQL** | 共享同一个 DB，行锁**天然跨实例**——不管你部署几个应用实例都有效 |
| **与数据行无关的逻辑**（定时任务只跑一次、同一用户只能发一封邮件） | **Redis 锁** | DB 管不了"代码段互斥"，只能自己加锁 |

**核心认知**：应用再多实例，只要共享 DB，**数据一致就靠 DB**；Redis 锁只补"代码互斥"这块。**能用 DB 约束解决的，别用 Redis 锁**（唯一索引比分布式锁可靠，见 [Redis 入门 · 分布式锁的边界](/service/common/redis-intro)）。

### 3.2 场景②：主从 / 读写分离

**架构**：主库写、从库读，主库把 binlog **异步**复制给从库。**主从 = 同一份数据的多个全量副本。**

**它解决什么**：

```text
读并发大 → 加从库（每台分担一部分读流量）→ 读水平扩展 ✓
写并发   → 瓶颈仍在主库（单点写）→ 主从不解决写扩展 ✗
```

**写一致性仍然在主库**：所有写都走主库，主库的行锁和单库场景一样管并发写——**从库只读，没有写并发问题**。

**真正的难点：复制延迟**

```text
用户下单 → 写主库成功 → 跳转订单页 → 读的是从库
         → 从库可能还没复制到 → "订单不存在"？
```

**主从是"最终一致"**：从库迟早追上，但追上之前的窗口内读到的是旧数据。

**解决策略（不是加锁！是复制与路由策略）**：

| 手段 | 做法 | 解决 |
|---|---|---|
| **半同步复制** | 写主库时**等至少一个从库 ACK 才返回成功** | 缩小延迟窗口（从"毫秒级不确定"到"至少一个从库确认"） |
| **关键读走主库** | 刚写过的数据（自己的订单）路由到主库读 | 避免"写后读不到自己写的数据" |
| **读从库容忍延迟** | 报表/列表这类可接受最终一致的读从库 | 榨干从库读能力 |
| **复制延迟监控** | 监控主从落后秒数，超阈值告警或切主读 | 别让延迟悄悄放大 |

```text
写 → 主库（行锁保证写一致）→ 半同步等从库确认 → 返回成功
读关键数据 → 主库（要读到刚写的）
读可容忍数据 → 从库（可能旧几毫秒/秒，最终一致）
```

**主从切换的坑**：主库宕机切从库时，可能丢"还没复制过去的写"——半同步 + GTID 可减少损失。**主从是容灾 + 读扩展方案，不是数据零丢失方案**（强零丢失得靠同步复制或分布式 DB）。

### 3.3 场景③：分库分表（数据切片）

**数据**：按**分片键**（如 user_id、order_id）切到多个库，每库只存一部分。

**锁设计核心：让锁"局部化"**

```text
同一条数据 → 只在一个分片里 → 行锁在该分片自动生效（和单库一样）
跨分片的操作 → 一次改多个库的数据 → 需要分布式事务（代价大）
```

**所以分片键设计是最高优先级的"锁设计"**——让需要一起操作的数据落在同一分片：

```text
❌ 订单按 user_id 分片，但"订单 + 订单明细 + 扣库存"散在不同片 → 跨片事务
✅ 让"一个订单的聚合"同片 → 单分片内行锁局部有效，无需跨库协调
```

**分片后的配套问题**：

| 问题 | 方案 |
|---|---|
| 自增主键失效（各片独立自增会撞） | **分布式 ID**（雪花：时间戳+机器+序列号） |
| 跨分片事务 | 分布式事务（2PC / TCC / Saga，**能避免就避免**） |
| 跨库无唯一约束 | 幂等表 / 幂等状态机 |
| 热点分片（某 key 特别热） | 拆 key（加后缀分散）/ 本地缓存 |
| 跨片查询（分页、聚合） | 慢；要么改数据模型让查询单片，要么做二次查询 + 应用层聚合 |

**判断准则**：**能局部锁就别跨节点**——分片键设计的目标是让 **90% 的操作落在单片内**（用局部行锁），只有极少数跨片才付分布式事务的代价。

**分片键的四个要求**（设计时的检查清单）：

| 要求 | 原因 |
|---|---|
| **数据要均匀** | 否则热点分片（某个大客户 / 某个爆款 key）压垮一片 |
| **查询要集中** | 常用查询条件要能带上分片键，否则每次都跨片 |
| **事务要内聚** | 一个事务要改的数据必须在同一片 |
| **要稳定** | 分片键不能变（用户 ID 不能变；用自增 ID 的话，扩容时按 ID 取模会错位） |

### 3.4 场景④：分布式数据库（TiDB / CockroachDB）

**本质**：分片（Region）+ 每片多副本（Raft 共识）+ 分布式事务（TiDB 用 Percolator 模型）——**全部封装在存储层**，对外是一个 MySQL 兼容的库。

```text
你写：UPDATE stock SET stock=stock-1 WHERE id=1
底层：找到 id 所在 Region → 多副本 Raft 达成一致 → 行锁/MVCC 内部协调
```

**对应用透明**：行锁、事务隔离级别和单库一样，**不需要你设计锁 / 分片 / 副本**——数据库全包了。

**代价**：

- **运维复杂度**：TiDB 集群本身要人管（PD、TiKV、TiDB 三种角色）
- **强一致写有跨节点协调开销**：比单机自增慢（但比你自己搞分片简单得多）
- **SQL 能力有边界**：某些 MySQL 语法和 DDL 不完全兼容

**适用**：**单库扛不住又不愿自己搞分库分表的团队**。

## 4. 原理：为什么主从的一致不靠锁

> 难度：懂原理

这是本篇**最值得记住的一条思维差异**。

### 4.1 单库场景：一致性 = 锁的问题

```text
多个实例同时改同一行
  → 都打到同一个 DB
    → DB 的行锁把它们串行化
      → 一致
```

**这里的风险是"并发写冲突"**，所以用锁解决。

### 4.2 主从场景：一致性 = 时序的问题

```text
多个实例同时改同一行
  → 都打到主库
    → 主库行锁串行化 ✓（并发写没问题）

但读的时候：
  → 读请求打到从库
    → 从库还没收到 binlog → 读到旧值 ❌
```

**这里的风险不是"并发写冲突"，而是"读到的数据比写的旧"**——是**时序问题**，不是并发问题。

**所以加锁解决不了它**。锁能保证"写是串行的"，但保证不了"从库已经追上主库"。**唯一的武器是复制策略**：

| 策略 | 怎么解决时序问题 |
|---|---|
| 半同步复制 | 让主库**等**从库确认 → 把"不确定的延迟窗口"变成"确定的最小延迟" |
| 读写路由 | 让关键读走主库 → **绕开**延迟窗口 |
| 延迟监控 | 知道窗口有多大 → 超阈值就切主读 |

**一句话**：**单库靠锁，主从靠复制策略。** 把这两套东西混了，就会得出"给读请求加个分布式锁"这种荒谬结论。

### 4.3 分片场景：一致性 = 局部性问题

```text
同分片的数据 → 行锁有效（和单库一样）
跨分片的数据 → 需要协调（分布式事务）
```

**所以分片键设计是最高优先级**——它决定了 90% 的操作能不能用上"局部行锁"这个免费的武器。

### 4.4 分布式库：一致性 = 存储层的事

```text
你写一条普通 SQL
  → 存储层找到数据所在 Region
    → 该 Region 的多个副本用 Raft 达成一致
      → 对外表现为"一个普通的 MySQL 事务"
```

**应用层什么都不用设计**——代价是这套机制本身很重（每条写都要跨节点共识）。

### 4.5 四种形态的统一视角

| 形态 | 一致性的**风险来源** | 对应的武器 |
|---|---|---|
| ① 单库 | 并发写冲突 | **DB 行锁** |
| ② 主从 | **复制延迟**（时序） | **复制策略**（不是锁！） |
| ③ 分片 | **跨片协调** | **分片键**（让锁局部化） |
| ④ 分布式库 | 节点间共识 | **存储层封装** |

## 5. 边界与坑

> 难度：会用 + 懂原理

### 5.1 一张表先过一遍

| 症状 | 见 |
|---|---|
| 写完立刻查，查不到自己写的数据 | 5.2 |
| 加了从库但读流量没降 | 5.3 |
| 分片后某个接口特别慢 | 5.4 |
| 分片扩容后数据"错位"了 | 5.5 |
| 主从切换后丢了数据 | 5.6 |
| 说"我们上了分布式库"但说不清代价 | 5.7 |

### 5.2 写完立刻读不到自己写的数据

**症状**：下单成功，跳转订单页显示"订单不存在"。

**原因**：**复制延迟**（4.2）——写主库成功就返回了，从库还没复制到。

**解法**（按场景选）：

| 场景 | 解法 |
|---|---|
| 用户读自己的数据（订单详情） | **关键读走主库**（按用户 ID 路由到主库） |
| 列表/报表类读 | 容忍延迟，读从库 |
| 延迟已经很大 | 开半同步复制；检查是否有大事务 / 大批量操作卡住复制 |
| 写后必须立刻读 | **别用主从**，用单库或分布式数据库的强一致读 |

**排查顺序**：先确认是不是读走了从库（看日志/链路里连的是哪个实例）→ 再看主从延迟秒数（`SHOW SLAVE STATUS` 的 `Seconds_Behind_Master`）→ 延迟正常但仍读不到 → 检查路由规则。

### 5.3 加了从库但读流量没降

**症状**：加了两台从库，流量还是全打主库。

**原因与对策**：

| 原因 | 解法 |
|---|---|
| **读路由没配**（还是全走主库） | 配读写分离（ShardingSphere / ProxySQL / 应用层自己路由） |
| **写后马上查的比例高** | 关键读走主库是合理的，但要看比例 |
| **从库延迟太高**，被自动摘除 | 查复制延迟；解决后再挂回 |
| **业务代码里直连了主库**（硬编码数据源） | 改数据源路由 |

### 5.4 分片后某个接口特别慢

**症状**：大部分接口正常，某个列表接口从 50ms 变成 5s。

**原因**：**跨片查询**。比如分页要按 `create_time` 排序，而分片键是 `user_id` → 每个分片都要取一部分再归并排序 → N 个分片 × 排序 → 慢。

**解法**（按优先级）：

| 方案 | 说明 |
|---|---|
| **改数据模型** | 加冗余字段（如"用户最近 N 条订单"单独存一张表） |
| **改分片键** | 让这个查询能带上分片键（代价大，慎重） |
| **应用层归并** | 各分片查一部分 → 应用层合并排序（数据量大时仍慢，且有深分页问题） |
| **换成 ES** | 搜索类查询交给搜索层 |

**根本教训**：**分片键决定了哪些查询会慢**。设计分片键时，必须拿实际的查询列表去套一遍——"这个查询能带上分片键吗"。

### 5.5 分片扩容后数据"错位"

**症状**：分片从 2 个扩到 4 个后，一半的数据查不到了。

**原因**：**取模分片的经典问题**——`hash(key) % N`，N 从 2 变 4 → **几乎所有 key 的归属都变了**。

**解法**：

| 方案 | 说明 |
|---|---|
| **一致性哈希**（+ 虚拟节点） | 节点增减只影响少量 key（见 [分布式基础](/service/common/distributed-basics)） |
| **按范围分片**（比如按 ID 区间） | 扩容是"新增一个区间"，老数据不动 |
| **预分片**（一开始就分 1024 个逻辑分片，物理上按需分配） | 扩容只是把逻辑分片挪到新机器，**映射不变** |
| **双写迁移** | 扩容期间新旧路由同时写、逐步搬数据（最重但最通用） |

**这是分库分表最不可逆的决策**——分片键和分片算法定了，改起来要停机搬数据。

### 5.6 主从切换后丢了数据

**症状**：主库宕机切从库后，最近几秒的写入不见了。

**原因**：**异步复制**——主库写完就返回了，还没复制到从库就宕机 → 那些写入在从库上根本不存在。

**解法**：

| 方案 | 说明 |
|---|---|
| **半同步复制** | 主库等至少一个从库 ACK → 丢数据窗口从"不确定"变成"最多丢一点"（但主库变慢） |
| **GTID + 选主时比对** | 切主时检查各从库的复制位点，选丢失最少的 |
| **强一致方案** | Group Replication / 同机房同步复制 / 分布式数据库 |

**认知**：**主从是容灾 + 读扩展方案，不是数据零丢失方案**。要求"零丢失"就得接受延迟和成本上升。

### 5.7 "我们上了分布式数据库"——该追问什么

**别急着接受这个说法**。三个问题问过去就知道对方是真懂还是跟风：

| 追问 | 想知道什么 |
|---|---|
| **"强一致的写有多高的延迟？"** | 跨节点共识的开销。正常单库 1ms，分布式可能 5~50ms |
| **"TiDB 集群谁来管？半夜挂了谁处理？"** | **运维归属**——这是最大的坑 |
| **"MySQL 语法完全兼容吗？哪些不兼容？"** | 迁移成本；DDL、索引、外键都有差异 |

**如果对方答不上来**，那大概率是"业务方没真正用起来，只是接了个中间件"。**分布式数据库的价值是省掉分片设计的活，代价是运维复杂度上升**——前提是团队真的有能力运维。

> **自检**：一个团队说"我们数据量大所以用了分库分表"。你会追问哪三件事来确认这个决定是对的？

::: details 参考答案
我会问三件事：

**① "数据量到底多大？单表多少行？"**
分库分表的常见触发点是**单表超过 1000 万行**（索引深度变大、DDL 变慢、备份恢复变久）。如果实际只有几百万行，**分片的复杂度（分布式 ID、跨片事务、跨片查询）完全不值得**——加索引、优化 SQL、读写分离可能就够了。这一条最容易被跳过，因为"数据量大"是模糊的说法。

**② "分了之后，这个列表接口的 SQL 还能带上分片键吗？"**
如果不能，**每次列表查询都要跨片归并** → 分片后反而更慢。分片键要和主要查询条件对齐，这是设计的第一原则。

**③ "跨片事务现在怎么处理的？业务里还有哪些操作是跨片的？"**
如果答案含糊（比如"用分布式事务框架"），要追问**用的是哪种方案、代码里怎么写的**。跨片事务是分片后最大的复杂度来源，**设计上应该尽量避免**（通过分片键让 90% 操作落在单片内）。

**补充问一句**："扩容过吗？扩容方案是什么？"——回答"没扩过"或"停机迁移"都是可接受的答案，但如果对方从没想过，说明这个决定是"跟风做的"而不是"算出来的"。
:::

## 6. 延伸

> 难度：了解

### 对照总结（学透这张表就够了）

| 场景 | 数据形态 | 写一致靠 | 读扩展 | 写扩展 | 你要"设计"的 |
|------|---------|---------|--------|--------|-------------|
| ① 多实例单库 | 一份 | **DB 行锁** | 加实例 | 加实例（受单库上限） | Redis 锁管代码互斥 |
| ② 主从 | 全量多副本 | 主库行锁 + **复制策略** | **加从库** | ❌（主库单点） | 半同步 / 读写路由 / 延迟监控 |
| ③ 分片 | 各存部分 | 片内行锁 + 跨片事务 | 加片 | 加片 | **分片键** / 分布式 ID / 幂等 |
| ④ TiDB | 切片 + 副本 | **内部封装** | 自动 | 自动 | 基本不用 |

**贯穿主线一句话**：**能局部锁就别跨节点**——单库靠 DB 行锁，主从靠复制策略（不是锁），分片靠分片键让锁局部化，分布式库靠底层封装。
