# JVM 入门

> **优先级：P0（面试必考）** — JVM 与并发并称 Java 面试两大护城河，几乎必问。

::: tip 背景
JS 开发者不需要关心 V8 内存细节也能干活；但 Java 面试会把 JVM 内存模型、GC、类加载当基础题问。本文聚焦面试考点，不深入源码。
:::

## JVM 是什么

Java 程序运行在 JVM（Java Virtual Machine）上：`.java` 编译为 `.class` 字节码，JVM 解释/编译执行。**一次编译，到处运行** 靠的就是 JVM 屏蔽了操作系统差异。

```
.java --javac--> .class --JVM--> 机器码
```

## 内存分区（必考，画图题）

```
┌─────────────────────────────────────┐
│ 线程共享                              │
│  ┌──────────┬──────────┬──────────┐  │
│  │  堆 Heap  │ 方法区/元空间 │  直接内存 │  │
│  │ (对象实例) │ (类信息/常量) │ (NIO)    │  │
│  └──────────┴──────────┴──────────┘  │
├─────────────────────────────────────┤
│ 线程私有                              │
│  ┌──────────┬──────────┬──────────┐  │
│  │ 虚拟机栈    │ 本地方法栈 │ 程序计数器 │  │
│  │ (方法调用) │ (native) │ (下一条指令)│  │
│  └──────────┴──────────┴──────────┘  │
└─────────────────────────────────────┘
```

| 区域 | 存什么 | 线程 | 异常 |
|------|--------|------|------|
| **堆** | 所有对象实例、数组 | 共享 | `OutOfMemoryError: Java heap space` |
| **方法区/元空间** | 类信息、常量、静态变量（JDK 8+ 用元空间，本地内存） | 共享 | `OOM: Metaspace` |
| **虚拟机栈** | 每个方法一个栈帧（局部变量、操作数栈） | 私有 | `StackOverflowError`（递归过深） |
| **程序计数器** | 当前执行指令地址 | 私有 | 无 |
| **直接内存** | NIO 的堆外内存 | 共享 | `OOM: Direct buffer memory` |

**JDK 8 变化**：永久代（PermGen）→ 元空间（Metaspace），从堆内移到了本地内存，不再有 PermGen OOM。

## JIT：JVM 为什么比解释执行快

`.class` 字节码不是机器码，JVM 有两种执行方式：

```
解释执行：逐行翻译字节码 → 启动快，跑得慢
JIT 编译（Just-In-Time）：把"热点代码"整段编译成机器码 → 启动稍慢，跑得飞快
```

**分层编译**（面试常考）：方法先解释执行，调用够频繁后升级为 C1（快速编译）→ 继续热 → C2（深度优化编译，榨干性能）。

### 逃逸分析：JIT 的杀手锏优化

JIT 分析对象的作用域，如果发现一个对象**不会逃出方法外**（没有 return、没被别的线程拿到），就做激进优化：

| 优化 | 做什么 |
|------|--------|
| **栈上分配** | 对象直接在栈上创建，方法结束自动回收，**不经过 GC** |
| **标量替换** | 对象拆成一个个字段用局部变量存，连"对象"都不存在了 |
| **锁消除** | 发现同步锁的对象其实是线程私有的，锁直接删掉 |

```java
// 这个 User 对象没人拿到方法外 —— JIT 可能把它优化成"栈上三个局部变量"
public void handle() {
    User u = new User("tom");      // 逃逸分析：u 没逃逸 → 栈上分配，零 GC 压力
    System.out.println(u.getName());
}
```

**前端对照**：JS 引擎（V8）也有同款——JIT + 逃逸分析 + 内联缓存。Java 和 JS 的"快"殊途同归：都是"热点代码编译成机器码 + 对象生命周期优化"。

## 垃圾回收（GC）

### 判断对象可回收

- **引用计数法**（早期）：循环引用问题，已弃用
- **可达性分析**（现用）：从 GC Roots 出发遍历，不可达即垃圾。GC Roots 包括：栈帧局部变量、静态变量、JNI 引用、活跃线程

### 回收算法

| 算法 | 思路 | 缺点 |
|------|------|------|
| **标记-清除** | 标记垃圾后直接清除 | 内存碎片 |
| **标记-复制** | 存活对象复制到另一半区域 | 浪费一半空间；适合"存活少"（新生代） |
| **标记-整理** | 存活对象移到一端，清掉其余 | 移动成本高；适合"存活多"（老年代） |

### 分代收集

```
新生代（复制算法，Minor GC 频繁）
├── Eden（新对象）
└── Survivor S0 / S1（幸存者，年龄 +1，15 岁进老年代）
老年代（标记-整理/标记-清除，Major GC）
```

**为什么分代**：绝大多数对象朝生夕灭（如方法里的临时对象），新生代用复制算法性价比最高。

### 常见收集器（面试答 G1 即可）

| 收集器 | 特点 |
|--------|------|
| **G1**（JDK 9+ 默认） | 分 Region 管理堆，可预测停顿时间（`-XX:MaxGCPauseMillis`），JDK 17 默认 |
| ZGC | JDK 15+，超低停顿（毫秒级），适合超大堆 |
| CMS | 老牌并发收集器，已废弃（JDK 14+ 移除） |

G1 一句话：**把堆分成多个 Region，优先回收垃圾最多的 Region**（Garbage First 名字由来）。

## 类加载机制

### 生命周期

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
```

- **加载**：读 .class 文件生成 Class 对象
- **验证**：字节码安全校验
- **准备**：静态变量赋默认值（0 / null）
- **解析**：符号引用 → 直接引用
- **初始化**：执行静态代码块、静态变量赋真实值

### 双亲委派模型（必考）

```
启动类加载器 Bootstrap（rt.jar，JDK 核心类）
  ↑ 委托
扩展类加载器 Platform（JDK 扩展类）
  ↑ 委托
应用类加载器 App（classpath 下的类）
```

**流程**：类加载请求 → 先问父加载器能不能加载 → 父都不行才自己加载。

**为什么这样设计**：保证核心类安全——你的代码无法覆盖 `java.lang.String`，避免污染 JDK 核心类（核心类始终由 Bootstrap 加载）。

**打破双亲委派**：SPI（JDBC 等）用线程上下文类加载器，Tomcat 也打破了（每个应用隔离）。

## JVM 调优与排查（面试基础）

常用参数：

```
-Xms256m -Xmx256m        # 堆初始/最大（生产建议相等，避免扩容抖动）
-Xss512k                 # 每个线程栈大小
-XX:MaxMetaspaceSize     # 元空间上限
-XX:+HeapDumpOnOutOfMemoryError   # OOM 时自动 dump
```

排查命令（详见 [线上问题排查](/service/troubleshooting)）：

```
jps       # 查看 Java 进程
jstack    # 线程栈（查死锁、线程状态）
jmap      # 堆快照（查 OOM 对象）
jstat     # 查看 GC 频率与耗时
```

### GC 日志怎么读（调优的基本功）

生产环境开 GC 日志（JDK 9+ 语法见《Java 服务部署》），一次 Minor GC 长这样：

```
[2026-10-13T11:00:02.123+0800][info][gc] GC(42) Pause Young (Normal) (G1 Evacuation Pause)
  GC(42) Eden regions: 24->0(32)
  GC(42) Survivor regions: 2->3(4)
  GC(42) Pause Young (Normal) 38M->12M(256M) 8.512ms
```

抓三个数就够：

| 看什么 | 健康值 | 异常信号 |
|--------|--------|---------|
| **停顿时间**（Pause ... 8.512ms） | < 200ms | 频繁超 1s → 停顿敏感业务不可接受 |
| **GC 频率**（GC(42) 编号涨得快） | Minor GC 分钟级 | 秒级一次 → 分配速率过高或堆太小 |
| **GC 后堆占用**（38M→12M） | 回落后保持平稳 | 每次 GC 后水位持续抬高 → **有泄漏趋势** |

**最常见的调优动作**（面试常考"你怎么调 JVM"）：不是改算法，是**改堆大小和 GC 器**——`-Xms=-Xmx`（消除伸缩抖动）→ 堆给到物理内存的 60~70%（留 30% 给堆外）→ 仍停顿超标的低延迟业务换 ZGC。

### OOM / 内存泄漏排查三步法

**现象**：`java.lang.OutOfMemoryError: Java heap space`（堆溢出）或更隐蔽的——进程内存天天涨、过几天被 OOMKilled。

```
① 保留现场：-XX:+HeapDumpOnOutOfMemoryError 自动 dump（没配就 jmap -dump:live,format=b 手动抓）
② 分析 dump：用 MAT（Eclipse Memory Analyzer）或 IDEA 打开
   → 看 Dominator Tree：谁占了最大内存？
   → 看 Leak Suspects：MAT 自动报告的可疑泄漏点
③ 定位代码：典型嫌疑人——
   · static 集合只加不减（"缓存"越攒越大）
   · ThreadLocal 没 remove（线程池复用场景，见《Java 并发》）
   · 连接/流没关（try-with-resources 没包住）
   · 大对象进缓存（一次把整个表 load 进 Map）
```

**排查顺序的黄金法则**：先看"对象数量是不是异常多"（代码 bug 加了不该加的），再看"单个对象是不是异常大"（一次加载太多数据），别一上来就调堆——堆调大只是让"到达 OOM 的时间变长"，不治病。

## 面试题速查

| 问题 | 一句话答案 |
|------|-----------|
| 堆和栈的区别 | 堆存对象（共享）、栈存调用帧（私有）；堆要 GC、栈随方法退出自动释放 |
| 什么是 OOM | 堆/元空间/直接内存耗尽的 `OutOfMemoryError` |
| 什么是 StackOverflow | 栈深度超限，递归没出口 |
| GC 判断对象死亡的算法 | 可达性分析（GC Roots） |
| 新生代为什么用复制算法 | 存活少，复制成本低、无碎片 |
| G1 和 CMS 区别 | G1 分 Region、可预测停顿；CMS 已废弃 |
| 双亲委派是什么 | 子加载器先委托父加载器，保证核心类不被覆盖 |
| 什么时候触发 Full GC | 老年代空间不足、元空间不足、System.gc() |
| 什么是 JIT | 热点代码运行时编译成机器码，分层编译 C1→C2 |
| 逃逸分析能做什么优化 | 栈上分配、标量替换、锁消除——对象不逃出方法就免 GC |
| 怎么判断 GC 健康 | 看停顿时间、GC 频率、GC 后水位是否持续抬高 |
| OOM 排查三步 | dump 现场（HeapDumpOnOutOfMemoryError）→ MAT 分析 Dominator Tree → 查代码嫌疑人（static 集合/ThreadLocal/未关流） |
| 调优第一步做什么 | 统一 -Xms=-Xmx 消除伸缩抖动，再考虑堆大小和 GC 器选择 |
