# 分布式基础（CAP / 分布式事务 / 分布式 ID）

> **优先级：P1（中高级岗必问）** — 单机 → 分布式时才会遇到的问题。面试常考概念题：CAP、分布式事务方案、分布式 ID 方案。

::: tip 背景
你已有微前端、BFF、权限设计经验（分布式系统的应用层），本文补理论层：分布式为什么难、一致性怎么权衡、事务跨库怎么做。
:::

## 为什么分布式难

单机系统：事务、锁、一致性由数据库/OS 保证。多机后：

- 一个事务跨多个库 → 没有全局事务管理器
- 一台机器挂 → 数据在哪？请求谁来接？
- 时钟不同步、网络可能延迟/丢包/分区

核心矛盾：**网络是不可靠的**。所有分布式难题都源于此。

## CAP 理论（必考）

| 字母 | 含义 |
|------|------|
| C（Consistency） | 一致性：所有节点同时看到同一份数据 |
| A（Availability） | 可用性：任何请求都有响应 |
| P（Partition tolerance） | 分区容错：网络分区（节点失联）时系统仍工作 |

**定理**：网络分区必然发生（P 必选），所以只能在 C 和 A 之间二选一：

- **CP 系统**：分区时拒绝服务保证一致（ZooKeeper、etcd、HBase）
- **AP 系统**：分区时继续服务，允许短暂不一致（Eureka、Cassandra、绝大多数业务系统）

**业务系统的实际答案**：平时一致，分区时选 A（可用性），通过**最终一致性**（消息队列、异步补偿）补 C。

**面试题**：MySQL 主从是 CP 还是 AP？——AP + 最终一致：主从有延迟，从库可能读到旧数据，但最终同步。

## BASE 理论（CAP 的落地方案）

- **Basically Available**：基本可用（降级、限流也算）
- **Soft state**：软状态（允许中间状态，如"支付中"）
- **Eventually consistent**：最终一致（异步同步到一致）

## 分布式事务（必考，选一种讲透）

跨库/跨服务事务，常见方案：

| 方案 | 思路 | 优缺点 |
|------|------|--------|
| **2PC（两阶段提交）** | 协调者先问所有参与者"能提交吗"（准备），全同意才提交（提交） | 强一致但**阻塞**（协调者挂了全卡住）、性能差 |
| **TCC** | Try（预留资源）→ Confirm（确认）→ Cancel（回滚），业务自己实现三方法 | 性能好，但**业务侵入大**（每个方法写三份逻辑） |
| **本地消息表** | 事务内写业务 + 消息表同库提交；后台定时扫消息表发 MQ；消费者幂等 | 简单可靠，业界常用（RocketMQ 事务消息即此思想的封装） |
| **Saga** | 长事务拆多个本地事务 + 补偿（逆操作） | 无锁高性能，但**无隔离性**（中间状态可见） |

**面试建议**：把**本地消息表**讲透（原理 + 代码结构），再提 TCC 是"最终一致性场景的强一致性变体"。别每个都讲一半。

```
本地消息表流程：
业务事务（订单库）: 写订单 + 写消息表（status=待发送） → 同库事务，要么都成要么都败
后台任务: 扫描待发送消息 → 发 MQ → 标记已发送
消费者: 消费 + 幂等（防止重复）
```

## 分布式 ID（必考）

| 方案 | 原理 | 特点 |
|------|------|------|
| UUID | 全局唯一字符串 | 无序、太长、影响索引性能 |
| 数据库自增 | 单点自增 | 简单但单点、性能低 |
| **雪花算法（Snowflake）** | 64 位：时间戳(41) + 机器 ID(10) + 序列号(12) | **业界主流**：趋势递增、无依赖、高性能 |
| Redis INCR | 原子自增 | 依赖 Redis 可用性 |

**雪花算法 64 位结构**（面试画图）：

```
0 | 41位时间戳（毫秒）| 10位机器ID | 12位序列号
符号位   ~69年（可自定纪元）    每毫秒4096个
```

**注意**：依赖机器时钟，时钟回拨会生成重复 ID（解决：回拨时等待/用备用机器号）。

## 分布式理论其他高频点

| 考点 | 要点 |
|------|------|
| 一致性哈希 | 节点增减只影响少量 key 的映射（环 + 虚拟节点），用于缓存集群路由 |
| 脑裂 | 集群分区后出现两个"主"，解决：选举需要多数派（过半机制） |
| 选举 | Raft/Paxos：多数派同意才提交，ZooKeeper/etcd 都用 |
| 限流 | 计数器 / 滑动窗口 / 令牌桶（Guava RateLimiter）/ 漏桶 |
| 熔断降级 | 失败率超阈值熔断（Sentinel/Hystrix），见微服务篇 |

## 面试题速查

| 问题 | 一句话答案 |
|------|-----------|
| CAP 是什么 | 一致性/可用性/分区容错三选二；分区必选，实际是一致性与可用性二选一 |
| CP 和 AP 例子 | ZooKeeper=CP；Eureka=AP；业务系统=AP+最终一致 |
| BASE 是什么 | 基本可用 + 软状态 + 最终一致 |
| 分布式事务方案 | 2PC（阻塞）/ TCC（侵入大）/ 本地消息表（常用）/ Saga（无隔离） |
| 雪花算法 | 时间戳+机器ID+序列号，趋势递增，防时钟回拨 |
| 一致性哈希 | 环映射 + 虚拟节点，节点变动影响最小化 |
