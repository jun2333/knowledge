# Redis 入门

> **优先级：P0（面试必考）** — 缓存三兄弟（穿透/击穿/雪崩）+ 持久化 + 分布式锁是后端面试固定节目。

::: tip 背景
Redis 是后端缓存的事实标准，面试题高度模板化。本文按面试考频组织：数据结构 → 缓存问题 → 持久化 → 分布式锁 → 其他高频点。
:::

## Redis 是什么

内存数据库（In-Memory Database）：数据在内存，单线程执行命令（6.0 后网络 IO 多线程，命令执行仍单线程），因此**单个命令原子**。用途：缓存、分布式锁、计数器、排行榜、消息发布订阅。

**为什么快**：内存访问（~100ns）+ 单线程无锁竞争 + IO 多路复用 + 高效数据结构。

## 五种基础数据结构（必背）

| 类型 | 底层 | 典型场景 |
|------|------|---------|
| **String** | SDS | 缓存对象（JSON 字符串）、计数器（`INCR`）、分布式锁 |
| **Hash** | 哈希表 | 存对象字段（用户信息），`HGETALL` |
| **List** | 双向链表 | 消息队列（`LPUSH`/`RPOP`）、最新列表 |
| **Set** | 哈希表 | 去重、抽奖、**交集/并集**（共同好友） |
| **ZSet** | 跳表 + 哈希 | **排行榜**（score 排序）、延时队列 |

**面试题**：ZSet 底层为什么用跳表？——有序链表 + 多级索引，插入/查找 O(log n)，比红黑树实现简单，且区间查询高效（树的中序遍历也能做，但跳表实现更简单直观）。

## 缓存三大问题（必考）

### 缓存穿透

**现象**：查询**不存在的数据**，缓存没有 → 每次都打到数据库（攻击者可构造不存在的 id）。

**解决**：
1. **缓存空值**：查不到也缓存 `null`（设置短过期时间）
2. **布隆过滤器**：请求先过布隆，不存在直接拦截（内存省，有误判率）

### 缓存击穿

**现象**：某个**热点 key 过期**的瞬间，大量请求同时打到数据库（并发重建缓存）。

**解决**：
1. **互斥锁**：只允许一个线程重建缓存，其他线程等待/拿旧值
2. **逻辑过期**：key 永不过期，value 里存过期时间，异步刷新（牺牲一致性换性能）

### 缓存雪崩

**现象**：**大量 key 同时过期**（或 Redis 宕机），请求全部打到数据库。

**解决**：
1. 过期时间**加随机值**（基础时间 + 随机数，避免同时过期）
2. 热点数据不过期（逻辑过期）
3. Redis 高可用：主从 + 哨兵/集群，防止单点
4. 服务端兜底：限流降级，DB 保护

**面试答题结构**：穿透=查不存在（空值/布隆）｜击穿=单个热点过期（互斥锁/逻辑过期）｜雪崩=大量同时过期（随机过期时间/高可用）。三者别混。

## 持久化：RDB vs AOF（必考）

| | RDB（快照） | AOF（追加日志） |
|--|------------|----------------|
| 机制 | 定期把内存全量快照到磁盘 | 每个写命令追加到日志文件 |
| 恢复速度 | 快（直接加载） | 慢（重放命令） |
| 数据安全性 | 可能丢最后一次快照后的数据 | 按 `appendfsync` 策略（everysec 丢 1s） |
| 文件大小 | 小 | 大（可重写压缩） |
| 实际使用 | **两者都开**：RDB 兜底恢复 + AOF 保证数据 | |

**面试题**：Redis 重启恢复顺序？——先 AOF（数据更全），AOF 不存在/关闭才用 RDB。

## 分布式锁（必考）

多实例（微服务）下 `synchronized` 失效（锁只在单进程内），需要跨进程锁：

```java
// 加锁：SETNX 保证原子
SET lock_key unique_value NX PX 30000
// NX: 不存在才设置；PX: 过期时间（防止死锁）；unique_value: 防止误删别人的锁

// 释放：必须用 Lua 保证"判断是自己的锁 + 删除"两步原子
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**为什么释放锁要 Lua 脚本**：先 GET 判断再 DEL 是两步，非原子——可能判断完还没删，锁过期了被别的线程拿到，然后你删了别人的锁。Lua 保证原子。

**Redisson**（Java 客户端）内置了看门狗（自动续期）和可重入锁，生产直接用 Redisson 而不是手写。

**面试题**：分布式锁 key 过期了但业务没执行完怎么办？——看门狗机制：Redisson 默认 30s 过期，业务没完自动续期。

## 其他高频考点

| 考点 | 要点 |
|------|------|
| 过期删除策略 | **惰性删除**（访问时发现过期删）+ **定期删除**（随机抽检）组合 |
| 内存淘汰策略 | `allkeys-lru`（常用）、`volatile-lru`、`noeviction`（默认，写满报错） |
| 主从复制 | 一主多从，读写分离（主写从读），全量同步 + 增量同步 |
| 哨兵模式 | 监控主节点，挂了自动选举新主（高可用） |
| Cluster 集群 | 16384 个槽位分片，水平扩展 |
| 缓存一致性 | **先更新 DB 再删缓存**（延迟双删/最终一致）；别先删缓存再更新 DB（并发下脏数据） |

**缓存一致性面试必答**：
```
更新 DB → 删除缓存（而不是更新缓存）
原因：并发更新缓存可能写入旧值；删除让下次查询重建，天然一致
增强：先删缓存再更新 DB 有窗口期 → 延迟双删（删缓存 → 更新 DB → 等 500ms 再删一次）
```

## 面试题速查

| 问题 | 一句话答案 |
|------|-----------|
| Redis 为什么快 | 内存 + 单线程无竞争 + IO 多路复用 |
| 穿透/击穿/雪崩 | 空值+布隆 / 互斥锁+逻辑过期 / 随机过期+高可用 |
| RDB 和 AOF 区别 | 快照 vs 追加日志；RDB 恢复快丢数据多，AOF 反之 |
| 分布式锁实现 | SETNX + 过期时间 + Lua 释放；生产用 Redisson |
| 为什么单线程还快 | 瓶颈不在 CPU 在内存和网络；单线程避免锁竞争 |
| 缓存一致性方案 | 更新 DB 后删缓存 + 延迟双删 |
| 过期删除策略 | 惰性 + 定期 |
| 哨兵和集群区别 | 哨兵=高可用（主从切换），集群=分片扩展 |
