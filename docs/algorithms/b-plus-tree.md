# B+ 树

> B+ 树是数据库索引的底层结构（MySQL InnoDB 就用它）。本篇讲清楚它长什么样、为什么数据库选它；在 MySQL 里的应用（聚簇索引、回表）见 [MySQL 进阶](/service/common/mysql-advanced)。

## 一、从二叉查找树说起

你已经知道 [二叉查找树](/algorithms/bst)：左小右大，查找走一遍路径，O(log n)。但 BST 用在数据库里有两个致命问题：

1. **会退化**：按顺序插入 1、2、3、4……BST 变成一根链表，查找退化成 O(n)
2. **就算平衡了也太高**：[平衡树](/algorithms/binary-tree)（AVL/红黑树）每个节点只有 2 个孩子。100 万数据，树高约 20 层——每次查找最多 20 层

第 2 点在内存里无所谓（内存寻址纳秒级），但**数据库的数据在磁盘上，每下一层就是一次磁盘 IO**（毫秒级，比内存慢 10 万倍）。20 次 IO 查一条数据，数据库直接瘫痪。

于是有了两个方向的改良：

| 结构 | 改进 | 解决的问题 |
|------|------|-----------|
| B 树 | 一个节点存多个 key、有多个孩子（"多路"） | 树高从 20 层降到 3~4 层 |
| **B+ 树** | 数据只放叶子，非叶子纯索引；叶子用链表相连 | B 树的基础上，节点更小（IO 更赚）+ 范围查询更快 |

## 二、B+ 树长什么样

```
                [15 | 40]                    ← 根节点：只存索引，不存数据
             /      |       \
      [5 | 10]   [20 | 30 | 35]   [50 | 60 | 70]    ← 内部节点：同样只存索引
      /   |   \    /    |    \      /    |    \
 [1|3|5] [8|10|12] [18|20|22] [32|36|38] [45|48|52] [55|58|65] [72|75|80]
    叶子节点：存实际数据，且用链表从左到右相连 →→→→→→→→→→→→→→→→→→→→→
```

三个关键设计，逐个对应数据库的痛点：

| 设计 | 数据库视角的意义 |
|------|-----------------|
| **矮**（多路，一个节点几百个孩子） | 千万级数据只要 3~4 层 = 3~4 次磁盘 IO |
| **非叶子节点只存索引不存数据** | 一个节点（= 一个磁盘页 16KB）能塞更多 key，一次 IO 能"扇出"到更多分支——这是矮的直接原因 |
| **叶子节点链表相连** | 范围查询（`BETWEEN`、`>`、`ORDER BY`）走到边界后顺着链表往后扫就行，不用在树里来回跳 |

## 三、查找过程

查 22，走三趟 IO：

1. 读根节点 `[15 | 40]`：22 > 15 且 22 < 40 → 走中间子树
2. 读内部节点 `[20 | 30 | 35]`：22 落在 20~30 之间 → 走第二个叶子
3. 读叶子节点 `[18|20|22]`：找到 22

**每下一层读一个磁盘页，3~4 层就是 3~4 次 IO**——这是 B+ 树对数据库最核心的价值。

查一个**范围**（18~36）：先按查找路径定位到 18 所在的叶子，然后**顺着叶子链表往右扫**，经过 20、22、32、36，收集完事——链表遍历，不碰内部节点。

## 四、插入与分裂：B+ 树怎么保持平衡

和红黑树的"旋转"不同，B+ 树靠**分裂**：

- 新 key 先落到对应叶子；叶子没满就按序插入
- 叶子满了（约 16KB 一页）就**分裂成两半**，中间的 key **上提**到父节点作为索引
- 父节点也满了就继续往上分裂——最坏一路裂到根，树高 +1

分裂是自底向上的，不需要像红黑树那样左旋右旋调颜色。这就是为什么 MySQL 插入数据时索引结构能自动保持平衡。

## 五、算法家族对照：树这一家子

| 结构 | 孩子数 | 平衡手段 | 主场 |
|------|--------|---------|------|
| [二叉查找树](/algorithms/bst) | 2 | 无（会退化） | 教学 |
| [AVL / 红黑树](/algorithms/binary-tree) | 2 | 旋转 + 变色 | 内存（STL map、Epoll 定时器） |
| B 树 | 多 | 分裂 | 磁盘（早期数据库） |
| **B+ 树** | 多 | 分裂 | **磁盘数据库索引（MySQL）** |

规律：**内存里旋转便宜，磁盘上 IO 贵**——所以内存里的树拼命控制高度靠旋转，磁盘上的树直接增加每层的分支数（多路），用更少层数摊薄 IO。

## 面试题速查

| 问题 | 一句话答案 |
|------|-----------|
| 为什么数据库用 B+ 树不用二叉树 | 二叉树太高，磁盘 IO 次数多；B+ 树多路矮胖，3~4 次 IO 定位千万数据 |
| B+ 树和 B 树的区别 | B+ 树数据只在叶子（非叶子纯索引，节点小 IO 赚）+ 叶子链表（范围查询快） |
| 为什么 B+ 树范围查询快 | 叶子链表相连，定位到边界后顺序扫，不用回溯内部节点 |
| B+ 树怎么保持平衡 | 节点满则分裂、中间 key 上提，自底向上，不需要旋转 |
