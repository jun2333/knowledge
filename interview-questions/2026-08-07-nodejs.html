一、Node.js 核心机制（8 题） ​

1.1 事件循环机制 ​

  1. Node.js 的事件循环有哪些阶段（phase）？各阶段的作用？
  2. process.nextTick 和 setImmediate 的区别？
  3. 以下代码的输出顺序是什么？为什么？
js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
console.log('sync');

你的回答：

  1. timer(检查定时器回调是否到期)->pending callback(推迟到下一轮的I/O回调)->poll(轮询I/O回调)->check(检查setImmediate)->close(执行关闭事件回调)
  2. process.nextTick优先级比微任务高，它在每个回调执行之间执行，而setImmediate是在事件循环check阶段检查执行
  3. sync、nextTick、promise、immediate、timeout 同步代码最先执行，微任务中nextTick优先级最高，它先于Promise等微任务，随后是宏任务：immediate之所以先于timeout是因为一般定时器任务在首轮事件循环即使判断到期，但此时存在setImmediate回调，也会先执行完setImmediate，然后下一轮才执行timer回调

批改（2026-09-08）：1.1 事件循环机制 6/10

第 1 问 ✅ 阶段顺序答对(timers → pending → poll → check → close)。可补两点：阶段间还有内部阶段 idle/prepare；poll 阶段没有到期回调时会等待 I/O 事件。 第 2 问 ⚠️ 有一处概念混淆：nextTick 本身就是微任务队列，不是"比微任务高"——准确说法是它在当前操作结束后、Promise 微任务之前执行（同属 microtask，但排在 Promise.then 前面）；setImmediate 是宏任务，在 check 阶段执行。优先级：nextTick > Promise > setImmediate。 第 3 问 ⚠️ 后半段说反了。准确结论：

js
// 输出:
sync        // 同步代码
nextTick    // 微任务,先于 promise
promise     // Promise 微任务
timeout 或 immediate   // 两者顺序【不确定】!

原因：setTimeout(0) 的回调进 timers 队列，真正到期大约在启动后 ~1ms；setImmediate 进当前循环的 check 队列。事件循环第一轮先进 timers 阶段：若定时器此刻已到期就先执行 timeout，否则这一轮先到 check 执行 immediate、下一轮 timers 再执行 timeout——两者竞争，主模块顶层结果不定。 唯一确定的情况：把两者放进一个 I/O 回调（如 fs.readFile 回调）里，immediate 恒先于 timeout（I/O 回调在 poll 阶段执行，poll 之后紧跟 check）。 记忆锚点：nextTick = 每次操作结束后、同轮内最早；setImmediate = 本轮 check 阶段；两者都不等于"立即执行"。

1.2 单线程与高并发 ​

  1. 为什么说 Node.js 是单线程的？它如何支撑高并发？
  2. 事件驱动 + 非阻塞 I/O 的工作机制是什么？（libuv 线程池、IO 多路复用）
  3. Node.js 的单线程瓶颈在哪？（CPU 密集任务）什么时候需要 worker_threads / cluster？

你的回答：

  1. 因为Node.js基于V8引擎设计，只有一个线程执行js主脚本，所以是单线程；支撑高并发靠的是异步I/O和事件循环机制，异步I/O不阻塞代码执行，其回调会在事件循环中有序执行
  2. 非阻塞I/O靠的是多路复用+事件循环机制，充分利用线程的能力；而事件驱动靠的是libuv线程池，libuv负责主线程与其他线程之间的通信
  3. 涉及复杂的计算类的CPU密集型任务如果单靠主线程会影响性能，因此需要worker_threads多线程，将CPU密集型任务放到另外线程去计算，它与主线程内存共享可通过postMessage通信；cluster是多进程集群，它可以充分发挥CPU的多核性能，并发启动多个工作进程，由主进程统一进行分发请求，即负载均衡

批改（2026-09-08）：1.2 单线程与高并发 6.5/10

第 1 问 ✅ 方向对，补精确表述：单线程指 JS 执行引擎只有一个线程跑业务代码；支撑高并发不是"靠更多线程"，而是少量线程 + 事件循环 + 非阻塞 I/O，线程几乎不被阻塞，单线程也能同时服务大量连接。 第 2 问 ⚠️ 概念有点混，理清分工：

  • 网络 I/O（socket）走系统 I/O 多路复用（epoll/kqueue），不需要线程池；
  • libuv 线程池（默认 4 个线程）只处理内核没有异步接口的阻塞操作：文件系统 I/O、DNS 解析、部分 crypto、zlib；
  • libuv 不是"通信员"，它是事件循环的实现者：把异步操作完成后的回调放回主线程依次执行。 第 3 问 ✅ 基本对。小修正：worker_threads 各线程默认不共享内存，靠 postMessage 传消息；真要共享才用 SharedArrayBuffer/transferable。cluster = 多进程（内存隔离）+ 主进程分发。

  1. CommonJS是基于闭包封装的运行时模块化方案，而ES Module是ES6以后官方支持的模块化方案，它在编译过程已经做好了模块划分，性能上优于CMS
  2. 原理的细节说不清楚
  3. 因为ESM在编译阶段已经做好了模块划分，每个模块内部用到的变量或者函数都被引用了，未引用的即可删除；而CMS需要运行时才能生成模块，这时候也没法删掉没用代码了(程序都在跑了)

批改（2026-09-08）：1.3 CommonJS 与 ESM 7/10

第 1 问 ✅ 方向对，补全：CMJ 是运行时模块（require 是函数、模块文件被包装成 (function(exports, require, module, __filename, __dirname){...}) 执行）；ESM 是编译期静态模块（import/export 是语法，模块关系先于执行确定），支持静态分析优化（tree-shaking）、异步加载。CMJ 同步 require、ESM 支持顶层 await。 第 2 问（未答）参考：

  1. 路径解析：① 内置核心模块（fs、path 直接返回）→ ② 相对/绝对路径 → ③ node_modules 从当前目录逐级向上找；
  2. 扩展名补全：依次尝试 .js .json .node；目录则读 package.json 的 main，没有则取 index.js；
  3. 加载执行：包装成函数、注入 exports/require/module 执行；
  4. 缓存：模块执行后缓存进 require.cache，再次 require 直接返回缓存的 module.exports；
  5. 循环依赖：A→B→A 时，B 里 require 到的 A 是"加载到一半的 A"，只拿到 A 已执行完导出的部分（其余是 undefined）。 第 3 问 ✅ 理解对：ESM 导入导出是语法、可静态分析 → 未用导出可安全剔除；CMJ 的 require 是运行时函数调用（甚至可以 if(x) require(y) 动态拼路径）→ 编译器无法静态判断"谁被用到"，只能全保留。

批改（2026-09-08）：1.4 Buffer 4/10

第 1 问 ⚠️ 知道 Buffer 是二进制类型，但"为什么需要"没说清。补关键点：JS 字符串是 UTF-16 编码，不适合也不能高效处理二进制数据（文件、网络包、图片、加密结果都是字节流）；Buffer = V8 堆外分配的原始内存，读写不走 GC 管理的字符串。 第 2 问（未答，且 TypedArray 是常见盲区）参考：

// Buffer → 字符串

buf.toString("hex");               // 16 进制
buf.toString("base64");
// 常见编码:utf8 / utf16le / latin1 / base64 / hex / ascii

1.5 Stream 流 ​

  1. Stream 是什么？有哪些类型（Readable / Writable / Duplex / Transform）？
  2. 为什么读取大文件要用流而不是 fs.readFile？
  3. pipe 的原理？什么是背压（backpressure）？

你的回答：

  1. 专门处理连续数据的核心抽象，Readable(可读流) / Writable(可写流) / Duplex(双工流) / Transform(转换流)
  2. 大文件用流分块处理不用占用太多内存，它就像水流一样流过内存，用fs读大文件占用大量内存
  3. 不知道

批改（2026-09-08）：1.5 Stream 流 5.5/10

第 1 问 ✅ 四类答对，各补一句场景：Readable 读数据源（文件、网络）；Writable 写目的地；Duplex 双工（net.Socket）；Transform 转换（zlib 压缩、crypto 加密——读的同时写、数据被改）。 第 2 问 ✅ 对：readFile 一次把整个文件读进内存；流按 chunk（默认 64KB）分块处理，内存占用与文件大小无关。补充：readFile 需等整份文件就绪才能开始处理（首字节延迟高），流可边读边处理。 第 3 问（未答）参考：

  • pipe 原理：readable.pipe(writable) 内部自动 data 事件读一块写一块，处理 error/end 并暂停/恢复数据流。
  • 背压（backpressure）：生产速度 > 消费速度时内部缓冲暴涨会撑爆内存。writable.write(chunk) 返回 false 表示"写不下了"，应 readable.pause() 暂停读；等 writable 触发 drain（缓冲排空）再 resume。pipe 自动做了这套，所以流式传大文件不爆内存。
  • 手动流推荐 pipeline()（stream/promises），比 pipe 多了错误传播与自动清理，支持多段链。示例：
js
import { pipeline } from "node:stream/promises";
import { createReadStream, createWriteStream } from "node:fs";
import { createGzip } from "node:zlib";

// 一段链：读文件 → gzip 压缩 → 写文件,任一段出错会自动 reject
await pipeline(
  createReadStream("source.txt"),
  createGzip(),
  createWriteStream("source.txt.gz"),
);

// 对比 pipe 的坑:
// rs.pipe(gzip).pipe(ws) 链中某段出错时,错误不会自动向整条链传播,
// 残留的流不会自动销毁,可能悬空(文件句柄/资源泄漏)。
// pipeline 统一处理:错误传播到第一个流并销毁整条链。

记忆锚点：管道中间要压缩/加密/转换 → 用 Transform 接在 pipeline 里；pipe 能跑但生产代码一律用 pipeline。

  3. 生产环境遇到未捕获异常应该怎么处理？（记录日志 + 自动重启）

  1. 使用事件监听全局异步错误，具体异步操作用try...catch或者Promise.catch，回调写法则在回调函数里捕获错误

批改（2026-09-08）：1.6 错误处理 6/10

  1. 同步代码 → try/catch；
  2. async/await → try/catch；Promise 链 → .catch()；
  3. callback 风格 → 错误优先参数 (err, data)，回调先判 if (err)；EventEmitter 风格（http server）→ 监听 error 事件；

2.1 Express vs Koa ​

  1. Express 和 Koa 的主要区别？
  2. 为什么说 Koa 的洋葱模型更利于写中间件？（async/await 支持）
  3. 你更推荐哪个？为什么？（可结合你项目中使用的 Koa）

你的回答：

  1. Express不是洋葱模型，而是线型中间件模型，并且配套比较齐全；而Koa的中间件是洋葱模型
  2. 因为控制的更细，就像spring boot的切面技术一样，能用一个中间件将进入和退出的逻辑都涵盖
  3. 我推荐Express，因为目前还是主流，并且开箱即用，包括nest.js底层都是基于Express

批改（2026-09-08）：2.1 Express vs Koa 6.5/10

第 1 问 ⚠️ 结论对，但"Express 不是洋葱是线性"的措辞会被追问。更准确：

  • Koa：中间件是 async 函数，await next() 天然支持"进入后再回来" → 完整洋葱；
  • Express：中间件本质是回调串，next() 只负责往下推，想在 next 后写回程逻辑很别扭 → 习惯称线性/串行（理论也能实现洋葱，但非一等公民）。 另可补：Express 自带路由模板、生态全；Koa 内核极简（洋葱 + ctx），功能靠中间件拼。 第 2 问 ✅ 对，补例：日志/计时/错误处理都能包住后续：
js
async function logger(ctx, next) {
  const start = Date.now();
  await next();                    // 请求进去……
  console.log(ctx.status, Date.now() - start);  // 响应回来再记耗时
}

function compose(middlewares) {
  return function (ctx) {
    let curIndex = -1 // 当前层级
    function dispatch(i) {
      if(i <= curIndex) {
        return Promise.reject('next recalled')
      }
      curIndex = i
      const fn = middlewares[i]
      if(!fn) return Promise.resolve()
      try{
        return Promise.resolve(fn(ctx, ()=>dispatch(i+1)))
      }catch(err){
        return Promise.reject(err)
      }
    }
    return dispatch(0)
  }
}

class TokenBucket {

    this.capacity = capacity
    this.rate = rate
    this.tokens = capacity
    this.lastRefill = Date.now()
  }
  refill() {
    const now = Data.now()
    const elapsed = (now - this.lastRefill) / 1000
    if(elapsed > 0) {
      this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.rate)
      this.lastRefill = now
    }
  }
  tryTake(n = 1) {
    this.refill()
    if(this.tokens > n) {
      this.tokens -= n
      return true
    }
    return false
  }
  async take(n = 1) {
    for(;;) {
      this.refill()
      if(this.tokens > n) {
        this.tokens -= n
        return true
      }
      const waitMs = Math.ceil((n - this.tokens) / this.rate * 1000) // 向上取整，多等也比少等好
      await new Promise(r => setTimeout(r, waitMs))
    }
  }

// ========== ① 更好的 key：稳定序列化（属性顺序无关 + 循环引用安全） ==========
function stableStringify(value, seen = new WeakSet()) {
  if (value === null) return 'null'
  const t = typeof value
  if (t === 'number' || t === 'boolean') return String(value)
  if (t === 'string') return JSON.stringify(value)
  if (t === 'undefined') return 'undefined'
  if (t === 'function') return '[fn]'            // 函数用占位，不丢位置
  if (t === 'symbol') return value.toString()
  if (t === 'bigint') return value.toString() + 'n'

  if (seen.has(value)) return '[circular]'       // 循环引用：标记而非抛错
  seen.add(value)

  if (Array.isArray(value)) {
    return '[' + value.map((v) => stableStringify(v, seen)).join(',') + ']'
  }
  if (value instanceof Date) return 'Date:' + value.getTime()
  if (value instanceof Map) {
    return 'Map:{' + [...value.entries()]
      .map(([k, v]) => stableStringify(k, seen) + ':' + stableStringify(v, seen))
      .sort().join(',') + '}'
  }
  if (value instanceof Set) {
    return 'Set:{' + [...value].map((v) => stableStringify(v, seen)).sort().join(',') + '}'
  }
  // 普通对象：key 排序 → 顺序无关
  return '{' + Object.keys(value).sort()
    .map((k) => JSON.stringify(k) + ':' + stableStringify(value[k], seen))
    .join(',') + '}'
}

    const v = args[0]
    if (v === null || (typeof v !== 'object' && typeof v !== 'function')) return String(v)
  }
  return stableStringify(args)
}

// ========== ③ 完整实现 ==========
function memoizeWithTTL(fn, options = {}) {
  const {
    ttl = 60000,
    maxSize = 100,
    timeout = 0,                 // Promise 超时（0 = 不限）
    keyFn = defaultKey,
  } = options

  const cache = new Map()

  function memoized(...args) {
    const key = keyFn(args)
    const now = Date.now()
    const hit = cache.get(key)

    if (hit && now < hit.expireAt) {            // 命中
      cache.delete(key); cache.set(key, hit)    // LRU 提权
      return hit.value
    }

    let value = fn.apply(this, args)

    if (value instanceof Promise) {
      if (timeout > 0) value = withTimeout(value, timeout)   // 加超时
      value.catch(() => cache.delete(key))                   // 失败/超时都清缓存
    }

    cache.set(key, { value, expireAt: now + ttl })
    if (cache.size > maxSize) cache.delete(cache.keys().next().value)

    return value
  }

  // ===== 手动失效 =====
  memoized.delete = (...args) => cache.delete(keyFn(args))
  memoized.clear = () => cache.clear()
  Object.defineProperty(memoized, 'size', { get: () => cache.size })

  return memoized
}

4缓存 Promise 本身 ⭐并发调同一参数会共享同一个 Promise → 只发一次请求（防缓存击穿）
5失败清除缓存 ⭐否则一次网络抖动，错误结果会被缓存整个 ttl
6LRU 容量上限Map 保持插入顺序，cache.keys().next().value 就是最旧的 key

实测验证：

① 同参数调 3 次              → 执行 1 次     ✅ 命中缓存
② 150ms 后再调(ttl=100)      → 执行 2 次     ✅ 过期后重算
③ 不同参数                   → 各自独立缓存
④ 并发 3 次同参数             → 执行 1 次     ✅ 共享同一个 Promise(防击穿)
⑤ 异步失败后重调              → 执行 2 次     ✅ 错误没被缓存
⑥ this 绑定                  → 15           ✅ apply(this)
⑦ 容量上限 2 塞 3 个          → 最早的被淘汰后重算

增强部分:
⑧ {a:1,b:2} vs {b:2,a:1}     → 执行 1 次     ✅ 稳定 key(顺序无关)
⑨ 循环引用参数                → 不抛错        ✅
⑩ Promise 超时(50ms)         → 抛错 + 清缓存,重调重新执行 ✅
⑪ size / delete / clear      → 2 → 1 → 0    ✅ 手动失效
⑫ 自定义 keyFn(同 id 不同对象)→ 命中同一缓存  ✅

面试追问准备：

追问回答要点
JSON.stringify(args) 做 key 有什么坑？属性顺序敏感（{a:1,b:2} ≠ {b:2,a:1}）；undefined/函数/Symbol 会丢失；循环引用会抛错 → 严格场景应支持传入自定义 keyFn
过期的 key 不删会内存泄漏吗？会（长尾 key 多时）。三种解法：① 惰性删除（本实现）② 定时清理 ③ 容量上限 + LRU（本实现同时用了 ①③）
缓存 Promise 有什么风险？若 Promise 一直 pending（请求挂住），后续调用会一起挂住 → 要给 fn 加超时（Promise.race + 定时器）
多实例 / 多进程怎么办？进程内缓存不共享 → 多实例要用 Redis（SET key value EX ttl）
怎么支持手动失效？在返回的函数上挂 clear() / delete(...args) 方法

一句话总结：核心是 Map + expireAt 时间戳 + 惰性判断；加分项是"缓存 Promise"（防击穿）和"失败清除"——这两点能区分"背过题"和"真用过"。

class MyPromise {
  constructor(executor) {
    this.state = 'pending'
    this.callbacks = []
    this.value = null

    const resolve = (val) => this.#transition('fulfilled', val)
    const reject = (val) => this.#transition('rejected', val)
    
  }
  #transition(state, value) {
    if(this.state !== 'pending') return // 状态不可逆
    this.state = state
    this.value = value
    queueMicroTask(() => this.callbacks.forEach(cb => cb(this)))
  }
  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      // 最关键的设计
      const callback = (promise) => {
        try {
          const fn = promise.state === 'fulfilled' ? onFulfilled : onRejected
          const result = fn ? fn(promise.value) : promise.value
          result instanceof MyPromise ? result.then(resolve, reject) : resolve(result)
        } catch (err) {
          reject(err)
        }
      }
      this.state === 'pending' ? this.callbacks.push(callback) : callback(this)
    })
  }
  catch(onRejected) {
    return this.then(null, cb)
  }
  static resolve(val){
    return new MyPromise((resolve) => resolve(val))
  }
  static reject(val){
    return new MyPromise((_, reject) => reject(val))
  }
}
