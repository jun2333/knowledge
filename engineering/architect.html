什么是架构师 ​

面试重要性

⭐⭐⭐⭐ 面试常问"你理解的架构师是什么"或"你做过哪些架构决策"。这篇文章给出可复述的定义框架，并拆开前端、后端两种语境。

本文定位

回答三个问题：架构师是什么、做什么、怎么想。前端与后端的架构师面对的问题域不同，分开阐述；最后对比两者的核心矛盾差异。

一、一句话定义 ​

架构师不是职位头衔，而是一种决策角色：在约束条件（成本、时间、团队、技术栈）下，做影响范围大、事后难改的结构性决策的人。

判断标准不是"你叫什么"，而是你做的决策符不符合三个特征：

特征说明反例
结构性决定模块边界、数据流、接口契约，而不是某个函数怎么写封装一个工具函数不算
影响面大跨模块、跨团队、跨项目阶段只影响一个文件的改动不算
难回退错了要动骨架，改动成本高改一行配置就能回退的不算

所以"架构师"和"高级开发"的区别不在资历，而在决策粒度：高级开发解决复杂问题，架构师解决会扩散、会演化的问题。

二、架构师做什么（通用） ​

所有领域的架构师，日常都在做这五类事：

1. 定边界 ​

回答"这个能力归谁管"。典型问题：

  • 这个逻辑放前端还是后端？（BFF 的诞生）
  • 支付状态机谁推进、谁只读？
  • 这个公共组件归业务组还是基建组维护？

边界定的好，团队可以并行开发；边界乱了，一个需求要跨三个模块改。

2. 定契约 ​

边界确定后，用接口把它固化下来：API 字段、事件结构、存储模型、组件 props。契约的意义在于：双方只要遵守契约，内部怎么改都不影响对方。所以契约的演进（加字段、弃用、版本化）是架构师的核心工作。

3. 做权衡 ​

架构没有最优解，只有在当前约束下损失最小的解。每次选型背后都是一串取舍：

  • 用微前端还是巨石应用？——独立部署 vs 复杂度
  • 用强一致还是最终一致？——正确性 vs 可用性
  • 用 SSR 还是 CSR？——首屏体验 vs 成本

选型本身不值钱，把取舍讲清楚才值钱——因为取舍决定了下一次变化的代价。

4. 留演进余地 ​

架构师要回答"以后怎么改"：扩展点画在哪、哪些决策故意做成可逆的、哪些地方现在不做将来会痛。不是预测未来，而是让不确定的部分变化代价最小。

5. 让决策可逆 ​

好的架构决策大多可逆：加一个适配层、抽一个接口，错了能换。不可逆的决策（选了某种存储、绑死某个平台）要尽可能推迟到信息最充分的时刻。"晚一点做不可逆的决定"本身就是架构手段。

三、前端架构师：考虑的问题 ​

前端架构师在浏览器/客户端这个受限环境里做决策。和"页面好不好看"无关，他关心的是以下问题：

1. 性能与体验 ​

前端架构最大的约束是用户的设备与网络不可控：

  • 首屏时间：JS 包怎么拆（路由级分包、按需加载）、资源怎么缓存（HTTP 缓存策略、ServiceWorker）
  • 渲染性能：列表虚拟化、避免重渲染、长任务切分（requestIdleCallback / 时间切片）
  • 体验指标：FCP / LCP / INP 哪些能改、哪些是上线前就要定的基线

前端架构师要把"性能"变成工程机制而不是"优化技巧"：预算（bundle size 超了 CI 报警）、自动化的性能监控、变更即回归的压测。

2. 工程化与协作 ​

多人协作下代码怎么组织、怎么保证质量：

  • 构建链路：Vite / Webpack 的配置边界、构建产物优化
  • 代码组织：Monorepo 还是多仓、包怎么拆分、依赖怎么治理
  • 规范体系：lint / 格式化 / 提交规范 / 代码评审标准
  • 发布策略：灰度、回滚、AB 实验怎么接

3. 组件体系与设计系统 ​

前端特有的复用来源是 UI 组件：

  • 组件分层：基础组件 / 业务组件 / 页面组件的边界
  • 设计系统：样式变量、主题切换、视觉规范怎么落地为代码
  • 组件契约：props 怎么设计才不越权（组件不该知道业务状态）

4. 状态与数据流 ​

前端一半的复杂度在状态管理：

  • 本地状态 / 全局状态 / 服务端状态（缓存）各放哪
  • 数据流方向（单向数据流、事件总线）和跨组件通信的规矩
  • 服务端状态缓存：请求去重、失效策略、乐观更新

5. 跨端与渲染策略 ​

业务跑在哪些端、用什么渲染方式：

  • Web / 小程序 / App（Hybrid / RN / 原生）的共用与差异
  • CSR / SSR / SSG / ISR 的选型与迁移路径
  • 兼容策略：浏览器矩阵、降级方案

前端特有的权衡 ​

权衡两端典型场景
体验 vs 成本原生体验 vs 一套代码跨端核心流程用原生、长尾用 H5
运行时 vs 构建时首屏更快 vs 构建更慢SSR 的权衡
客户端 vs 服务端逻辑放哪更安全/更省校验、权限、埋点
框架 vs 自研跟生态 vs 完全可控组件库选型

一句话总结前端架构：在设备、网络、浏览器兼容三重不可控下，把"体验"做成可持续的工程体系。

四、后端架构师：考虑的问题 ​

后端架构师面对的世界是多用户并发、数据要持久、系统要 7×24 可用。他关心的是：

1. 数据与存储 ​

  • 数据模型设计：实体关系、字段设计、索引策略
  • 存储选型：MySQL / PostgreSQL / MongoDB / Redis 各管什么
  • 规模演进：分库分表、读写分离、归档策略

2. 服务划分 ​

  • 模块边界：按业务域切（订单、库存、用户）还是按技术层切
  • 微服务 vs 单体：独立部署 vs 分布式复杂度（网络、事务、排查）
  • 服务间通信：同步（RPC / HTTP）vs 异步（消息队列），谁调用谁、谁依赖谁

3. 接口契约 ​

  • API 设计：资源模型、语义、错误码规范
  • 版本演进：兼容旧客户端、废弃策略
  • 幂等性：重试安全、重复提交防护

4. 一致性与可靠性 ​

  • 事务边界：ACID 在哪层保证
  • 分布式一致性：最终一致、分布式事务（TCC / SAGA / 本地消息表）
  • 故障应对：重试、超时、熔断、降级、限流——先保可用再保正确的取舍

5. 容量与性能 ​

  • 并发模型：连接池、线程模型、异步化
  • 缓存策略：缓存什么、失效策略、缓存一致性
  • 削峰：消息队列缓冲、批处理

6. 安全 ​

  • 认证授权：会话 / JWT、RBAC 权限模型、数据权限隔离
  • 数据安全：SQL 注入、敏感数据加密、脱敏
  • 接口安全：防刷、限流、CSRF

7. 可观测性与运维 ​

  • 日志规范：结构化日志、请求追踪 ID
  • 指标与告警：核心链路指标、容量水位
  • 链路追踪：跨服务问题怎么定位
  • 发布运维：CI/CD、灰度、蓝绿、回滚预案

后端特有的权衡 ​

权衡两端典型场景
一致性 vs 可用性强一致 vs 最终一致CAP 的取舍
正确性 vs 性能严格校验 vs 快速响应缓存、异步化
单体 vs 微服务简单 vs 独立扩展团队规模、流量规模
同步 vs 异步简单直接 vs 削峰解耦下单流程、通知

一句话总结后端架构：在多用户、数据、故障的三重压力下，把"正确性"和"可用性"做成可持续的系统能力。

五、前端 vs 后端：核心矛盾的差异 ​

维度前端架构师后端架构师
首要约束设备、网络、浏览器兼容并发、数据一致性、可用性
核心矛盾体验与复杂度的平衡正确性与规模的平衡
主要风险首屏慢、卡顿、兼容崩数据错、服务挂、扩容难
架构载体组件体系、状态流、构建链路服务边界、存储模型、消息链路
失败的代价用户流失、口碑受损资损、系统瘫痪
演进动力业务形态变化（跨端、新渲染方式）规模变化（流量、数据量、团队）
最难的决策边界画错→改造成本高且牵动体验数据模型/服务边界定错→几乎重来

一个直观比喻：前端架构像城市规划——道路（构建链路）、街区（模块）、地标（组件）怎么布局，决定城市好不好用；后端架构像水利工程——水源（数据）、管道（服务）、闸门（限流降级）怎么设计，决定系统会不会决堤。 前者服务"人的体验"，后者服务"系统的存续"。

六、架构师的思维模式 ​

把"架构师怎么做决策"提炼成几条可练习的思维：

  1. 权衡，不是最优：面试/讨论时说"我选了 X，因为当时约束是 Y，代价是 Z，将来如果 A 变了会换成 B"——这就是架构师语言
  2. 边界比实现重要：先画清楚"谁负责什么、谁依赖谁"，再谈具体技术
  3. 契约先于实现：接口定了，两端可以并行开工，这是架构决策的杠杆
  4. 决策要可逆：能做成可逆的就不做不可逆的；不可逆的推迟做
  5. 简单优先，演进驱动：不为假想的未来加抽象；等真实需求出现，用最小代价演进（参考 YAGNI 与渐进式架构）
  6. 反面教材：过度设计——为一年后可能出现的需求设计三层抽象，是架构新手最常见的错误。架构是"应对变化的最小结构"，不是"预测变化的全部结构"

七、从开发到架构师：怎么练 ​

架构能力不是"学了架构课"就会，而是在具体项目里反复做结构性决策练出来的。练习路径：

  1. 先把一个模块当系统设计：你负责的页面/服务，画出它的边界、数据流、扩展点——哪怕很小，练习"结构性视角"
  2. 给每个方案记权衡：做技术选型时，写下"选了 A 放弃了 B，因为……代价是……"——这是架构决策的存档习惯
  3. 主动画边界：开发时发现"这个逻辑放这里怪怪的"，停下来想想应该放哪——这就是架构直觉的来源
  4. 读别人的架构：看知名开源项目的目录结构、模块依赖方向，问"为什么这么切"（你研究过的 dsh 插件化设计就是一个很好的样本）
  5. 在评审里练表达：代码评审时讨论的不是"这段代码对不对"，而是"这个边界划得对不对"

前端转全栈的路径上，前端架构师和后端架构师的知识是互补的：前端的体验约束会让后端方案更务实（BFF 就是前端视角催生的架构），后端的正确性思维会让前端方案更严谨（接口契约、错误处理）。全栈架构师不是"两个都会"，而是两边的权衡都看得见，能在边界上做全局最优的决策——这恰恰是架构师区别于单领域工程师的核心能力。
